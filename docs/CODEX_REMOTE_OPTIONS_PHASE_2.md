# Phase 2 Codex 手机远程方案探索

> 当前状态：PTY 方案已于 2026-07-21 完成 macOS、Ubuntu 和手机端验收；remote-control 与 app-server 作为备选保留。

Chub 后续不把产品会话模型限定为 Codex。供应方无关的 Session/Activity 状态、适配器边界和迁移方向
见 [Chub AI Session 状态模型设计](AI_SESSION_STATE_DESIGN.md)；本文继续记录 Codex CLI 的具体实现。

## 1. 目标

让手机通过 Chub 操作 Mac 上的原生 Codex CLI。Codex 继续负责会话、审批、命令执行、文件修改和 Git 操作；Chub 负责可信网络入口、工作区选择、会话权限模式、终端生命周期和移动端访问。

## 2. 方案对比

| 方案 | 方式 | Chub 复杂度 | 手机体验 | 状态 |
| --- | --- | ---: | ---: | --- |
| PTY / Web Terminal | 浏览器直接操作原生 Codex TUI | 中 | 已验证可接受 | 优先 |
| Codex remote-control | 使用官方远程控制与配对能力 | 低 | 待验证 | 保留 |
| Codex app-server | Chub 实现专用 Codex Web 客户端 | 高 | 可深度定制 | 保留 |

`codex exec/resume` 适合固定分析和无人交互任务，可作为补充，不作为完整手机入口的首选。

## 3. 实时终端（PTY）方案

本文统一使用“实时终端”和“快速交互”描述同一 Codex session 的两种交互入口。
“实时终端”指 ttyd/tmux 承载的原生 Codex TUI；“快速交互”指通过普通页面提交的
单次后台任务。

### 3.1 首轮实验

2026-07-20 在 MacBook 上用 `ttyd 1.7.7` 进行了首轮实验：Tailscale IPv4 监听、固定工作目录、原生 `codex` 子进程、可写终端、单客户端。手机通过 tailnet 访问后，Codex TUI 可正常使用。

### 3.2 产品边界

Chub 不解析 Codex 的消息或审批交互，只管理：

- 工作区白名单。
- 会话的创建、进入、状态和停止。
- 会话权限模式：`Ask for approval`、`Approve for me`、`Full access` 和 `Read Only`。
- 会话与工作目录、Codex session 的对应关系。
- Tailscale 监听条件。
- 手机进入终端的页面入口。
- 失控会话的终止。

### 3.3 工作区与会话

手机不接受任意路径。Chub 维护显式工作区列表，每项至少包含 ID、名称、绝对路径和是否允许手机启动 Codex。

会话列表以本机未归档 Codex 会话为准，不区分由谁创建。首版新建入口固定为三个目录：用户目录、Workspace 和 Chub。

首版操作：

- 新建会话：在选定目录启动 Codex。
- 进入会话：连接运行中的 PTY，或恢复已停止的 Codex 会话。
- 停止会话：结束 Codex 和对应 PTY，但保留可恢复记录。
- 归档会话：停止相关进程，并通过 Codex 归档本地会话。
- 删除会话：后台维护接口仍支持停止相关进程并通过 Codex 永久删除本地历史；首页日常操作不提供删除入口。
- 切换权限：保存目标权限；如果会话正在运行，先停止当前 PTY，下一次进入时按新权限启动。
- 强制停止：正常结束失败时终止完整进程组。

### 3.4 断线恢复

正式方案采用两层恢复：

- 运行层：`ttyd → tmux → codex`，浏览器断开只结束客户端。
- 持久层：保存 Codex session ID，必要时使用 `codex resume <session_id>`。

### 3.5 Session ID 与 Hook

`SessionStart` hook 提供 `session_id`、`transcript_path`、`cwd`、`source`。Chub 通过固定 hook 绑定 `CHUB_PTY_SESSION_ID`，再用 session ID 恢复和映射会话。`UserPromptSubmit` 和 `Stop` hook 只用于记录“执行中 / 等待输入”状态。

### 3.6 Web 集成

节点主页显示会话面板，点击会话进入独立终端页。终端页使用同源代理、短期 HttpOnly 凭证和独立 base path；页面返回时恢复会话面板状态。

同一会话只保留一个活动终端连接。新设备进入时接管连接，旧页面自动返回节点页；Codex 继续在本机 tmux 中运行，不因浏览器切换而停止。

### 3.7 Tailscale 下的终端连接排查

Codex PTY 页面由 Chub 代理 ttyd 的 HTTP 资源和 WebSocket。终端是持续的双向实时传输，依赖稳定的低抖动链路。首页、文档等普通 HTTP 页面可以正常访问，并不代表终端 WebSocket 一定稳定；跨网络访问经过质量不稳定的 DERP 中继、发生高延迟、抖动、丢包、MTU 不合适或网络切换时，可能出现 ttyd 页面外壳加载但终端内容不显示、输入无响应或连接中断。Tailscale 中继可以承载 WebSocket，但不稳定的中继路径不适合保证 ttyd 的实时终端体验。

排查时优先确认：

- 浏览器网络面板中的 `/codex/.../terminal/` 是否返回成功。
- `/codex/.../terminal/ws` 是否成功升级为 `101 Switching Protocols`。
- 应用日志中的 `terminal_websocket_accepted`、`terminal_websocket_disconnected`、`terminal_websocket_failed` 和 `terminal_http_*` 记录。

日志只记录会话和连接状态，不记录 Token、Cookie 或终端输出。普通 HTTP 页面正常而 WebSocket 失败时，应优先检查 Tailscale 路径稳定性、DERP 中继、丢包和 MTU，而不是重复检查文档或首页接口。

ttyd 实时终端本身不提供轮询、终端快照或命令队列等降级模式。无法获得稳定直连或可靠中继时，
应将 Codex PTY 视为网络条件不满足；此时可以改用下方独立的快速交互入口，而不是把普通页面可访问
作为终端可用的判断依据。

### 3.8 普通网络快速交互

为适应无法稳定承载 ttyd WebSocket 的普通网络，补充一个不进入实时终端页面的快速交互入口。该能力使用 Codex CLI 的非交互恢复命令，将用户输入作为新的 turn 发送到已有 Codex session，并在任务完成后返回最终结果：

```text
普通页面输入
  → Chub 固定选择 session、工作目录和权限配置
  → codex exec resume <SESSION_ID> <PROMPT>
  → 读取 JSONL 状态和最终回答
  → 普通 HTTP 轮询任务状态并展示结果
```

#### 设计边界

- 复用已有 `codex_session_id` 和会话上下文，不通过 `tmux send-keys` 模拟终端输入。
- 权限模式由 Chub 固定映射到 Codex CLI 配置，不由客户端通过任意命令或配置传入；用户需求文本通过参数或 stdin 传递，不能拼接成 shell 命令。
- `Read Only` 适合分析和检查；`Approve for me` 可用于自动审核型后台任务；`Full access` 风险最高；`Ask for approval` 在没有 ttyd 页面时无法处理需要人工确认的请求，因此第一版直接要求进入实时终端。
- 同一 session 不允许多个快速交互任务并发执行；实时终端正在执行时也拒绝快速交互。快速交互执行期间禁止进入实时终端，避免用户从未刷新外部记录的 TUI 中提交并发任务。
- 后台任务以 JSONL 模式运行，执行阶段通过操作日志记录，并使用最终消息文件读取最终回答；输出、输入和任务记录都必须设置大小上限，不能把完整终端内容写入运行日志。
- Chub 必须向后台进程传入现有 hook 所需的 session 绑定环境，使 `UserPromptSubmit`、`Stop` 等状态仍能回写对应 Chub session。
- 页面使用普通 HTTP 轮询任务状态，不依赖 ttyd WebSocket；任务需要持续审批、实时追问或中途输入时，提示用户进入 ttyd。

当前已实现后台任务 API、任务状态持久化、并发互斥和前端提交/结果展示。任务通过受保护的
`POST /api/codex/sessions/{session_id}/quick-interactions` 创建，再通过
`GET /api/codex/quick-interactions/{task_id}` 查询单个任务，或通过
`GET /api/codex/sessions/{session_id}/quick-interactions` 恢复该 session 的历史；任务完成后返回
Codex 的最终结果，不建立 ttyd WebSocket。任务状态文件保存在 Codex PTY 数据文件旁，服务重启时
未完成任务会标记为失败，临时执行文件只在任务运行期间存在。

快速交互页面顶部负责发布任务，下方恢复当前 session 通过快速交互提交的需求、状态、最终结果或失败原因，
默认展示最新 3 条，底部“加载更多”每次继续读取 3 条；历史仍保存在 Chub 本地，常规保留上限为
30 条快速交互任务，接口使用有界分页，不一次返回全部结果。用户可以在记录右上角置顶或取消置顶；
每个 Session 始终先展示最近创建的一条，其后按置顶时间倒序展示置顶记录，再按创建时间倒序展示普通记录。
最近一条即使已置顶也只展示一次，新任务产生后原最近记录按自身置顶状态进入对应区域。置顶状态写入本地任务
状态文件并在服务重启后保留；置顶记录和存在置顶记录时该 Session 的最新记录不参与普通历史清理，因此极端情况下
持久化总数可以暂时超过 30 条。排序在分页前由后端统一完成，避免页面只重排当前已加载记录。页面在存在运行中任务、Session
仍在执行或运行中状态未知时轮询，页面隐藏后暂停，重新显示时立即刷新。页面使用当前标签并依赖
浏览器返回，不增加专用返回按钮。
Codex CLI 以 JSONL 模式输出的 `error` 和 `turn.failed` 事件会经过长度限制和脱敏后展示，额度不足、
限流或认证失败等原因不再统一折叠为“执行失败”。

第一版的边界：Ask for approval 必须进入实时终端完成审批，因此快速交互入口对该权限模式禁用；
会话尚未启动、实时终端正在执行或同一 session 已有快速交互任务时拒绝提交；
实时终端明确空闲时，无论是否仍有浏览器连接，都保持 TUI/tmux 运行，同时通过
`codex exec resume` 执行快速交互。
快速交互运行超过 10 分钟时只提示“执行时间较长，仍在运行”，不终止仍在执行的 Codex 进程。
真正的总执行上限由 `codex_pty.quick_interaction_timeout_seconds` 配置，默认 21600 秒（6 小时），
允许范围为 10 分钟至 24 小时；只有达到该上限才终止进程并记录为 `timed_out`。单次输入最多
8000 字符，最终结果最多返回 100000 字节。操作日志记录 requested、started、
succeeded/failed 或 timed_out 状态，但不记录用户输入和结果正文。

互斥检查在用户点击“执行”时由后端重新读取 session 状态，不依赖页面已加载的旧状态；反向进入
实时终端时也会检查该 session 是否存在运行中的快速交互。两条入口使用同一 session 级协调锁，
避免不同设备同时提交导致的检查与启动竞态。

#### 首页统一状态与轮询

首页使用统一的 Session 活动状态，并通过 `activity_source` 区分本次执行由实时终端还是快速交互
触发。后台内部短暂的 `requested` 不作为产品状态展示；从提交被接受到任务成功、失败或超时结束，
首页显示“快速交互 · 执行中”，结束后清除来源并显示“会话 · 等待输入”。执行期间禁用重复提交、
进入实时终端、停止、归档和删除；已有实时终端连接可以继续接收输出，但不能再向 Codex 写入。
前后端使用同一 session 级协调机制避免检查与操作竞态，“交互记录”仍可正常查看。
停止、权限切换、归档和删除在产生连接副作用前完成互斥检查；实时终端输入转发与快速交互
启动使用同一 session 锁串行化。

首页为每个 Session 提供“实时终端 / 快速交互”两态入口切换按钮。按钮显示当前入口，点击后立即
切换为另一入口，不打开弹窗、不显示下拉箭头，也不要求再次保存。选择结果仅作为当前浏览器的导航偏好
保存在本地，不复用 `activity_source`。点击 Session 时按当前入口进入对应页面；首页不再单独展示
“快速交互”和“交互记录”按钮。快速交互页面顶部提供任务输入与执行入口，下方展示任务状态、
结果和历史记录。尚未建立原生 Session 时固定使用实时终端。

快速交互输入区按普通卡片布局：标题使用与其他卡片一致的字号，执行按钮位于输入框下方，不沿用
弹窗标题和顶部操作布局。标题区域可以折叠输入内容，不显示额外箭头，也不持久化折叠状态。当前页面
提交成功后先完整折叠输入卡片，再刷新并展示新增交互记录，避免两个区域同时改变布局；任务结束后不自动展开。重新进入或刷新页面时，仅当快速交互仍在执行才默认折叠，
否则默认展开，之后由用户手动控制。输入区不重复展示“执行中”，执行状态统一由下方交互记录呈现。
权限、终端占用、会话异常和状态未知确认等会影响下一步操作的信息仍保留在输入区。
点击执行后的提交过程不在输入区增加临时状态文案，只禁用输入框和执行按钮；执行状态继续由交互记录等既有位置呈现，避免临时消息改变卡片高度。

自动刷新只原位更新状态或内容发生变化的任务记录，新任务插入顶部，已经完成且未变化的历史记录不重建，
避免打断长内容阅读、文本选择和滚动位置。输入卡片状态与交互记录分别处理请求失败：一部分刷新失败时，
另一部分仍可保留并更新自己的最近成功内容。
置顶按钮位于记录卡片右上角的时间右侧；操作期间只禁用当前按钮，成功后按后端结果重新读取并排序，失败时保留
原位置并单独提示。按钮使用原生 `button`、`aria-label` 和 `aria-pressed`，手机端保留足够点击高度。

首页继续只轮询 `GET /api/codex/sessions`：存在 `activity=working`，或存在 PTY
`running + unknown` 时继续轮询；快速交互执行期间固定使用快速轮询，页面隐藏时暂停，
重新显示时立即刷新，所有活动状态结束后停止。快速交互提交成功后立即定向刷新 Codex 卡片，
不为每个 session 额外查询任务列表。快速交互页面独立轮询当前 Session 状态和有界历史列表，
终端页仍使用 WebSocket。

快速交互与实时终端只在实际执行阶段互斥。会话为 `running + idle` 时，无论是否存在活动或正在
建立的终端 WebSocket，都保留 ttyd/tmux 和现有连接并直接启动 `codex exec resume`；
实时终端为 `working` 时仍拒绝提交。
服务重启后状态为 `unknown` 时，页面要求用户明确
确认可能中断任务；警告已经显示时，点击“执行”本身即表示确认，不增加额外勾选项。若页面打开后
后端状态才变为 `unknown`，第一次提交只在当前页面补充警告，用户再次点击后才携带确认。后端收到
确认后仍重新读取状态：若已变为 `working` 则拒绝，若为 `idle` 则正常切换，仍为 `unknown` 才
按确认停止。停止成功但快速交互启动失败时保留真实的已停止状态和失败任务记录，不伪造回滚或成功。

服务重启时，持久化中仍为 `requested/running` 的快速交互会标记为失败并清理
`activity_source=quick`。若实时终端仍存活，Activity 回退为 `unknown`；否则回到 `idle`。

### 3.9 安全边界

- Chub 只监听节点的 Tailscale IP。
- ttyd 只监听本机。
- 不使用 Funnel，不提供公网或普通局域网入口。
- 首页提供四种权限模式选择，并映射到 Codex CLI 的工作区、只读和完全访问配置；具体审批交互仍由 CLI 原生界面管理。
- 终端输出不写入 Hub 活动日志。

### 3.10 验收结果

2026-07-21 已完成 macOS、Ubuntu 和手机端验收：会话新建、进入、停止、恢复和归档正常；删除后台接口保留；长输出可滚动查看；浏览器退出和跨设备接管不会停止本机 Codex；新设备进入后旧页面会自动返回节点页；节点维护、跨平台运行和移动端布局符合当前使用要求。

## 4. 结论

实时终端方案已经通过当前阶段三端验收：手机可操作 macOS 与 Ubuntu 节点上的原生 Codex TUI，且能保留会话、恢复和安全边界。实时终端方向正式收尾；普通网络快速交互作为独立的补充方案继续设计，不替代 ttyd 的实时终端。remote-control 与 app-server 继续保留为备选方案。
