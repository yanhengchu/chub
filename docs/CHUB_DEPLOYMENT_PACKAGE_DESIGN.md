# Chub 正式部署包与安装设计

> 状态：已验收
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：Chub 正式部署包的构建内容、内含正式插件包、目标设备安装流程、可选 OpenClaw 接入、状态隔离和验收边界。
> 本文不负责：已部署实例的升级与恢复、Runtime 或任务编排插件的 ZIP 协议、OpenClaw/微信业务路由或账号配置；这些内容由对应专项设计维护。

## AI 可执行契约

1. 正式部署包只能从**本地 Git 当前已提交的 HEAD**构建，不是当前设备目录、磁盘镜像或运行态备份。发布前 `git status --porcelain=v1 --untracked-files=all` 必须为空；受版本控制和未跟踪的项目内容都必须先由维护者完成本地提交，已忽略的本机配置、运行态和发布物不属于该门禁。构建只能使用固定包含与排除清单，页面和外部入口不得提供任意源路径、输出路径或 ZIP 内容。
2. 版本发布使用维护页填写的一个发布版本生成当前 Codex Runtime 和微信任务编排的正式 ZIP。填写版本必须与 `pyproject.toml`、Codex Runtime 源清单和微信任务编排源清单中的已提交版本完全一致；发布只校验，不修改这些源文件或当前节点版本。任一扩展产物无法构建或摘要无法确认时，主包不得生成成功结果。
3. 发版说明默认不保存，页面首次打开或刷新时为空。维护者可直接手工填写，或点击“生成发版说明”由固定“版本发布说明”内部 Session 生成；生成任务复用新 Session 通用设置，以本次操作前最近一次成功发版记录保存的 tag/commit 到当前 HEAD 为基线，并综合当前暂存、未暂存和未跟踪的项目改动；同版本重复发布后的记录和 tag 以其最新位置为准。首次发布改为概括当前工作区内容。AI 结果只在当前页面流程自动填入，可编辑；服务端只为发起页面的短期随机令牌保留当前一个草稿，令牌仅通过受保护请求头传递，有效期固定为 30 分钟。重新生成、失败、过期、发布开始或 Web 重启时清理。刷新或 Web 重启后丢弃，绝不自动发布。
4. 主包只随包交付插件 ZIP；新设备安装 Chub 不自动导入、不自动启用 Runtime 或微信任务编排插件。目标设备必须在 Chub 可用后，将所需 ZIP 放入对应固定制品目录，再通过“插件管理”的统一生命周期显式导入、启用并选择版本。
5. 包内包含 Chub 内置 Debug Chrome 实现，但不得包含来源设备的本机配置、账号、Token、Cookie、浏览器 Profile、Session、任务、运行锁、日志、缓存、构建环境或第三方运行态。目标设备必须重新创建本机配置，并按需初始化独立 Profile 和完成外部账号授权。
6. Chub 核心部署与 OpenClaw 安装是独立结果。部署 AI 可以在维护者选择后执行固定的 OpenClaw 安装和检查，但 OpenClaw 未安装、配置失败或通道未验收不得使 Chub 核心部署失败，也不得自动清理已成功部署的 Chub。
7. 包内 `DEPLOY_WITH_AI.md` 是目标设备 AI 的唯一通用部署操作入口：它先执行共享的依赖、安装、配置、健康和最终状态确认，再按 macOS、原生 Ubuntu 或 Ubuntu WSL2 进入必要的平台关注事项。Ubuntu 用户服务确认 linger 配置；WSL2 还必须确认当前会话为 Version 2，并额外验证 Windows localhost 和重启恢复。AI 必须在源 ZIP 父目录生成不含秘密、可在重连后继续更新的部署报告，并只能按明确的 `succeeded`、`failed` 或 `recovery_pending` 标准收敛。仅在维护者选择后继续 Runtime/任务编排插件导入或 OpenClaw 接入；涉及凭据、账号、微信绑定或真实微信收发时停止并交给维护者。

## 发布物与构建边界

### 正式部署包

所有部署包正式 ZIP 统一命名为 `<名称>-release-<版本>-<UTC分钟>-<Git短hash>.zip`。一次部署包构建中的三个产物使用同一个构建标识：主包为 `chub-release-<版本>-<构建标识>.zip`，随包模块为 `codex-runtime-release-<版本>-<构建标识>.zip` 与 `weixin-refinement-release-<版本>-<构建标识>.zip`；构建标识使用 UTC 到分钟和当前 HEAD 的 12 位短 hash。主包固定写入 `data/local/artifacts/releases/`。每个包包含：

- Chub 主程序、页面资源、固定脚本、内置 Debug Chrome 实现、示例配置、依赖声明和目标设备安装所需服务定义；
- 受控的项目文档及包内 `DEPLOY_WITH_AI.md`；
- 当前构建出的 Codex Runtime 正式 ZIP 与微信任务编排正式 ZIP；
- 发布清单：Chub 版本、构建标识、构建时间、维护者填写的发版说明、每个内含扩展的文件名、版本/标识和 SHA-256，以及每个文件的受控清单与摘要。构建测试还必须从解压后的主包冷导入 Chub 内置 Debug Chrome 调用层，不能只按文件名判断该能力可用。

构建不复制 `.venv`、`node_modules`、`.git`、本机 `config/*.local.yaml`、`data/local/`、日志、测试缓存、Python 缓存、临时文件或既有发布物。配置只固定包含示例配置、自动化模板和系统升级计划，不随包复制 `config/automations.yaml` 或其他未登记配置。Chub OpenClaw 插件的仓库源码、构建说明和已验证补丁清单可随主程序交付；OpenClaw 本体、其运行目录、账号、配置和依赖不属于 Chub 发布包。插件模块开发源码是否随包由本次发布配置决定；无论是否包含源码，两个正式插件模块 ZIP 都必须随包交付。

发布包使用临时文件完成构建。两个随包插件 ZIP 必须先在独立临时安装目录按各自导入预检验证协议、版本兼容性和入口可加载性；随后主 ZIP 与发布清单必须完成成员和摘要校验，才原子发布。生成按钮只创建当前构建产物并展示构建标识、时间、内含扩展、大小和摘要；它不重启 Web/Worker、不修改当前 Runtime 默认实现、不导入扩展，也不影响已受理任务。

发布物只保留在固定输出目录。同一 Chub 版本正常只保留最新一次成功构建的主 ZIP 和 `history/chub-release-<版本>.json` 唯一发版记录；其他版本不受影响。发版记录包含构建标识、提交、当前和前序 tag 引用、产物与随包模块摘要、构建环境依赖快照和维护者在发布页填写的发版说明；不得写入账号、路径、Token 或其他秘密。新产物、tag 和发版记录完成后，Chub 清理同版本旧 ZIP；若本机文件系统拒绝清理，发布仍以新产物、tag 和记录已完成为成功，但页面必须明确提示残留数量和手动处理位置。发布失败恢复旧 tag 与旧记录，并保留上一轮成功发布物，不影响已部署节点、已导入模块或正在运行的服务。

### 扩展产物

Codex Runtime 与微信任务编排插件继续遵循各自现有 ZIP 协议、版本标识、内容摘要、导入/覆盖和任务快照规则。部署包只负责将同次构建产生的正式 ZIP 放到固定的 `bundled-modules/` 目录；不能以此绕过插件预检、Web/Worker 双端注册、活动实现选择或插件删除保护。

构建完成后，发布清单中的摘要是目标设备导入前核对交付物一致性的依据；它不替代目标设备导入操作的最终注册确认。

## 发布配置与页面操作

“维护与版本”页提供“版本发布”卡片，只提供一个发布版本。页面显示三个已提交的源版本，并提示发布版本必须与它们一致。

- **发布版本**：同时用于主部署包、Codex Runtime ZIP、微信任务编排 ZIP 和本地 tag `chub-v<版本>`。它不是改版本的入口；维护者必须先在源文件中完成版本变更并本地提交。Codex 正式槽位标识与 Runtime 描述由后端固定管理，不在页面单独配置。
- **发版说明**：写入本次 ZIP 清单和该版本唯一发版记录的本地发布元数据；不属于 Git 提交门禁。页面默认和刷新后均为空；手工填写任意非空说明，或 AI 生成成功自动填入后，都会显示“发布版本”。生成时记录的版本、提交和工作区快照只用于组织说明内容；生成成功后不因它们变化撤销草稿或阻止发布。设置保存接口不接受说明字段；生成结果不作为发布配置保存，刷新或 Web 重启后必须重新生成。生成过程创建或复用“版本发布说明”内部 Session，默认在 Runtime Sessions 主列表隐藏，可在会话设置单独显示。不得填写凭据、账号、Token、内网地址或其他秘密。

生成只要求当前目录可读取为 Git 工作区，并不要求工作区干净、版本声明一致或 Git 提交者身份可用；这些仍是正式发布门禁。开始时记录目标版本、目标 HEAD、工作区变更指纹与最近成功发版记录的 tag/commit，供生成说明时参考。生成结果固定为首行直接描述本次发布和 3-6 条能力摘要，不加“概述”前缀：首次发布按实际能力域概括，后续发布只写本次变化。任务终态由 Quick Worker 回调回传当前 Web 实例和操作日志；生成成功后保留本页草稿，不因版本、提交或工作区变化标记过期。生成 Session 采用通用设置，属于维护者授信的本机任务；提示词要求其不修改项目，但不将其表达为独立的只读执行边界。Quick Worker 或 Runtime 不可用时，只有 AI 生成功能不可用，手工填写说明仍可显示发布入口。实际点击“发布版本”仍执行完整发布前检查，且说明为空时明确拒绝。

版本设置读取失败时不允许发布。登记发布前，Quick Worker 必须处于 `ready` 且执行中、排队任务均为零；Worker 忙碌或状态无法确认时明确拒绝，不登记发布操作、不生成 ZIP、不变更 tag，待其空闲后重试。随后 Chub 检查本地 Git 工作区干净、本地 Git 提交者身份可用、HEAD 在构建期间未变化，并校验页面版本与三个已提交源版本一致。发布不执行 Git `commit`、`pull` 或 `push`，也不修改项目版本文件、当前节点 `app.version`、默认 Runtime、已导入模块、已绑定 Session 或已受理任务。维护者自行决定何时提交、推送或按既有流程升级运行环境。页面不得接受任意输出路径、模块路径、命令或构建参数。

卡片提供“包含插件模块开发源码”开关，默认关闭。关闭时，主包不包含 `runtime-modules/` 与 `orchestration-modules/` 的开发源码，只提供两个正式插件 ZIP；目标设备可先部署 Chub 核心，再按需导入。开启时，主包额外包含当前受控开发源码，供维护者在目标设备使用现有开发实现和刷新流程；它不自动导入或启用正式插件 ZIP，也不复制来源设备的模块安装状态。

点击“发布版本”后，Web 只登记后台固定发布流程。页面与 `scripts/build_chub_release_zip.py` 都使用同一发布路径：先检查 Quick Worker 和 Git 基线，再在受限临时目录完成主包、两个扩展包和清单校验；校验通过后写入 `data/local/artifacts/releases/`，创建或更新本地带注释 tag `chub-v<版本>`，再覆盖该版本唯一发版记录。相同版本可重复发布：新成功构建替换旧 ZIP、旧记录和 tag 指向，tag 移到新的 HEAD，记录写入最新发版说明。页面轮询操作终态，确认成功后展示产物名称、大小、提交、tag、发版记录名称和说明，完整文件摘要保存在包内发布清单。tag、记录或成功状态写入失败时，Chub 回滚本次 tag 与记录变更并清理本次产物，不重启 Web/Worker，也不影响已受理任务。

同一时刻只允许一个版本发布操作。已有发布处于 `requested` 或 `started` 时，新的发布请求明确返回当前状态；它不创建第二个并行操作，也不阻止无关的只读、任务执行或第三方服务能力。发布运行依附当前 Web 实例；若服务重启或进程结束导致其无法继续，下一实例必须将该操作记录为失败并允许重新发布，不能长期显示为“发布中”。

## 目标设备部署

### Chub 核心部署

目标设备解压正式包后，按 `DEPLOY_WITH_AI.md` 执行固定流程：

1. 检查支持的平台、发行版默认 Python 版本和基础命令；当前支持 macOS LaunchAgent 与 Ubuntu systemd user service。Windows WSL 只允许以 Ubuntu WSL2、systemd 已启用且 `systemctl --user` 可用的路径部署，不把 WSL1、非 Ubuntu 发行版或未启用 systemd 的环境视为可部署平台。
2. 创建新的 Python 环境并通过受控超时的正常网络安装声明的依赖；只有维护者已提供可信镜像时才使用镜像重试。
3. 从示例创建 `config/settings.local.yaml`，由维护者填写新设备节点、可信网络和可选服务配置。
4. 安装 Chub Web、Quick Worker 及固定服务定义，随后确认 Web 和 Worker 的健康状态，并在源 ZIP 父目录写入脱敏的部署报告。报告是部署交付物，不得包含配置、日志、账号或秘密；它不授权将项目、虚拟环境或运行态写入 Windows 挂载目录。

Web 健康、Quick Worker 健康和服务安装后的可恢复状态都已确认，才表示 Chub 核心部署成功。仅解压、依赖安装完成、服务进程创建或 HTTP 200 均不单独表示部署成功。

### 可选扩展导入

核心部署成功后，设置页“插件管理”会自动发现解压目录 `bundled-modules/` 中的正式 ZIP，可直接导入并启用；如需从其他位置恢复制品，也可分别放入 `data/local/artifacts/plugins/runtime/` 或 `data/local/artifacts/plugins/weixin-orchestration/`。Runtime 还需在 Codex 设置中选择当前使用版本；微信任务润色在其设置中选择已启用版本。未导入任一扩展不影响 Chub 核心运行；导入失败只按该扩展的恢复边界收敛，不回滚 Chub 核心部署。部署包未包含开发源码时，目标设备不提供 `codex-runtime-dev` 或微信开发实现；这不是核心部署故障，维护者可导入随包正式 ZIP 后继续使用对应能力。

### 可选 OpenClaw 接入

`DEPLOY_WITH_AI.md` 必须提供“跳过 OpenClaw”和“安装/接入 OpenClaw”两条明确路径，默认先完成 Chub 核心部署。选择 OpenClaw 后，AI 只能按仓库登记的兼容基线安装第三方依赖、构建并部署 Chub 插件、完成固定配置检查和 Gateway 健康检查；不得猜测第三方版本、安装位置、微信账号、Owner 或凭据。

OpenClaw 接入的成功条件独立于 Chub：插件加载、Gateway 就绪、已配置通道及兼容基线确认后，才可报告该子项成功。真实微信文字、语音、点击和收件仍只能由维护者本人在客户端完成。未选择、无法安装或未完成 OpenClaw 配置时，Chub 应继续显示其为未配置/不可用，而不是将整个节点判为异常。

## 页面与操作边界

“维护与版本”页面新增正式部署包生成入口时，只允许可信来源调用固定构建动作。页面的“发版产物”区域显示最近一次成功构建的版本、构建标识、时间、大小、内含扩展、摘要和发版说明，并可通过固定“打开”动作请求本机文件管理器打开配置的发布目录；页面不提供 Web 下载、文件浏览或任意路径输入。

构建操作记录 `requested`、`started`、`succeeded` 或 `failed`。生成请求被受理不代表产物可用；只有 ZIP、内含扩展和发布清单完成校验，且本地 tag 与发版记录均写入后才显示成功产物信息。构建失败保留上一轮成功包，不阻止无关的状态查看、Quick Worker、OpenClaw 或已受理任务。

## 与升级和恢复的关系

正式部署包用于新设备或全新目录的安装，不替代现有设备上的“升级与恢复”。升级与恢复仍只处理 Chub 自有 AI 运行态、Web 与 Quick Worker，且不复制、覆盖或迁移用户配置、OpenClaw、浏览器、原生 Runtime 数据或第三方账号。

目标设备从部署包首次安装后，后续维护继续使用既有 `chub` 服务管理、Web 重启、Worker 恢复、Runtime 插件维护和 OpenClaw 重启与恢复流程。不得用重新解压部署包替代已部署节点的受控升级恢复。

## 验收范围与复检

实现后至少验证：

- 构建包包含主程序、发布清单和两个可独立校验的正式插件 ZIP；
- 工作区不干净或页面版本与三个已提交源版本不一致时，发布明确拒绝且不生成产物、不变更 tag；
- 维护页正确展示三个已提交源版本；说明为空时可创建或复用隐藏的版本发布说明 Session，并以最近成功发版记录的最新 tag/commit 与当前 HEAD 生成可编辑摘要；成功发布后主包、两个插件 ZIP、包内清单、当前 HEAD、本地 `chub-v<版本>` tag 与唯一发版记录一致；同版本重复发布会替换旧 ZIP、旧记录和 tag 指向；
- 开发源码开关分别覆盖“未包含开发源码但可部署并导入正式 ZIP”和“包含开发源码且可使用现有开发流程”；
- 本机配置、凭据、运行态、日志、缓存和依赖目录不在包内；
- 在新目录完成 Chub 核心安装后，Web、Worker 和适用的平台服务恢复均可确认，且源 ZIP 父目录生成不含秘密的部署报告；
- Runtime 与微信编排 ZIP 可放入固定制品目录后由插件管理导入，且未导入时不影响核心部署；
- 跳过 OpenClaw 的部署成功，及选择 OpenClaw 后其失败不影响已完成的 Chub 核心部署；
- 构建失败、摘要不一致和单个扩展构建失败均不会产生半成品成功结果或泄露路径/敏感信息。
