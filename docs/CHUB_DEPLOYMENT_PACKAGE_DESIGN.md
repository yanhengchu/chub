# Chub 正式部署包与安装设计

> 状态：已验收
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：Chub 正式部署包的构建内容、内含正式插件包、目标设备核心安装流程、状态隔离和验收边界。
> 本文不负责：已部署实例的升级与恢复、Runtime 或任务编排插件的 ZIP 协议、OpenClaw/微信业务路由或账号配置；这些内容由对应专项设计维护。

## AI 可执行契约

1. 正式部署包只能从**本地 Git 已提交的 HEAD**构建，不是当前设备目录、磁盘镜像或运行态备份。发布开始前 `git status --porcelain=v1 --untracked-files=all` 必须为空；受版本控制和未跟踪的项目内容都必须先由维护者完成本地提交，已忽略的本机配置、运行态和发布物不属于该门禁。若输入的是更高版本，受控发布流程只更新固定的六个版本/兼容版本声明并创建本地版本提交，再以该新 HEAD 构建；同版本重发不创建空提交。构建只能使用固定包含与排除清单，页面和外部入口不得提供任意源路径、输出路径或 ZIP 内容。
2. 版本发布使用维护页填写的一个目标版本生成当前 Codex Runtime 和微信任务编排的正式 ZIP。版本必须是 `MAJOR.MINOR.PATCH`，且不得低于当前源码声明与最近成功发布记录中的较高版本；允许同版本重发或更高版本升级。升级时，发布流程统一更新 `pyproject.toml`、默认配置、Codex Runtime 与微信任务编排源清单中的版本及 Chub 兼容版本，并创建固定本地提交；任一扩展产物无法构建或摘要无法确认时，主包不得生成成功结果。
3. 发版说明默认不保存，页面首次打开或刷新时为空。维护者可直接手工填写，或点击“生成发版说明”由固定“版本发布说明”内部 Session 生成；生成任务复用新 Session 通用设置，以本次操作前最近一次成功发版记录保存的 tag/commit 到当前 HEAD 为基线，并综合当前暂存、未暂存和未跟踪的项目改动；同版本重复发布后的记录和 tag 以其最新位置为准。首次发布改为概括当前工作区内容。AI 结果只在当前页面流程自动填入，可编辑；服务端只为发起页面的短期随机令牌保留当前一个草稿，令牌仅通过受保护请求头传递，有效期固定为 30 分钟。重新生成、失败、过期、发布开始或 Web 重启时清理。刷新或 Web 重启后丢弃，绝不自动发布。
4. 主包只随包交付插件 ZIP；核心部署流程不导入、不启用 Runtime 或微信任务编排插件，也不将它们纳入部署成功条件。工作站启动后，维护者根据实际环境手动决定是否将所需 ZIP 放入对应固定制品目录，并通过“插件管理”的统一生命周期显式导入、启用和选择版本。
5. 包内包含 Chub 内置 Debug Chrome 实现和可独立运行的 `config/settings.yaml` 默认配置，但不得包含来源设备的本机覆盖配置、账号、Token、Cookie、浏览器 Profile、Session、任务、运行锁、日志、缓存、构建环境或第三方运行态。目标设备仅在需要覆盖默认值时创建 `config/settings.local.yaml`，并按需初始化独立 Profile 和完成外部账号授权。本机覆盖不得包含 `app.version`：该字段是发布控制的唯一版本声明；发现该覆盖时 Chub 完整忽略该本机配置并记录脱敏原因，避免运行节点版本与已发布源码不一致。
6. Chub 核心部署与 OpenClaw、Runtime、插件包及其他第三方能力的后续配置相互独立。部署 Agent 不安装、接入或检查这些能力；维护者在工作站启动后按实际环境手动处理。它们未安装、配置失败或未验收不得使 Chub 核心部署失败，也不得自动清理已成功部署的 Chub。
7. 包内 `DEPLOY_WITH_AI.md` 是目标设备 AI 的唯一通用部署操作入口：它先执行核心依赖、安装、配置、健康和最终状态确认，再按 macOS、原生 Ubuntu 或 Ubuntu WSL2 进入必要的平台关注事项。Ubuntu 用户服务确认 linger 配置；WSL2 还必须确认当前会话为 Version 2，并以 WSL 内 `chub check` 作为部署确认。流程不执行 `wsl.exe --shutdown`，以免触发 Windows `wslrelay` localhost 转发的不稳定状态。需要 Windows localhost 时，维护者可在平级 `chub-local-modules/loopback-forwarder/` 放置固定 TCP forwarder，并单独注册 `chub-loopback-forwarder.service` 将 `0.0.0.0:8081` 转到 Chub 的 `127.0.0.1:8080`；该外置模块不随正式包升级覆盖，也不属于核心部署成功条件，Windows 可选检查只通过 `localhost:8081` 进行。AI 必须在部署目录平级目录生成不含秘密、可在重连后继续更新的部署报告及长期 `DEPLOYMENT_NOTES.md`；报告固定命名为 `<source-zip-stem>-report.md`，同名时仅追加受控序号，并使用唯一隐藏检查点恢复报告路径、状态和阶段。Runtime、插件包、OpenClaw 和其他第三方能力不属于部署流程，工作站启动后由维护者按实际环境手动配置。
8. 正式 ZIP 必须将 Chub 运行脚本以 Unix `0755` 元数据写入，不能依赖构建环境当前 umask。目标设备在首次执行脚本前仍固定执行 `find scripts -type f -exec chmod u+x {} +` 并确认 `scripts/chub` 可执行，以覆盖 Windows 解压工具、WSL 挂载文件系统和不保留 ZIP 权限元数据的解压实现；该步骤只作用于新解压目录，不修改来源 ZIP 或既有部署。内部平台适配脚本同样属于该权限范围，但不形成新的维护者 CLI。

## 发布物与构建边界

### 正式部署包

所有部署包正式 ZIP 统一命名为 `<名称>-release-<版本>-<UTC分钟>-<Git短hash>.zip`。一次部署包构建中的三个产物使用同一个构建标识：主包为 `chub-release-<版本>-<构建标识>.zip`，随包模块为 `codex-runtime-release-<版本>-<构建标识>.zip` 与 `weixin-refinement-release-<版本>-<构建标识>.zip`；构建标识使用 UTC 到分钟和当前 HEAD 的 12 位短 hash。主包固定写入 `data/local/artifacts/releases/`。每个包包含：

- Chub 主程序、页面资源、固定脚本、内置 Debug Chrome 实现、完整默认配置、依赖声明和目标设备安装所需服务定义；
- 受控的项目文档及包内 `DEPLOY_WITH_AI.md`；
- 当前构建出的 Codex Runtime 正式 ZIP 与微信任务编排正式 ZIP；
- 发布清单：Chub 版本、构建标识、构建时间、维护者填写的发版说明、每个内含扩展的文件名、版本/标识和 SHA-256，以及每个文件的受控清单与摘要。构建测试还必须从解压后的主包冷导入 Chub 内置 Debug Chrome 调用层，不能只按文件名判断该能力可用。

构建不复制 `.venv`、`node_modules`、`.git`、本机 `config/*.local.yaml`、`data/local/`、日志、测试缓存、Python 缓存、临时文件或既有发布物。配置只固定包含 `config/settings.yaml`、自动化模板和系统升级计划，不随包复制 `config/automations.yaml` 或其他未登记配置。Chub OpenClaw 插件的仓库源码、构建说明和已验证补丁清单可随主程序交付；OpenClaw 本体、其运行目录、账号、配置和依赖不属于 Chub 发布包。插件模块开发源码是否随包由本次发布配置决定；无论是否包含源码，两个正式插件模块 ZIP 都必须随包交付。

发布包使用临时文件完成构建。两个随包插件 ZIP 必须先在独立临时安装目录按各自导入预检验证协议、版本兼容性和入口可加载性；随后主 ZIP 与发布清单必须完成成员和摘要校验，才原子发布。生成按钮只创建当前构建产物并展示构建标识、时间、内含扩展、大小和摘要；它不重启 Web/Worker、不修改当前 Runtime 默认实现、不导入扩展，也不影响已受理任务。

发布物只保留在固定输出目录。同一 Chub 版本正常只保留最新一次成功构建的主 ZIP 和 `history/chub-release-<版本>.json` 唯一发版记录；其他版本不受影响。发版记录包含构建标识、提交、当前和前序 tag 引用、产物与随包模块摘要、构建环境依赖快照和维护者在发布页填写的发版说明；不得写入账号、路径、Token 或其他秘密。新产物、tag 和发版记录完成后，Chub 清理同版本旧 ZIP；若本机文件系统拒绝清理，发布仍以新产物、tag 和记录已完成为成功，但页面必须明确提示残留数量和手动处理位置。发布失败恢复旧 tag 与旧记录，并保留上一轮成功发布物，不影响已部署节点、已导入模块或正在运行的服务。

### 扩展产物

Codex Runtime 与微信任务编排插件继续遵循各自现有 ZIP 协议、版本标识、内容摘要、导入/覆盖和任务快照规则。部署包只负责将同次构建产生的正式 ZIP 放到固定的 `bundled-modules/` 目录；不能以此绕过插件预检、Web/Worker 双端注册、活动实现选择或插件删除保护。

构建完成后，发布清单中的摘要是目标设备导入前核对交付物一致性的依据；它不替代目标设备导入操作的最终注册确认。

## 发布配置与页面操作

“维护与版本”页提供“版本发布”卡片，维护者填写一个目标发布版本。页面显示当前 Chub、Runtime 和微信编排源码版本，并提示可同版本重发或升级到更高的 `MAJOR.MINOR.PATCH` 版本。

- **发布版本**：同时用于主部署包、Codex Runtime ZIP、微信任务编排 ZIP 和本地 tag `chub-v<版本>`。同版本重发直接使用当前 HEAD；高版本发布由受控流程统一更新固定版本声明，并创建 `chore(release): v<版本>` 本地提交。Codex 正式槽位标识与 Runtime 描述由后端固定管理，不在页面单独配置。
- **发版说明**：写入本次 ZIP 清单和该版本唯一发版记录的本地发布元数据；不属于 Git 提交门禁。页面默认和刷新后均为空；手工填写任意非空说明，或 AI 生成成功自动填入后，都会显示“发布版本”。生成时记录的版本、提交和工作区快照只用于组织说明内容；生成成功后不因它们变化撤销草稿或阻止发布。设置保存接口不接受说明字段；生成结果不作为发布配置保存，刷新或 Web 重启后必须重新生成。生成过程创建或复用“版本发布说明”内部 Session，默认在 Runtime Sessions 主列表隐藏，可在会话设置单独显示。不得填写凭据、账号、Token、内网地址或其他秘密。

生成只要求当前目录可读取为 Git 工作区，并不要求工作区干净、版本声明一致或 Git 提交者身份可用；这些仍是正式发布门禁。开始时记录目标版本、目标 HEAD、工作区变更指纹与最近成功发版记录的 tag/commit，供生成说明时参考。生成结果固定为首行直接描述本次发布和 3-6 条能力摘要，不加“概述”前缀：首次发布按实际能力域概括，后续发布只写本次变化。任务终态由 Quick Worker 回调回传当前 Web 实例和操作日志；生成成功后保留本页草稿，不因版本、提交或工作区变化标记过期。生成 Session 采用通用设置，属于维护者授信的本机任务；提示词要求其不修改项目，但不将其表达为独立的只读执行边界。Quick Worker 或 Runtime 不可用时，只有 AI 生成功能不可用，手工填写说明仍可显示发布入口。实际点击“发布版本”仍执行完整发布前检查，且说明为空时明确拒绝。

版本设置读取失败时不允许发布。登记发布前，Quick Worker 必须处于 `ready` 且执行中、排队任务均为零；Worker 忙碌或状态无法确认时明确拒绝，不登记发布操作、不生成 ZIP、不变更 tag，待其空闲后重试。随后 Chub 检查本地 Git 工作区干净、本地 Git 提交者身份可用，并按数字版本比较目标、当前源码与最近成功发布记录。通过这些门禁后，先持久记录本次 `requested` 发布及目标版本，再允许更新版本声明；高版本发布仅提交固定版本声明，同版本重发不会创建空提交。版本提交完成立即把该状态写入同一发布记录，提交后及构建前后均确认 HEAD 与工作区未变化。这样服务在版本提交后中断时，下一实例会明确显示“版本已提交、正式发布未完成”，可用同一版本重试。发布不执行 Git `pull` 或 `push`，不修改默认 Runtime、已导入模块、已绑定 Session 或已受理任务。维护者自行决定何时推送或按既有流程升级运行环境。页面不得接受任意输出路径、模块路径、命令或构建参数。

卡片提供“包含插件模块开发源码”开关，默认关闭。关闭时，主包不包含 `modules/` 下的开发源码，只提供两个正式插件 ZIP；目标设备可先部署 Chub 核心，再按需导入。开启时，主包额外包含当前受控开发源码及其内置模块索引，供维护者在目标设备使用现有开发实现和刷新流程；它不自动导入或启用正式插件 ZIP，也不复制来源设备的模块安装状态。无论开关如何，主包固定包含本机模块索引模板，供首次安装创建平级 `chub-local-modules/`。

点击“发布版本”后，页面先按当前源码版本明确显示实际结果：同版本重发不会创建提交，高版本会更新固定声明并创建本地提交；来源声明不一致或目标非法时明确提示仍由服务端最终拒绝。确认后 Web 登记后台固定发布流程。页面与 `scripts/build/build-chub-release-zip.py` 都使用同一发布路径：先检查 Quick Worker 和干净 Git 基线，持久记录目标版本；若为高版本则仅更新固定版本声明并创建本地版本提交，并立即记录“版本声明已提交”；随后在受限临时目录完成主包、两个扩展包和清单校验；校验通过后写入 `data/local/artifacts/releases/`，创建或更新本地带注释 tag `chub-v<版本>`，再覆盖该版本唯一发版记录。相同版本可重复发布：新成功构建替换旧 ZIP、旧记录和 tag 指向，tag 移到新的 HEAD，记录写入最新发版说明。页面轮询操作终态，确认成功后展示产物名称、大小、提交、tag、发版记录名称和说明，并提醒正式包不会自动更新当前运行的 Web 或 Quick Worker；如需当前节点加载本次源码，维护者待 Worker 空闲后先 reload Worker、再重启 Web。完整文件摘要保存在包内发布清单。版本提交后若构建、tag、记录或成功状态写入失败，Chub 回滚 tag、记录和本次产物，但保留版本提交，并明确提示维护者修复后以同一版本重试；不自动改写 Git 历史，不重启 Web/Worker，也不影响已受理任务。

同一时刻只允许一个版本发布操作。已有发布处于 `requested` 或 `started` 时，新的发布请求明确返回当前状态；它不创建第二个并行操作，也不阻止无关的只读、任务执行或第三方服务能力。发布运行依附当前 Web 实例；若服务重启或进程结束导致其无法继续，下一实例必须将该操作记录为失败并允许重新发布，不能长期显示为“发布中”。

## 目标设备部署

### Chub 核心部署

目标设备解压正式包后，按 `DEPLOY_WITH_AI.md` 执行固定流程：

1. 检查支持的平台、发行版默认 Python 版本和基础命令；当前支持 macOS LaunchAgent 与 Ubuntu systemd user service。Windows WSL 只允许以 Ubuntu WSL2、systemd 已启用且 `systemctl --user` 可用的路径部署，不把 WSL1、非 Ubuntu 发行版或未启用 systemd 的环境视为可部署平台。
2. 创建新的 Python 环境并通过受控超时的正常网络安装声明的依赖；只有维护者已提供可信镜像时才使用镜像重试。
3. 直接使用随包的 `config/settings.yaml` 启动核心服务；仅在需要设备标识或可信网络等差异时创建 `config/settings.local.yaml` 覆盖。Runtime、插件包和第三方服务配置留待工作站启动后由维护者按环境处理。
4. 安装 Chub Web、Quick Worker 及固定服务定义；首次安装同时创建平级 `chub-local-modules/` 与空模块索引，若该目录已存在则绝不修改。随后确认 Web 和 Worker 的健康状态，并在部署目录平级目录写入脱敏的部署报告与长期部署问题记录。两者不得包含配置、日志、账号或秘密；它们不授权将项目、虚拟环境或运行态写入 Windows 挂载目录。

Web 健康、Quick Worker 健康和服务安装后的可恢复状态都已确认，才表示 Chub 核心部署成功。仅解压、依赖安装完成、服务进程创建或 HTTP 200 均不单独表示部署成功。

### 工作站启动后的手动扩展配置

工作站核心启动后，维护者可按实际环境在设置页“插件管理”中发现解压目录 `bundled-modules/` 的正式 ZIP，并决定是否导入、启用和选择版本；如需从其他位置恢复制品，也可分别放入 `data/local/artifacts/plugins/runtime/` 或 `data/local/artifacts/plugins/weixin-orchestration/`。这些操作不是部署步骤，不写入部署报告，也不改变已完成的 Chub 核心部署结果。部署包未包含开发源码时，目标设备不提供 `codex-runtime-dev` 或微信开发实现；这不是核心部署故障。

### 工作站启动后的第三方能力配置

OpenClaw、微信、Tailnet、Codex 认证和其他第三方能力由维护者在工作站启动后根据实际环境和对应专项文档手动配置。它们不属于 `DEPLOY_WITH_AI.md` 的部署职责，不应由部署 Agent 猜测版本、安装位置、账号、Owner 或凭据，也不改变 Chub 核心部署的最终状态。

## 页面与操作边界

“维护与版本”页面新增正式部署包生成入口时，只允许可信来源调用固定构建动作。页面的“发版产物”区域显示最近一次成功构建的版本、构建标识、时间、大小、内含扩展、摘要和发版说明，并可通过固定“打开”动作请求本机文件管理器打开配置的发布目录；页面不提供 Web 下载、文件浏览或任意路径输入。

构建操作记录 `requested`、`started`、`succeeded` 或 `failed`。生成请求被受理不代表产物可用；只有 ZIP、内含扩展和发布清单完成校验，且本地 tag 与发版记录均写入后才显示成功产物信息。构建失败保留上一轮成功包，不阻止无关的状态查看、Quick Worker、OpenClaw 或已受理任务。

## 与升级和恢复的关系

正式部署包用于新设备或全新目录的安装，不替代现有设备上的“升级与恢复”。升级与恢复仍只处理 Chub 自有 AI 运行态、Web 与 Quick Worker，且不复制、覆盖或迁移用户配置、OpenClaw、浏览器、原生 Runtime 数据、第三方账号或平级 `chub-local-modules/`。手工删除包含两者的共同父目录不属于 Chub 可保证的保留范围。

目标设备从部署包首次安装后，后续维护继续使用既有 `chub` 服务管理、Web 重启、Worker 恢复、Runtime 插件维护和 OpenClaw 重启与恢复流程。不得用重新解压部署包替代已部署节点的受控升级恢复。

## 验收范围与复检

实现后至少验证：

- 构建包包含主程序、发布清单和两个可独立校验的正式插件 ZIP；
- 工作区不干净、Worker 忙碌、版本格式无效或目标版本低于当前源码/最近成功发布版本时，发布明确拒绝且不生成产物、不变更 tag；
- 高版本发布会只更新六个固定版本/兼容版本声明并创建本地版本提交；同版本重发不创建空提交。两种情形成功后主包、两个插件 ZIP、包内清单、当前 HEAD、本地 `chub-v<版本>` tag 与唯一发版记录一致；同版本重发会替换旧 ZIP、旧记录和 tag 指向；
- 说明为空时可创建或复用隐藏的版本发布说明 Session，并以最近成功发版记录的最新 tag/commit 与当前 HEAD 生成可编辑摘要；页面在高版本提交前明确显示其影响，不自动 push、部署或重启服务；
- 开发源码开关分别覆盖“未包含开发源码但可部署并导入正式 ZIP”和“包含开发源码且可使用现有开发流程”；
- 本机配置、凭据、运行态、日志、缓存和依赖目录不在包内；`settings.local.yaml` 含 `app.version` 时完整忽略，运行版本只能来自已发布的默认配置；
- 在新目录完成 Chub 核心安装后，Web、Worker 和适用的平台服务恢复均可确认，且部署目录平级目录生成不含秘密的部署报告与部署问题记录；
- Runtime 与微信编排 ZIP 作为可供工作站启动后手动导入的制品交付，未导入不影响核心部署；
- OpenClaw 及其他第三方能力未配置、配置失败或未验收均不影响已完成的 Chub 核心部署；
- 构建失败、摘要不一致和单个扩展构建失败均不会产生半成品成功结果或泄露路径/敏感信息；发布在版本提交前已登记，若版本提交已完成，tag、记录和本次产物回滚而版本提交保留，操作记录明确该状态且可用同一版本重试。

当前已实现发布配置页面、后台单任务构建、固定本地输出目录、随包两个正式插件 ZIP 和包内 AI 部署说明。已完成一次 Windows WSL2 Ubuntu 26.04 的真实核心部署流程验证，覆盖发行版默认 Python、systemd/linger 与 WSL 内 Chub 健康确认；Windows localhost 访问与 `wsl.exe --shutdown` 后恢复不再属于部署验收，因为该 shutdown 后的 `wslrelay` 转发在该环境中不稳定。该结论不扩展为原生 Windows、WSL1、非 Ubuntu WSL、macOS 或原生 Ubuntu 的实机验收结论，也不宣称 OpenClaw 安装或真实微信链路已随此能力验收。本次新增的 WSL2 部署成功口径、外置 loopback-forwarder 操作说明和已废弃 systemd unit 清理仅完成本地测试与部署包校验，必须在下一次 WSL2 真实部署时复验。以下变化必须重新验收：发布物包含/排除边界、版本配置语义、模块 ZIP 协议或版本绑定、目标设备服务安装、WSL systemd 或网络边界、外置 forwarder 的访问边界、部署报告交付边界、OpenClaw 兼容基线、页面构建授权、部署成功口径，或任何凭据/运行态迁移规则。
