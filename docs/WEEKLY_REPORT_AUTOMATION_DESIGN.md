# 本期工作周报自动化与生成设计

> 状态：已验收。
> 主要读者：AI Agent、实现和排障 Agent；维护人员用于确认输入门禁、生成流程和验收范围。
> 本文负责：Chub 如何下载本期飞书周报资料、发布唯一有效输入，并通过 `generate-weekly-report` 完成重点确认、正式稿生成和复核。
> 本文不负责：维护者的业务事实判断、飞书页面内容本身、定时调度、缺失资料自动放行，以及下载与生成的一键串联。
> 维护说明：当前采用人工触发、分阶段执行和重点确认门禁；受管 Chrome 的跨平台实机范围以 `.agents/skills/chrome-cdp/SKILL.md` 的当前状态为准。

## 1. 当前定位

本期工作周报是一条由 Chub 自动化和 `generate-weekly-report` 技能共同完成的端到端流程：第一阶段从飞书准备并发布完整输入，第二阶段整理本期重点、等待维护者确认，再生成和复核正式周报。

```text
受管 Debug Chrome 下载主周报和关联文档
  -> 校验租户、路径、数量、结构和关联文档周期
  -> 原子发布本期 inputs
  -> 按已知文档身份创建 mapping / manifest
  -> 生成本期重点确认清单
  -> 维护者确认或调整
  -> 生成正式周报
  -> 格式校验 + 事实与文案 Review
```

两个阶段属于同一产品链路，但保持独立状态和验收边界：只有完整输入发布后才能开始生成。成功发布新输入会更新本期 `.inputs-updated` 标记，页面会隐藏早于该标记的旧产物，阶段 B 还会重新校验 Manifest 和确认记录；等待或失败的下载不会发布新输入，也不会改变上一份输入的标记。当前不提供定时下载、缺失资料自动放行、无确认生成或全自动一键串联。

## 2. 页面与操作方式

首页的“自动化任务”卡片按职责分为“V 国内业务本期周报”“其他配置任务”和“自动化环境”：

- “V 国内业务本期周报”内的“资料下载”展示 `V 国内业务周报下载` 的本期材料、最近结果和手动运行入口；“周报文档”独立展示重点确认清单和正式稿；两个子区各自标明所属周期，跨周仍在执行的下载不会与新周期文档混淆；
- 资料下载成功只表示本期输入已通过发布门禁，不表示重点确认清单或正式稿已生成；生成仍由维护者在材料齐备后手动发起；
- “其他配置任务”展示其余启用任务；
- “工作站环境”管理 Chub Debug Chrome、浏览器用户和受管浏览器实例；“自动化环境”只展示飞书登录检查和任务执行所需状态；
- “全部任务”页面展示完整任务列表和执行结果；
- 项目文档卡片只展示设计方案和调研资料，不再承载本期周报。

维护者可从首页、全部任务页或命令行手动触发下载。浏览器未启动时，页面使用当前已初始化且被选中的受管 Profile 启动，默认采用无界面模式；自动化任务运行过程中不会隐式初始化或切换 Profile。未初始化 Profile 的复制、活动 Profile 选择以及有界面/无界面模式选择，必须在工作站环境中显式操作，并等待最终状态；自动化环境只检查飞书登录状态并执行任务。周报生成继续由维护者在材料齐备后手动发起。

## 3. 周期和工作区

正式周报周期固定为周一至周日。每周三开始新一期处理窗口，从周三至下周二的下载和汇总始终归属同一周期，下周二为报送日。

```text
data/local/artifacts/weekly-reports/<周期>/
  inputs/
    <主周报>.md
    linked/
      <关联文档>.md
      .sources.json
  mapping.json
  manifest.json
  output/
    本期工作重点确认清单-<周期>.md
    weekly-report-confirmation.json
    本期业务周报-<周期>.md
    周报生成核对记录-<周期>.md
```

新周期开始时页面切换为待下载或待生成，但不删除上期工作区、材料和操作记录。下载阶段只发布唯一有效的 `inputs/`；生成阶段只读输入文件，所有新内容写入本期工作区。

`mapping.json` 是维护者或 Agent 提供的适配输入，适配器只读取它并生成 `manifest.json`，不会自动把 mapping 复制到工作区。若需要完整留痕，应将本次实际使用的 mapping 另行保存在本期工作区；它不是自动化下载产物。

## 4. 阶段一：资料准备与发布

### 4.1 受管浏览器

自动化只连接由 `chrome-cdp` 管理的独立 Debug Chrome，不接管用户日常 Chrome。浏览器 Profile 由默认 Chrome 的普通持久化 Profile 一次性受控复制；复制前必须确认默认 Chrome 已退出，复制后的网站登录状态与默认 Chrome 不自动双向同步。

Profile 初始化、选择、启动和停止都等待最终状态并写入操作日志。任务运行只使用当前已选的已初始化 Profile；任务执行和登录检查使用跨进程锁避免冲突；任务只关闭自己创建的页面和弹窗，不关闭共享 Debug Chrome 或用户已有页面。

自动化环境可通过工作站环境提供的受管浏览器检查固定租户云文档的登录状态。需要登录时只展示飞书登录二维码 Canvas；二维码作为短期凭证保存在私有临时目录，接口返回 `no-store`，登录完成或环境变化后立即清理。二维码、Cookie、Token、手机号和完整登录页不进入日志或长期状态。

### 4.2 配置和 Runner

任务清单来自跨节点公共配置 `config/automations.yaml` 和不提交的本机配置 `config/automations.local.yaml`，示例维护在 `config/automations.example.yaml`。任务只声明受控身份和文档入口；选择器、步骤、超时、输出及扩展规则由仓库内版本化模板维护。

所有入口使用同一 Automation Runner：

```text
校验任务配置
  -> 获取共享浏览器锁
  -> 创建任务页面并检查登录和导航域名
  -> 执行白名单页面步骤并捕获下载
  -> 校验主文档结构、关联链接、数量、路径和关联文档周期
  -> 原子发布输入或安全落盘
  -> 写入最终状态并清理本次资源
```

Web 提交只表示任务已受理；成功必须以文件或完整输入集最终发布为准。步骤模型不接受任意 JavaScript、Shell、Python、本机路径或未知动作。主页面和弹窗必须停留在任务生成的域名白名单内；有外部副作用的点击和下载触发不自动重试。

### 4.3 周报输入契约

`V 国内业务周报` 下载主周报，并从“各端周报”章节提取数量受限、同租户且路径类型受控的关联文档。当前资料范围为：

- 上周周报 `previous-report`，只用于结构、背景和延续事项参考；
- 产品商业化、产品/OS、运营、客户端、服务端五类本期事实来源；
- 可选的周会记录、人工确认和补充材料。

五类本期资料都允许每周更换飞书文档地址。下载阶段不负责确认产品、运营、客户端或服务端等业务角色，只按受信主周报提取同租户链接，校验当前资料数量、上周参考数量和允许的路径类型；只有扩展模板显式配置 `required_current_document_roles` 时，下载器才额外按标题前缀和固定路径检查角色。业务角色必须在后续 mapping 中按已知文档身份显式映射，不能按链接顺序猜测。链接必须属于同一飞书租户并使用 `/wiki/` 或 `/docx/` 文档类型。

当前本期下载要求五份非背景关联文档和一份按周期周标题识别的上周参考。每份非背景资料下载后必须从正文开头的标题或周期声明中检测到结束日期落在本期，否则保持等待且不发布整套输入；上周参考不执行本期日期校验。主文档运行时只校验“各端周报”章节存在，不由自动化 Runner 强制校验主文档自身的报告周期，主文档的事实使用范围由 mapping 和 Manifest 约束。

主文档、五份本期来源和上周参考先进入运行暂存区。只有全部下载并通过结构、数量和周期校验，才整体发布到本期 `inputs/`。资料未更新或数量不足时显示“等待各端更新”；下载、读取或结构异常时显示失败。两种情况都丢弃本次暂存结果并保留上一份有效输入；由于本次没有新发布，上一份 `.inputs-updated` 标记和由它决定的页面产物可见性保持不变，避免生成阶段读取半套材料。

本期资料的使用范围结束日期必须落在正式周期内，开始日期可以早于周一；上周参考不参与本期日期校验。图片或 Canvas 中无法可靠读取的内容不能作为确定事实。

## 5. 阶段二：重点确认与正式生成

`generate-weekly-report` 技能位于 `.agents/skills/generate-weekly-report/`。它不打开飞书、不下载文档，也不修改自动化任务状态。

### 5.1 输入适配

`mapping.json` 声明来源角色、使用范围和报告校验规则，适配器据此生成 `manifest.json`。Manifest 为每份材料记录受控相对路径、业务角色、mapping 中提供的来源标题和链接、下载/内容状态、实际使用周期、文件大小、文件修改时间、文件哈希及已解析的标题边界；Manifest 顶层记录生成时间和 fingerprint。自动化 `run_id`、进程和最终状态保存在 Chub 自动化状态中，不写入 Manifest；Manifest 也不生成每份材料独立的下载时间字段。

技能不能根据文件顺序或自然语言文件名猜测角色。阶段 A 必须先读取本期 `inputs/` 中的主周报；`required_roles` 只校验 mapping 实际声明的角色，通用校验器不会自动新增或强制 `main-report` 角色。若主周报需要纳入哈希确认，mapping 必须显式列出它。只有 `ready` 或经维护者明确记录为 `manually-approved` 的材料才能进入正式汇总；绝对路径、目录穿越、远程输入路径、非 Markdown 文件和不唯一的标题范围均明确拒绝。

### 5.2 重点确认门禁

阶段 A 先生成本期重点确认清单，记录每项 OKR 和其他重点工作的去向、来源覆盖、冲突、缺失项，以及建议纳入、合并、弱化、排除或待确认的内容。

维护者确认同时写入清单和 `weekly-report-confirmation.json`，绑定确认时间、最终取舍、带缺口批准范围、Manifest fingerprint、清单路径和清单哈希。阶段 B 重新校验输入哈希、Manifest fingerprint 和清单哈希；新输入发布后的页面失效由 `.inputs-updated` 标记控制。`approved_gaps` 当前只记录维护者批准的缺口范围，不绕过缺失文件、下载失败或阻塞性 `content_status` 的输入校验；现有文件只有在 `ready` 或 `manually-approved` 时才能通过输入门禁。输入、使用范围或清单发生变化时，必须重新生成或更新 Manifest/确认记录后再继续。

### 5.3 正式周报和复核

阶段 B 以已确认重点为主线，再回到原始材料核对数字、日期、版本、状态和责任边界。上周事项必须明确为继续、更新、关闭或不纳入；不同来源统计窗口不改写成完整周报周期，也不直接作不等口径比较。

正式稿默认直接进入业务关键指标或第一项 OKR，不展示输入资料清单和内部编制说明。Manifest 中提供的本期来源链接统一放在文末的“各端周报”章节；若 mapping 没有提供 `source_url`，校验器不会凭空生成链接。业务摘要只在维护者明确要求时生成。

技能内的 `.agents/skills/generate-weekly-report/scripts/validate_weekly_report.py` 执行 Manifest、周期、角色、路径、使用范围、哈希绑定、业务章节、Markdown 表格、来源链接和占位标记等确定性检查。正式稿还必须完成完整性、事实准确性和文案一致性 Review，结果写入本期核对记录。校验失败时可保留草稿，但不能标记完成。

## 6. 状态失效和失败处理

- 同一时间只允许一个浏览器任务或登录检查操作；状态文件用于展示和恢复，不替代互斥锁。
- 输入目录只有在完整校验通过后才通过暂存目录和重命名更新；失败不会覆盖上一份有效材料。发布过程由异常回滚保护，但进程若恰好在 marker 与 inputs 两次重命名之间退出，当前实现不会自动对账，恢复时必须检查 `.inputs-updated` 与 `inputs/` 是否一致。
- 新输入发布后，页面依据 `.inputs-updated` 隐藏较旧的重点清单和正式稿；阶段 B 依据 Manifest、确认 JSON 和清单哈希拒绝过期输入。等待或失败下载不发布新输入，也不自动隐藏上一份产物。
- 输入缺失、仍在编辑或范围不明确时默认停止。维护者可以在确认记录中记录 `approved_gaps`，但当前实现不会用它绕过输入校验；需要继续时必须先把实际可用材料整理为 `ready` 或 `manually-approved` 并重新生成 Manifest。
- 下载状态、运行标识和失败摘要保存在自动化状态/操作日志中；生成阶段以确认 JSON、正式稿和核对记录作为本地产物。最终成功不以子进程启动、HTTP 受理或模型回复为依据。

## 7. 安全和维护边界

- 原始材料只读；生成内容只写入当前周期受控目录。
- 配置、Manifest、日志和展示文档不得包含 Token、Cookie、账号、二维码或终端票据。
- `source_url` 来自 mapping，当前适配器不替它清洗凭证；只能填入不含用户信息、Token 或 Secret 查询参数的 HTTPS 飞书链接。
- 日志只记录任务、角色、相对路径、状态和错误摘要，不记录文档全文。
- 项目资料页面只展示适合可信网络只读访问的内容，敏感业务材料不得直接纳入公开展示。
- 当前不支持验证码或多因素认证自动处理、任意脚本、多下载并行、跨设备编排、集中式任务队列或系统定时调度。
- Ubuntu 的 Chub Debug Chrome 由独立的 `chub-debug-chrome.service` 和固定本机 Unix socket Supervisor 持有；Chub 重启不停止该服务，Supervisor 不可用时自动化启动、停止和状态查询失败关闭。macOS 继续沿用现有 LaunchAgent/浏览器适配路径。
- Ubuntu 的系统升级服务切换会停止并重建 `chub-debug-chrome.service`，确认 Supervisor 服务为 `active` 后再恢复 Worker 和 Web；这只代表浏览器控制服务已就绪，不代表 Debug Chrome 实例已启动。浏览器实例属于工作站环境按需资源，系统升级结果记录为 `skipped`，明确不会自动启动；Supervisor 失败记录为独立降级，不阻断核心服务恢复。Quick Worker 专用恢复只补齐并启动 Supervisor，不执行完整 `chub install`。系统升级流程还会处理当前 Python 依赖、固定服务定义以及 OpenClaw 插件/适配器/补丁同步。
- macOS 已完成受管 Chrome 无界面生命周期和 Playwright 会话的实机验证；Ubuntu 已完成 Profile 与有界面生命周期实机验证，无界面生命周期和 Playwright 会话仍只有自动化覆盖，相关真实环境使用前需补验。Windows 不属于 Chub 当前支持平台，其验证状态仅由 `chrome-cdp` 技能维护。

飞书页面结构、来源角色、周期、报告结构或稳定业务口径变化时，应同步维护自动化模板、技能 reference、样例和测试。仅本周事实变化时不修改通用规则。现阶段继续保留人工触发和重点确认，是保障输入完整性与最终事实准确性的产品边界。

## 8. 验收范围与复检

- 已验收范围：受控 Chrome 资料下载、输入原子发布、Manifest/确认记录门禁、重点确认、正式稿生成和复核；macOS 已完成受管 Chrome 无界面生命周期与 Playwright 会话实机验证，Ubuntu 已完成 Profile 与有界面生命周期实机验证。
- 未验证或不承诺：本次新增 Ubuntu Debug Chrome Supervisor 的服务安装、跨 Web 重启保持、无界面生命周期和 Playwright 会话的真实环境验证，Windows，以及定时下载、缺失资料自动放行和无确认生成；自动化覆盖不能替代未完成的实机验收。
- 复检触发：飞书页面结构、来源角色、周期/报告结构、Manifest 或确认哈希契约、输入发布/失效规则、受管 Chrome 生命周期或生成校验规则变化时，必须重新运行相关技能校验并完成受影响平台的实际流程确认。
