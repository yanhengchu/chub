# 本期工作周报自动化与生成设计

> 状态：已验收
> 主要读者：AI Agent、实现和排障 Agent；维护人员用于确认输入门禁、生成流程和验收范围。
> 本文负责：Chub 如何下载本期飞书周报资料、发布唯一有效输入，并通过 `generate-weekly-report` 完成重点确认、正式稿生成和复核。
> 本文不负责：维护者的业务事实判断、飞书页面内容本身、定时调度、缺失资料自动放行，以及下载与生成的一键串联。
> 维护说明：当前采用人工触发、分阶段执行和重点确认门禁；受管 Chrome 的跨平台实机范围以 `.agents/skills/chrome-cdp/SKILL.md` 的当前状态为准。

## 1. 当前定位

本期工作周报是一条由 Chub 自动化和 `generate-weekly-report` 技能共同完成的端到端流程：第一阶段从飞书准备并发布完整输入，第二阶段整理本期重点、等待维护者确认，再生成和复核正式周报。

```text
受管 Debug Chrome 下载主周报和关联文档
  -> 校验租户、路径、数量、结构和关联文档周期
  -> 按已知文档身份生成 mapping / manifest
  -> 原子发布本期 inputs、mapping、manifest 和更新标记
  -> 生成本期重点确认清单
  -> 维护者确认或调整
  -> 生成正式周报
  -> 格式校验 + 事实与文案 Review
```

两个阶段属于同一产品链路，但保持独立状态和验收边界：只有完整输入发布后才能开始生成。成功发布新输入会更新本期 `.inputs-updated` 标记，页面会隐藏早于该标记的旧产物，阶段 B 还会重新校验 Manifest 和确认记录；等待或失败的下载不会发布新输入，也不会改变上一份输入的标记。当前不提供定时下载、缺失资料自动放行、无确认生成或全自动一键串联。

## 2. 页面与操作方式

首页的“自动化任务”区域中，配置驱动的业务自动化均使用内部流程卡片；自动化环境和账户环境继续使用普通状态行。周报流程卡片与其他自动化任务遵循[前端 UI 设计](FRONTEND_UI_DESIGN.md)的统一展示规则：

- `V 国内业务周报下载 · <本期周期>` 是一个流程卡片，固定按“下载本期资料 → 生成工作重点确认清单 → 生成正式周报”展示三个步骤；周期只显示在卡片标题，避免在每步状态中重复；
- 下载步骤展示本期材料、最近结果和固定脚本的手动运行入口。下载成功只表示本期输入已通过发布门禁，不表示后两步已生成；确认清单和正式周报步骤按真实产物与确认记录显示等待、已生成或已确认状态，并在产物存在时提供查看入口；
- 重新生成或编辑重点确认清单后，早于该清单的正式周报保留为“查看旧文档”，但不再作为本期当前正式稿；第三步恢复为确认并生成或重新运行，直到基于当前清单生成新的正式周报；
- “生成工作重点确认清单”和“生成正式周报”始终展示运行按钮：完整输入未发布时第二步置灰并说明需先下载资料；重点确认清单生成且尚未确认时，第三步改为“确认并生成正式周报”，点击后在确认弹窗明确同意按当前清单生成，服务端写入绑定当前清单哈希和 Manifest 指纹的确认记录，并立即在同一周报 Session 提交 Stage B；确认记录写入成功但任务提交失败时，页面保留“运行”入口用于恢复。前置条件满足后按钮可用。本期第二、三步共用一个周报 Quick Session，名称固定为 `V 国内业务周报 · <周期>`：首次运行第二步创建，第二步重试及第三步都在同一会话继续提交；新周期或会话不可恢复时才创建新会话。每次提交仍是独立任务，并以固定提示调用 `generate-weekly-report` 的对应 Stage；Stage A 只生成确认清单并停止等待确认，Stage B 读取已发布输入、确认清单和有效确认记录后生成正式稿及核对记录。生成过程不重新打开飞书、不重新下载，也不改变下载自动化状态。Quick Session 的 `requested` 和 `started` 都属于执行中：任一阶段处于该状态时，右侧显示不可点击的“运行中”，不替换为“查看会话”，其他阶段的运行或重试入口也保持不可用。阶段产物生成后保留“查看文档 + 查看会话 + 重新运行”：查看会话使用标准次级按钮，并在首页原位切换至该 Quick Session，不跳转独立会话子页面；未形成产物的完成或失败任务保留“查看会话 + 重新运行”；
- 周报自动化会话的 Runtime、权限、模型和推理等级在设置页的 AI Runtime 通用配置中统一维护，选择后立即生效，仅影响之后新建的周报生成 Session。已创建的本期周报 Session 继续使用其创建时配置，不因之后修改默认设置而失去第二、三步运行资格。权限、模型和推理等级与快速交互使用同一组选项和模型联动规则；当前只接入 Codex；只读权限不能创建新的周报生成 Session；
- 其他配置任务各自作为流程卡片展示；即使当前只有一个可执行步骤，也保留一个步骤容器，以便后续按相同规范扩展；
- 首页“自动化环境”管理 Chub Debug Chrome、浏览器用户和受管浏览器实例；“账户环境”单独提供飞书账户与 Codex Runtime 账户状态检查；两者均是单一能力或即时状态，不使用流程卡片；
- “全部任务”页面展示完整任务流程和执行结果；
- 项目文档卡片只展示设计方案和调研资料，不再承载本期周报。

维护者可从首页、全部任务页或命令行手动触发下载。浏览器未启动时，页面使用当前已初始化且被选中的受管 Profile 启动，默认采用无界面模式；自动化任务运行过程中不会隐式初始化或切换 Profile。未初始化 Profile 的复制、活动 Profile 选择以及有界面/无界面模式选择，必须在首页核心服务卡中显式操作，并等待最终状态；飞书账户检查依赖运行中的 Debug Chrome，Codex Runtime 账户检查复用 AI 额度最终快照且不依赖浏览器，只有认证类型与额度均可读取时才显示可用。只要 Debug Chrome 处于运行态，下载任务、飞书账户检查和需要浏览器读取的 AI Runtime 检查可并行使用各自页面；页面首次显示或浏览器启动后的刷新，仍会自动检查“未检查”的账户项。下载、浏览器初始化或周报生成处于执行中时，自动化分区以局部请求原位刷新；终态或等待人工操作后停止轮询，页面后台降频，刷新失败保留最近一次成功内容。浏览器启动、停止、重启、Profile 初始化和模式切换仍是独占操作：有自动化任务正在执行时，停止或重启入口保持不可用。任一账户已有检查结果后不自动重试，只能由维护者手动检查。两项检查均不展示账号标识或凭据。周报生成由流程卡片在前置条件满足后显式创建会话，仍保持下载、重点确认、正式稿三个独立操作，不串成一次点击到底。

## 3. 周期和工作区

正式周报周期固定为周一至周日。每周三开始新一期处理窗口，从周三至下周二的下载和汇总始终归属同一周期，下周二为报送日。

```text
data/local/artifacts/weekly-reports/<周期>/
  inputs/
    <主周报>.md
    linked/
      <关联文档>.md
      .sources.json
  mapping.json
  manifest.json
  output/
    本期工作重点确认清单-<周期>.md
    weekly-report-confirmation.json
    本期业务周报-<周期>.md
    周报生成核对记录-<周期>.md
```

新周期开始时页面切换为待下载或待生成，但不删除上期工作区、材料和操作记录。下载阶段只在同一次可回滚发布中更新唯一有效的 `inputs/`、`mapping.json`、`manifest.json` 和 `.inputs-updated`；生成阶段只读输入文件，所有新内容写入本期工作区。

`mapping.json` 是本次下载按已知 V 周报来源身份生成的适配输入，并与 `manifest.json` 一起保留在本期工作区。它固定携带 V 周报的正式稿/清单章节校验契约，以及主周报和每份关联资料的受控 `source_url`；正式稿据此在“各端周报”统一展示来源链接。Runner 不根据关联链接顺序猜测角色：无法映射到上周参考、音乐产品、产品、运营、客户端或服务端等已知来源时，本次输入不发布，保留上一份有效输入。

## 4. 阶段一：资料准备与发布

### 4.1 受管浏览器

自动化只连接由 `chrome-cdp` 管理的独立 Debug Chrome，不接管用户日常 Chrome。浏览器 Profile 由默认 Chrome 的普通持久化 Profile 一次性受控复制；复制前必须确认默认 Chrome 已退出，复制后的网站登录状态与默认 Chrome 不自动双向同步。

Profile 初始化、选择、启动和停止都等待最终状态并写入操作日志。任务运行只使用当前已选的已初始化 Profile；任务执行和登录检查使用跨进程锁避免冲突；任务只关闭自己创建的页面和弹窗，不关闭共享 Debug Chrome 或用户已有页面。

账户环境可通过受管浏览器检查固定租户云文档的飞书登录状态。需要登录时只展示飞书登录二维码 Canvas；二维码作为短期凭证保存在私有临时目录，接口返回 `no-store`，登录完成或环境变化后立即清理。Codex Runtime 检查复用 AI 额度最终快照：只有 ChatGPT 登录或 API Key 认证对应的额度可读时才报告可用；API Key 模式且额度采集页面跳转到登录页时明确报告“已配置，但 AI 额度账户未登录”，其他读取错误才报告暂不可用。不读取、保存或展示账号标识、Cookie、Token、API Key 或完整认证响应。二维码、Cookie、Token、手机号和完整登录页不进入日志或长期状态。

### 4.2 配置和 Runner

任务清单来自跨节点公共配置 `config/automations.yaml` 和不提交的本机配置 `config/automations.local.yaml`，示例维护在 `config/automations.example.yaml`。公共配置可只保留 `version: 2` 和空的 `tasks:`，表示没有跨节点共享任务；本机任务仍照常合并加载。任务只声明受控身份和文档入口；选择器、步骤、超时、输出及扩展规则由仓库内版本化模板维护。

所有入口使用同一 Automation Runner：

```text
校验任务配置
  -> 获取共享浏览器锁
  -> 创建任务页面并检查登录和导航域名
  -> 执行白名单页面步骤并捕获下载
  -> 校验主文档结构、关联链接、数量、路径和关联文档周期
  -> 原子发布输入或安全落盘
  -> 写入最终状态并清理本次资源
```

Web 提交只表示任务已受理；成功必须以文件或完整输入集最终发布为准。步骤模型不接受任意 JavaScript、Shell、Python、本机路径或未知动作。主页面和弹窗必须停留在任务生成的域名白名单内；有外部副作用的点击和下载触发不自动重试。

### 4.3 周报输入契约

`V 国内业务周报` 下载主周报，并从“各端周报”章节提取数量受限、同租户且路径类型受控的关联文档。当前资料范围为：

- 上周周报 `previous-report`，只用于结构、背景和延续事项参考；
- 产品商业化、产品/OS、运营、客户端、服务端五类本期事实来源；
- 可选的周会记录、人工确认和补充材料。

五类本期资料都允许每周更换飞书文档地址。下载阶段不负责确认产品、运营、客户端或服务端等业务角色，只按受信主周报提取同租户链接，校验当前资料数量、上周参考数量和允许的路径类型；只有扩展模板显式配置 `required_current_document_roles` 时，下载器才额外按标题前缀和固定路径检查角色。业务角色必须在后续 mapping 中按已知文档身份显式映射，不能按链接顺序猜测。链接必须属于同一飞书租户并使用 `/wiki/` 或 `/docx/` 文档类型。

当前本期下载要求五份非背景关联文档和一份按周期周标题识别的上周参考。每份非背景资料下载后必须从正文开头的标题或周期声明中检测到结束日期落在本期，否则保持等待且不发布整套输入；上周参考不执行本期日期校验。主文档运行时只校验“各端周报”章节存在，不由自动化 Runner 强制校验主文档自身的报告周期，主文档的事实使用范围由 mapping 和 Manifest 约束。

主文档、五份本期来源和上周参考先进入运行暂存区。只有全部下载并通过结构、数量和周期校验，且已按已知来源身份生成可校验的 `mapping.json` 与 `manifest.json`，才整体发布到本期工作区。资料未更新或数量不足时显示“等待各端更新”；下载、读取、角色映射、Manifest 或发布异常时显示失败。两种情况都丢弃本次暂存结果并保留上一份有效输入；由于本次没有新发布，上一份 `.inputs-updated` 标记和由它决定的页面产物可见性保持不变，避免生成阶段读取半套材料。

本期资料的使用范围结束日期必须落在正式周期内，开始日期可以早于周一；上周参考不参与本期日期校验。图片或 Canvas 中无法可靠读取的内容不能作为确定事实。

## 5. 阶段二：重点确认与正式生成

`generate-weekly-report` 技能位于 `.agents/skills/generate-weekly-report/`。它不打开飞书、不下载文档，也不修改自动化任务状态。

### 5.1 输入适配

`mapping.json` 声明来源角色和使用范围，Runner 在下载暂存区生成与之对应的 `manifest.json` 后再整体发布。Manifest 为每份材料记录受控相对路径、业务角色、mapping 中提供的来源标题、下载/内容状态、实际使用周期、文件大小、文件修改时间、文件哈希及已解析的标题边界；Manifest 顶层记录生成时间和 fingerprint。自动化 `run_id`、进程和最终状态保存在 Chub 自动化状态中，不写入 Manifest；Manifest 也不生成每份材料独立的下载时间字段。

技能不能根据文件顺序或自然语言文件名猜测角色。阶段 A 必须先读取本期 `inputs/` 中的主周报；`required_roles` 只校验 mapping 实际声明的角色，通用校验器不会自动新增或强制 `main-report` 角色。若主周报需要纳入哈希确认，mapping 必须显式列出它。只有 `ready` 或经维护者明确记录为 `manually-approved` 的材料才能进入正式汇总；绝对路径、目录穿越、远程输入路径、非 Markdown 文件和不唯一的标题范围均明确拒绝。

### 5.2 重点确认门禁

阶段 A 先生成本期重点确认清单，业务内容固定为两个简洁列表：`本周需要同步的事项`只记录本期已确认、需要同步的关键事实及已纳入/合并的主文档重点；`需要维护者确认的重点事项`只记录待确认、弱化或排除的主文档重点，以及会影响正式稿取舍的冲突、缺失和解释选择。每项主文档重点必须进入其中一项，不另设 OKR、来源覆盖、上期延续、对照或正式稿叙事章节；这些上下文在对应列表项内简短说明。清单头部保留周期和 Manifest fingerprint，末尾保留确认记录占位，不作为第三个业务内容区块。

维护者确认同时写入清单和 `weekly-report-confirmation.json`，绑定确认时间、最终取舍、带缺口批准范围、Manifest fingerprint、清单路径和清单哈希。阶段 B 重新校验输入哈希、Manifest fingerprint 和清单哈希；新输入发布后的页面失效由 `.inputs-updated` 标记控制。`approved_gaps` 当前只记录维护者批准的缺口范围，不绕过缺失文件、下载失败或阻塞性 `content_status` 的输入校验；现有文件只有在 `ready` 或 `manually-approved` 时才能通过输入门禁。输入、使用范围或清单发生变化时，必须重新生成或更新 Manifest/确认记录后再继续。

### 5.3 正式周报和复核

阶段 B 以已确认重点为主线，再回到原始材料核对数字、日期、版本、状态和责任边界。上周事项必须明确为继续、更新、关闭或不纳入；不同来源统计窗口不改写成完整周报周期，也不直接作不等口径比较。

正式稿默认直接进入业务关键指标或第一项 OKR，不展示输入资料清单和内部编制说明。Manifest 中提供的本期来源链接统一放在文末的“各端周报”章节；若 mapping 没有提供 `source_url`，校验器不会凭空生成链接。业务摘要只在维护者明确要求时生成。

技能内的 `.agents/skills/generate-weekly-report/scripts/validate_weekly_report.py` 执行 Manifest、周期、角色、路径、使用范围、哈希绑定、业务章节、Markdown 表格、来源链接和占位标记等确定性检查。正式稿还必须完成完整性、事实准确性和文案一致性 Review，结果写入本期核对记录。校验失败时可保留草稿，但不能标记完成。

## 6. 状态失效和失败处理

- 同一时间只允许一个浏览器任务或登录检查操作；状态文件用于展示和恢复，不替代互斥锁。
- 输入目录、Mapping、Manifest 和更新标记只有在完整校验通过后才通过暂存文件和重命名整体更新；失败不会覆盖上一份有效材料。发布过程由异常回滚保护，更新标记最后写入，因此它只表示完整输入契约已经可读。
- 新输入发布后，页面依据 `.inputs-updated` 隐藏较旧的重点清单和正式稿；阶段 B 依据 Manifest、确认 JSON 和清单哈希拒绝过期输入。等待或失败下载不发布新输入，也不自动隐藏上一份产物。
- 输入缺失、仍在编辑或范围不明确时默认停止。维护者可以在确认记录中记录 `approved_gaps`，但当前实现不会用它绕过输入校验；需要继续时必须先把实际可用材料整理为 `ready` 或 `manually-approved` 并重新生成 Manifest。
- 下载状态、运行标识和失败摘要保存在自动化状态/操作日志中；生成阶段以确认 JSON、正式稿和核对记录作为本地产物。最终成功不以子进程启动、HTTP 受理或模型回复为依据。

## 7. 安全和维护边界

- 原始材料只读；生成内容只写入当前周期受控目录。
- 配置、Manifest、日志和展示文档不得包含 Token、Cookie、账号、二维码或终端票据。
- `source_url` 来自 mapping，当前适配器不替它清洗凭证；只能填入不含用户信息、Token 或 Secret 查询参数的 HTTPS 飞书链接。
- 日志只记录任务、角色、相对路径、状态和错误摘要，不记录文档全文。
- 项目资料页面只展示适合可信网络只读访问的内容，敏感业务材料不得直接纳入公开展示。
- 当前不支持验证码或多因素认证自动处理、任意脚本、多下载并行、跨设备编排、集中式任务队列或系统定时调度。
- Ubuntu 的 Chub Debug Chrome 由独立的 `chub-debug-chrome.service` 和固定本机 Unix socket Supervisor 持有；Chub 重启不停止该服务，Supervisor 不可用时自动化启动、停止和状态查询失败关闭。macOS 继续沿用现有 LaunchAgent/浏览器适配路径。
- Debug Chrome Supervisor 与浏览器实例均属于自动化环境的独立按需状态：Chub、Quick Worker 和升级与恢复都不会启动、停止或修复 `chub-debug-chrome.service`。Ubuntu 上需要恢复 Supervisor 时，只能使用 `chub chrome-supervisor-reconcile [--restart]`；Supervisor 服务就绪不代表浏览器实例已经启动。Python 依赖修复使用 `chub runtime-dependencies`，同样不属于核心升级步骤。OpenClaw 插件、适配器和补丁继续由第三方服务维护入口处理。
- macOS 已完成受管 Chrome 无界面生命周期和 Playwright 会话的实机验证；Ubuntu 已完成 Profile 与有界面生命周期实机验证，无界面生命周期和 Playwright 会话仍只有自动化覆盖，相关真实环境使用前需补验。Windows 不属于 Chub 当前支持平台，其验证状态仅由 `chrome-cdp` 技能维护。

飞书页面结构、来源角色、周期、报告结构或稳定业务口径变化时，应同步维护自动化模板、技能 reference、样例和测试。仅本周事实变化时不修改通用规则。现阶段继续保留人工触发和重点确认，是保障输入完整性与最终事实准确性的产品边界。

## 8. 验收范围与复检

- 已验收范围：受控 Chrome 资料下载、输入原子发布、Manifest/确认记录门禁、重点确认、正式稿生成和复核；Web 入口按前置条件创建受控 Quick Session 并保留会话查看/重试路径；macOS 已完成受管 Chrome 无界面生命周期与 Playwright 会话实机验证，Ubuntu 已完成 Profile 与有界面生命周期实机验证。
- 未验证或不承诺：本次新增 Ubuntu Debug Chrome Supervisor 的服务安装、跨 Web 重启保持、无界面生命周期和 Playwright 会话的真实环境验证，Windows，以及定时下载、缺失资料自动放行和无确认生成；自动化覆盖不能替代未完成的实机验收。
- 复检触发：飞书页面结构、来源角色、周期/报告结构、Manifest 或确认哈希契约、输入发布/失效规则、受管 Chrome 生命周期或生成校验规则变化时，必须重新运行相关技能校验并完成受影响平台的实际流程确认。
