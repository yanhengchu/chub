# Chub 任务编排收敛实施设计

> 状态：已归档
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，确认本轮收敛的交付边界与验收。
> 本文负责：定义既有通道专属编排的退役边界，以及 Web 与外部通道共同接入统一任务编排分发点的实施顺序、状态清理、兼容取舍和验收门槛。
> 本文不负责：统一分发器或插件模块的长期通用协议、具体通道指令语法、页面交互文案、Worker/Session 状态机，或后续文本优化的产品规则。
> 维护说明：本文是已完成的一次性收敛交付记录，仅用于历史追溯。当前任务编排架构以[任务编排插件模块架构设计](../../CHUB_TASK_ORCHESTRATION_PLUGIN_DESIGN.md)为唯一长期依据；不得把本文的实施顺序或过渡决定写回当前架构契约。

## AI 可执行契约

1. 本次不将既有通道专属编排实现抽取、适配或迁移为通用核心；先退役其专属请求、阶段与交互状态，再以新的通用请求模型接入两个入口。
2. 退役前必须只读检查专属编排请求、等待确认、阶段子任务和待处理回调的结构是否可安全识别；检查通过后无论其是否终态均直接清理。它们是已不兼容的 Chub 自有运行态，不迁移、不双读、不重放，也不保留等待维护者处理的永久门禁。
3. 清理只覆盖专属编排运行态；不得删除已提交的普通 Worker 任务、Chub Session、外部绑定与路由、用户配置、日志、模块源码、通用插件安装记录或第三方原生数据。
4. 统一分发器是外部用户主任务的唯一物理提交 writer。入口适配负责认证、入口幂等、目标选择、交互和交付关联；分发器负责请求幂等、阶段快照、恢复与唯一主任务投递；Worker 只执行物理任务并报告终态。
5. 首次共同接入只使用空阶段链。通道与 Web 的普通任务都必须经过相同的通用请求、恢复和最终投递模型，但各自保持既有用户交互与结果交付方式。
6. 历史专属指令在新阶段模块交付前必须明确拒绝，不能把原先需要编排的正文自动降级为普通任务。后续文本优化必须按新的通用阶段契约重新设计、实现和验收。
7. 入口固定目标不等于绕过 Session 写入门禁。分发器在最终物理投递时仍须调用既有 Worker/Session 提交门禁；目标暂忙或不可写时按该入口既有的拒绝与重试契约收敛，不新增通用排队或隐式重投。

## 当前问题与目标

当前 Web 快速任务直接进入 Quick Worker；外部通道任务则在通道协调实现内持有编排请求、阶段状态和交付关联后才进入 Worker。两条路径共享执行层，却不共享提交前的状态模型，因此无法保证后续阶段模块对入口具有一致的幂等、恢复与失败边界。

本次目标不是把两个入口的交互合并，而是形成“两个入口适配器、一个编排核心、一个 Worker 执行面”：

```text
Web 页面 ────────┐
                 ├─ 入口适配 → 统一任务编排分发器 → Quick Worker → 原入口展示/回送
外部通道入口 ────┘
```

统一核心不保存或解释外部通道路由、确认队列、指令文本或页面 DOM 状态。它只保存对交付关联不透明的引用；由原入口适配器在可信终态时自行展示或回送。

## 实施边界与顺序

以下步骤是代码收敛顺序，不建议把“只退役、不建立空阶段链”作为长期上线状态：那会继续保留两条直接提交路径，且让能力清单、专项设计与实际边界长期失配。最合适的是在同一交付中依次完成退役和两个入口的空阶段链接入；若维护者明确要求分次发布，第一步只能保留普通任务的既有直接提交，并在能力清单中明确“统一编排尚未交付”。

### 1. 退役专属编排

移除外部通道协调中的专属编排分流、阶段运行、确认队列、阶段能力宿主及其恢复/回调路径。普通任务继续经过原有认证、去重、固定指令、目标选择和受控主任务提交，不能因退役而中断。

专属编排运行态作为不兼容的 Chub 自有状态按固定白名单清理，不做双读、双写、状态转换或重放。旧请求 ID、回调和确认续提在清理后明确失败；新分发器不得接管它们。相关插件产物和用户配置不因运行态清理被覆盖，但在新的阶段实现完成前不得被加载、注册为可选阶段或显示为可用能力；不能只在阶段选择处强制空链而保留可操作的旧设置入口。

为避免改变历史指令的执行含义，原本属于专属编排的前缀在重建期间保留为固定拒绝，不进入普通任务正文。该拒绝必须由入口固定路由提供，不能继续依赖已退役模块的命令注册。普通正文不受此限制。

### 2. 建立统一空阶段链

建立持久化的通用编排请求，至少保存入口种类、稳定入口幂等关联、规范化正文、固定目标 Session、阶段链快照、cursor、最终物理任务关联、终态以及不透明交付关联。它不复用旧专属请求、翻译状态或能力宿主的模型和版本。

Web 与外部通道同时改为调用该分发器，并默认匹配空阶段链。空阶段链仍须生成或恢复编排请求，并只能在通过既有 Worker/Session 写入门禁后投递一次物理任务。Web 在首次点击前生成稳定请求 ID，并在重试与页面恢复时复用；服务端以受信入口种类、当前已授权 Session 和该 ID 的组合建立幂等关联，校验其格式与长度，不能把客户端给出的 ID 当作跨 Session 或跨入口的全局任务键。外部通道继续使用已验证的发送者/通道范围内消息关联。

同时将 Worker 完成后的交付从任务执行模型中解耦：Worker 只持有执行所需信息并报告可信终态；页面时间线和通道回送由各自入口适配器使用自己的交付关联处理。通道的路由类型不得进入通用分发器或 Worker 任务模型。

### 3. 为后续阶段模块留出边界

在两个入口的空阶段链完成实际回归之前，不重新启用文本优化。之后可按通用架构增加新的阶段模块：它只接收阶段输入和受限能力投影，返回检查点、等待声明或下一任务文本；它不能直接创建主任务、访问入口路由或改变目标 Session。

是否向 Web 提供文本优化、预览或确认是独立产品决定。即使通道阶段模块已重新交付，也不得因模块已导入而自动改变 Web 任务；Web 的匹配条件、交互和验收必须单独定义。

## 状态与失败边界

| 场景 | 必须结果 |
| --- | --- |
| 清理前发现未结束专属编排状态 | 经只读结构检查后直接清理；不猜测完成、不自动迁移、不重放。 |
| 重复 Web 提交或外部消息 | 返回同一通用编排请求与同一物理任务，不产生第二次投递。 |
| 空阶段链 | 经分发器直接投递一次主任务；不得绕过请求持久化。 |
| 固定目标暂忙或不可写 | 由现有 Worker/Session 门禁给出拒绝或可恢复结果；分发器不私建全局队列或自动重投。 |
| 入口交付失败 | 主任务终态与入口交付终态分别记录；不能把回送失败误报为任务失败或重投任务。 |
| 分发器/Worker 重启 | 仅按已保存的通用请求、任务关联和可信终态恢复；结果未知且继续会重复副作用时失败关闭。 |
| 将来的阶段失败或不可用 | 已选中阶段的请求失败关闭；不跳过阶段、不执行原文、不替换实现。未匹配入口继续按自身空阶段链工作。 |

## 验收与文档同步

代码实施至少验证：清理白名单和空状态前置检查；两个入口的空阶段链唯一投递；Web 请求重试；外部通道认证、去重、目标选择和回送未退化；Web 时间线与任务查询未退化；重启恢复不重复投递；Worker 协议升级后不读取旧 `translation` 任务、队列或租约；内部阶段任务不递归；任一入口或阶段的故障不阻塞另一入口。

当前实现已完成专属实现和运行态的退役、两个入口的空阶段链及 Worker v14 隔离。维护者已完成一次真实微信收发与 Web 提交，Chub 后台记录两个主任务均到达成功终态，微信完成通知也已送达；随后 Worker 与 Web 服务重载并确认健康。分发器和固定内部工作流均已补齐“先持久化 `operation_id`、回执丢失或重启后对账、找回则关联、找不到则明确失败”的恢复闭环；分发器状态损坏也只使新的普通任务局部不可用。本轮留存释放、浏览器重试解除和全量自动化复检均已完成，本文恢复为“已验收”。

真实外部通道的收发仍由维护者本人在对应客户端验证；Agent 只检查 Chub、Worker 与通道后台状态及最终记录。
