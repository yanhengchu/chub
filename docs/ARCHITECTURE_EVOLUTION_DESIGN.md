# Chub 前端 UI 模块化设计

> 状态：首轮物理拆分已完成，并已通过 Ubuntu、MacBook 和手机端验收；当前仍保留原有全局调用与加载顺序。

## 1. 背景

Chub 当前采用 FastAPI、Jinja2、原生 JavaScript 和 CSS，保持单进程、同源部署且无需前端构建链。后端已经按 `core`、`services`、`automations`、`codex`、`api` 和 `web` 形成较清晰的模块边界，当前没有调整后端总体架构的必要。

前端的数据请求也已通过 JSON API 与后端业务分开，但首页代码逐渐集中：

- `app/web/static/app.js` 同时负责请求、缓存、轮询、状态判断、DOM 渲染、弹窗、卡片折叠和页面启动；
- `app/web/static/app.css` 同时承载全局规则、主题值、布局、组件和页面专用样式；
- `index.html`、`app.js` 和 `app.css` 之间缺少明确的功能边界；
- 新增或调整一张首页卡片时，容易影响其他卡片和公共交互。

当前需要解决的是前端代码继续增长带来的维护问题，不是重新设计页面，也不是建设独立前端工程。

## 2. 本次目标

本次调整把现有 Web UI 整理为：

> 稳定页面外壳 + 共享基础能力 + 按职责分文件的 Feature + 通用组件 + 页面组合入口。

具体目标：

1. 降低首页脚本和样式文件的集中度，让每个功能拥有清晰边界。
2. 保持每张动态卡片独立请求、缓存、刷新、轮询和错误处理。
3. 让公共请求、页面恢复、消息、badge 和折叠卡片等稳定能力只维护一份。
4. 让后续新增卡片、调整布局或增加主题时，不复制已有业务判断。
5. 保持现有轻量技术栈、部署方式和跨平台行为。

### 2.1 当前 UI 风格基线

当前已经实现和验收的界面正式命名为 `Standard`，中文称“简约标准版”。它是 Chub 当前默认的视觉与交互基线，特点是轻量工具型布局、清晰信息层级、克制配色与装饰、自然高度卡片、统一间距，以及服务于状态变化的短动效。“标准版”仅表示默认风格，不区分功能等级。

后续如果增加其他 UI 风格，应以 Standard 为对照，至少比较：

- 信息密度与内容层级；
- 色彩、字体、圆角、阴影和间距；
- 卡片、按钮、弹窗与原生控件的视觉表达；
- 折叠、刷新和状态变化动效；
- 桌面端与手机端布局；
- 键盘操作、减少动态效果和其他无障碍表现。

不同风格共享相同的模板语义、Feature 业务逻辑、API、安全边界和主要交互流程。视觉差异收敛到根节点风格标识、样式 Token 与公共组件，不复制业务逻辑。当前已经实现 Standard 与 Cyber 的固定预览和真实公共页面切换。

设置页提供风格预览与应用两个独立动作：卡片主体进入固定风格预览，“应用”按钮即时切换当前页面。风格选择与 Cyber 代码雨速度、亮度和密度保存在当前浏览器，不跨设备同步；偏好缺失、非法或无法读取时回退 Standard。风格选择同时写入一份不含敏感信息、同站点可读的主题 Cookie，服务端据此在 HTML 首屏直接输出根节点风格和 `color-scheme`；本地存储仍是浏览器端的主题选择来源。预览页不受当前选择影响，始终固定展示目标风格，不读取真实节点或会话数据，也不执行业务操作。

Standard 同时是新增页面和新增功能的默认 UI 规范。新增界面应先复用现有 Token、公共组件和交互模式；只有现有组件无法表达明确业务需求时才新增样式，并同步检查桌面与手机布局、正常/禁用/加载/空数据/失败状态、键盘操作和减少动态效果。预览页用于覆盖有代表性的视觉与交互状态，不作为所有业务页面的一比一副本。

Standard 当前采用以下宽度基线：

- 桌面端首页、设置页、次级列表、文档与周报详情、日志详情和快速交互页面统一使用 1080px 最大内容宽度；
- 手机端取消桌面最大宽度的视觉影响，按可用屏幕宽度自然铺满并保留现有基础边距；
- 快速交互单条消息占消息区域约 90%，用户消息与助手消息分别保留约 10% 的对侧空间，不再设置导致宽屏间距放大的固定消息宽度上限；
- 消息正文、执行来源、时间、通知状态、置顶和输入区由预览与真实页面复用同一组组件样式，避免维护两套视觉规则。

### 2.2 Standard 设计规范

- 定位：默认、长期使用的轻量工具型界面，优先信息清晰、操作效率和跨设备稳定性，不使用“基础版”表达功能等级。
- 色彩：浅灰绿页面底色、近白卡片、深绿主色和低饱和状态色；装饰必须服从信息层级，危险与警告保持独立语义色。
- 字体：中文正文、标题和控件统一使用清晰无衬线字体；数字或路径可以继承现有组件表达，不为了视觉效果大面积改用等宽字体。
- 容器：卡片使用自然高度、适度圆角、轻边框与克制阴影；桌面双列、手机单列，不强制同排等高。
- 间距：标题、简介、内容和操作保持稳定层级；卡片简介建议约 12–18 个字符，以准确和视觉平衡为先。
- 组件：普通文字按钮、按钮型导航和快速交互发送按钮统一使用 14px 字号，并复用现有主次按钮、状态 badge、消息气泡、原生表单控件、模态 dialog 和折叠卡片规则；下级页面依赖浏览器返回，不新增专用返回栏。
- 动效：只用于折叠、状态变化和必要反馈，时间短且不造成内容跳动；系统减少动态效果时直接切换。
- 响应式：桌面内容最大宽度 1080px，手机按可用宽度铺满；快速交互消息最多占消息区约 90%，由对侧留白表达用户和助手方向。

### 2.3 Cyber 设计规范

- 定位：专业服务器监控终端与黑客工作站氛围的科技终端版；保持克制、可长期阅读，不使用频闪、故障撕裂或大面积高强度辉光。
- 色彩：纯深黑底色配冷青绿色主状态，黄、红分别表达等待与失败；卡片使用轻切角或近直角边框及半透明深色遮罩，让同一层代码雨可低强度贯穿页面和卡片。
- 字体：中文正文继续使用无衬线字体；时间戳、状态码、路径、命令参数、节点编码和元信息使用等宽字体。
- 结构：与 Standard 保持相同业务信息结构和组件语义，不复制 Feature 逻辑；标题可使用 `$`、`>`、`#` 与英文节点编码强化终端层级。普通操作按钮和按钮型导航入口使用 `>` 提示符；页面标题、Codex Session 主体、图标按钮、弹窗关闭/取消、置顶与正文链接按自身语义保留，不机械添加提示符。
- 状态：状态 badge 使用绿、黄、红或灰色点状指示灯配合文字，不能只依赖颜色；OpenClaw 网关与消息通道在 Cyber 下使用完整背景标签和发光指示点，Standard 保持轻量指示点与文字；危险操作继续保留明确说明和确认弹窗。
- 会话：用户消息表达为命令输入行，助手消息表达为系统日志输出，取消传统圆角聊天气泡；输入区保留 `>` 提示符和低频光标提示，发送按钮复用全局次级按钮视觉并保持单行。
- 代码雨：仅使用 `0/1` 单字符流，背景层固定且不拦截交互。亮度从雨尾到雨头渐变；卡片通过半透明遮罩透出同一层雨流，不为每张卡片创建独立动画。
- 代码雨参数：设置页分别保存速度、整体亮度上限和横向密度，默认值为 60%、70% 和 50%。亮度下限按上限的 50% 自动计算；默认密度对应桌面 6 列、手机 3 列。
- 随机与续接：每次进入预览随机生成横向位置、初始进度、轻微速度差和字符组合，同一次浏览期间保持稳定。每个逻辑雨列最多两条 16 字符雨串，以约 58%–76% 周期偏移交错循环，下一条可在上一条完全离屏前进入。
- 动效与性能：手机端自动降低最大雨列数；系统减少动态效果时停止雨流和提示符动画，并只保留每列一条静态雨串。代码雨不可影响键盘操作、点击、滚动或正文对比度。

### 2.4 两套风格的共同验收边界

- 预览只展示静态示例和本地交互，不读取真实节点、任务或会话数据，不执行维护操作。
- 两套风格必须覆盖节点状态、自动化、Codex 会话、表单、按钮、状态反馈、空/加载/失败状态、折叠、确认弹窗和快速交互会话。
- 桌面与手机必须保持无横向溢出、控件可操作、文本可读、焦点和键盘语义有效；减少动态效果不得退化。
- Standard 是新增页面与功能的默认实现标准；Cyber 是可选风格。新增或修改公共页面时需要同时检查两套风格，终端 PTY 继续使用独立的原生终端样式，不参与切换。
- 服务端根据非敏感主题 Cookie 在 HTML 首屏直接设置根节点标识和 `color-scheme`，浏览器主题脚本负责与本地偏好同步并初始化代码雨，避免页面先显示 Standard 再切换 Cyber；业务 Feature 不读取或判断主题，严格 CSP 不为主题初始化放宽内联脚本限制。

## 3. 必须保持不变的内容

这次属于保持行为不变的内部结构整理。以下内容不在调整范围内：

- 页面视觉效果、信息层级、文案、布局和响应式断点；
- 首页、次级页面和浏览器返回链路；
- 卡片独立刷新、会话级缓存、轮询频率、错误保留和折叠动画；
- dialog、原生表单控件、键盘操作和无障碍属性；
- Codex PTY、快速交互、自动化、日志和项目资料的业务行为；
- API 路径、认证方式、请求字段、响应结构和错误语义；
- Jinja2 + 原生 JavaScript/CSS 的技术栈；
- 单进程、同源静态资源和无前端构建步骤的部署方式。

静态资源的内部文件路径和模板引用可以调整，但用户访问地址、页面路由和 API 不变。

## 4. 核心调整内容

### 4.1 整理 JavaScript 基础能力

首轮将与具体功能无关的共享能力集中在 `dashboard-core.js`，暂不为了目录形式继续拆小：

- API 请求：Hub Token 注入、统一响应解析和错误处理；
- 页面会话：页面可见性、浏览器返回恢复和受控的 Storage 读写；
- 页面启动与模块注册：只负责初始化功能，不承载具体业务逻辑。

应用外壳单独负责 Token 生命周期、连接与退出、认证失效后的统一清理、服务重启最终状态确认，以及各 Feature 的初始化和定向刷新；这些职责不下沉到 `api-client`，也不归属任一业务 Feature。

共享层不得包含 Codex、自动化、日志或资料的专用状态判断。缓存键、数据结构、有效期和清理策略仍由对应 Feature 或 Component 管理，不建立全局状态仓库。

### 4.2 按功能拆分 Feature

首页主要能力分别形成 Feature 模块：

- 节点状态；
- Codex 会话；
- OpenClaw Gateway；
- 自动化任务；
- 项目资料；
- 日志。

每个 Feature 文件集中承载：

- 调用对应 API；
- 保存本功能最近一次成功内容；
- 处理加载、成功、失败和轮询状态；
- 渲染本功能 DOM；
- 对外暴露初始化、刷新和必要的生命周期方法。

本轮保持现有显式函数调用和加载顺序，不为了形式统一新增生命周期框架。后续确实出现多页面组合或复杂跨 Feature 协调时，再从真实调用中提取 `init`、`refresh`、`suspend`、`reset` 和 `dispose` 等最小接口，不引入全局事件总线。

Feature 文件仍通过现有全局函数和共享 `elements` 工作，并不是可独立加载的模块。一个 Feature 请求失败时不得清空、阻塞或闪烁刷新其他 Feature；跨功能共享资源操作继续由应用外壳显式协调。

### 4.3 提取通用 DOM 组件

首轮只提取已经稳定且能够保持行为不变的交互组件：

- 可折叠卡片；
- 状态 badge；
- 通用消息和错误提示。

组件只管理通用 DOM 行为和无障碍状态，不负责请求业务数据，也不根据中文提示推断业务状态。现有 dialog 的确认内容、关闭条件和后续操作差异明显，继续由所属 Feature 或应用外壳管理，不为了形式统一抽取空泛封装。

### 4.4 拆分 CSS 层次

将单一 CSS 文件逐步整理为：

```text
app/web/static/css/
  tokens.css          # 颜色、字号、间距、圆角、阴影、动画时长
  base.css            # reset、排版、原生控件和全局交互规则
  components.css      # card、button、badge、dialog、message
  responsive.css      # 现有手机端与桌面端媒体查询
```

首轮按原文件连续区间拆分，加载顺序固定为 Token、Base、Component、Responsive，以保证规则顺序和选择器优先级不变。页面模板直接按该顺序引用四个文件，避免 `@import` 加载瀑布；旧的 `app.css` 不再保留。本次不修改 Token 数值、不新增主题，也不为了分类移动可能改变层叠结果的规则。只有后续修改某个真实页面时，才在视觉对照通过的前提下继续细分页面样式。

### 4.5 整理模板职责

Jinja2 继续负责页面骨架和服务端初始信息。存在稳定复用价值时，可以使用 partial 或 macro 整理卡片标题、dialog 外壳等静态结构。

模板不承载动态业务状态，JavaScript 不通过字符串拼接生成不受控 HTML；动态外部内容继续使用 DOM API 和 `textContent`。

## 5. 目标目录结构

首轮采用同源外部脚本和固定 `defer` 顺序完成物理拆分，不改变原有全局调用语义，也不增加 Node.js、打包器或构建产物。只有后续出现需要独立复用和测试的稳定接口时，才逐步迁移为浏览器原生 ES Modules：

```text
app/web/
  templates/
    index.html
    partials/
      app_styles.html         # 统一分层样式及固定加载顺序
  static/
    js/
      core/
        dashboard-core.js
      components/
        collapsible-card.js
        ui.js
      features/
        node-status.js
        codex-sessions.js
        openclaw.js
        automations.js
        project-documents.js
        logs.js
      app.js                    # 首页应用外壳与组合入口
    css/
      tokens.css
      base.css
      components.css
      responsive.css
```

次级页面已有的独立脚本可以继续保留。只有共享边界明确时才迁移公共能力，避免为了目录整齐一次性改写所有页面。

## 6. 模块边界

首轮实际依赖方向为：

```text
固定 defer 顺序
  -> Core 与共享 elements
  -> Shared DOM components
  -> Feature 文件
  -> app.js 应用外壳与启动
```

当前需要遵守：

- 模板中的脚本顺序属于受测试保护的兼容契约，不能随意调整；
- `app.js` 只负责组合、跨功能协调和初始化，不复制 Feature 的状态判断；
- Feature 可以使用 Core 与 Component，Feature 之间不直接读取内部状态；
- Component 不调用业务 API；
- Core 当前仍保存共享 DOM 引用并承担认证失效后的跨功能清理；只有出现真实复用需求时才继续解耦；
- UI 只通过现有 HTTP API 获取动态业务数据；
- 不在前端引入任意 API、文件路径或系统命令拼接能力。

## 7. 实施顺序

采用小步迁移，每一步保持页面可运行、可测试、可回退定位：

1. 保存桌面端、手机端关键页面和交互基线。
2. 按项目资料、日志、节点状态、自动化和 Codex 拆出 Feature 文件，保持函数内容与调用顺序。
3. 抽出通用 UI 与可折叠卡片逻辑，将 `app.js` 收敛为首页应用外壳。
4. JavaScript 稳定后，按原顺序拆分 Token、Base、Component 和 Responsive CSS。
5. 运行全量测试，并在临时服务上完成桌面端和手机端真实浏览器回归。
6. 后续只有在真实功能改动需要时，再继续提取 API Client、生命周期接口或模板 partial。

迁移期间不同时修改产品交互或视觉设计。发现现有缺陷时单独记录，避免结构调整与行为修复混在同一批改动。

## 8. 验证与验收

### 8.1 自动化验证

- 运行完整 pytest；
- 保持现有 API 和 Web 页面测试通过；
- 为模块加载、关键 DOM 结构和静态资源引用补充必要测试；
- 运行 `git diff --check`；
- 确认没有遗留失效的静态资源路径。

### 8.2 浏览器验收

桌面端与手机端至少检查：

- 首页首次加载及各卡片独立刷新；
- 刷新失败时保留最近一次成功内容；
- 页面隐藏、恢复和浏览器返回后的缓存与定向刷新；
- 卡片折叠持久化、动画、键盘操作和减少动态效果；
- 所有 dialog、原生选择器和危险操作确认；
- Codex 状态、入口切换、轮询及快速交互；
- 自动化运行状态和项目资料、日志入口；
- 页面布局、间距、颜色、字体和响应式效果与调整前一致。
