# Chub 前端 UI 模块化设计

> 状态：首轮物理拆分已完成，并已通过 Ubuntu、MacBook 和手机端验收；当前仍保留原有全局调用与加载顺序。

## 1. 背景

Chub 当前采用 FastAPI、Jinja2、原生 JavaScript 和 CSS，保持单进程、同源部署且无需前端构建链。后端已经按 `core`、`services`、`automations`、`codex`、`api` 和 `web` 形成较清晰的模块边界，当前没有调整后端总体架构的必要。

前端的数据请求也已通过 JSON API 与后端业务分开，但首页代码逐渐集中：

- `app/web/static/app.js` 同时负责请求、缓存、轮询、状态判断、DOM 渲染、弹窗、卡片折叠和页面启动；
- `app/web/static/app.css` 同时承载全局规则、主题值、布局、组件和页面专用样式；
- `index.html`、`app.js` 和 `app.css` 之间缺少明确的功能边界；
- 新增或调整一张首页卡片时，容易影响其他卡片和公共交互。

当前需要解决的是前端代码继续增长带来的维护问题，不是重新设计页面，也不是建设独立前端工程。

## 2. 本次目标

本次调整把现有 Web UI 整理为：

> 稳定页面外壳 + 共享基础能力 + 按职责分文件的 Feature + 通用组件 + 页面组合入口。

具体目标：

1. 降低首页脚本和样式文件的集中度，让每个功能拥有清晰边界。
2. 保持每张动态卡片独立请求、缓存、刷新、轮询和错误处理。
3. 让公共请求、页面恢复、消息、badge 和折叠卡片等稳定能力只维护一份。
4. 让后续新增卡片、调整布局或增加主题时，不复制已有业务判断。
5. 保持现有轻量技术栈、部署方式和跨平台行为。

### 2.1 当前 UI 风格基线

当前已经实现和验收的界面正式命名为 `Standard`，中文称“简约标准版”。它是 Chub 当前默认的视觉与交互基线，特点是轻量工具型布局、清晰信息层级、克制配色与装饰、自然高度卡片、统一间距，以及服务于状态变化的短动效。“标准版”仅表示默认风格，不区分功能等级。

后续如果增加其他 UI 风格，应以 Standard 为对照，至少比较：

- 信息密度与内容层级；
- 色彩、字体、圆角、阴影和间距；
- 卡片、按钮、弹窗与原生控件的视觉表达；
- 折叠、刷新和状态变化动效；
- 桌面端与手机端布局；
- 键盘操作、减少动态效果和其他无障碍表现。

不同风格默认共享相同的模板语义、Feature 业务逻辑、API、安全边界和主要交互流程。视觉差异应优先收敛到样式 Token 与公共组件；只有出现明确需求并完成独立设计、实现和多端验收后，才作为正式风格提供。当前模块化工作只为这种演进保留边界，不实现主题切换或第二套样式。

## 3. 必须保持不变的内容

这次属于保持行为不变的内部结构整理。以下内容不在调整范围内：

- 页面视觉效果、信息层级、文案、布局和响应式断点；
- 首页、次级页面和浏览器返回链路；
- 卡片独立刷新、会话级缓存、轮询频率、错误保留和折叠动画；
- dialog、原生表单控件、键盘操作和无障碍属性；
- Codex PTY、快速交互、自动化、日志和项目资料的业务行为；
- API 路径、认证方式、请求字段、响应结构和错误语义；
- Jinja2 + 原生 JavaScript/CSS 的技术栈；
- 单进程、同源静态资源和无前端构建步骤的部署方式。

静态资源的内部文件路径和模板引用可以调整，但用户访问地址、页面路由和 API 不变。

## 4. 核心调整内容

### 4.1 整理 JavaScript 基础能力

首轮将与具体功能无关的共享能力集中在 `dashboard-core.js`，暂不为了目录形式继续拆小：

- API 请求：Hub Token 注入、统一响应解析和错误处理；
- 页面会话：页面可见性、浏览器返回恢复和受控的 Storage 读写；
- 页面启动与模块注册：只负责初始化功能，不承载具体业务逻辑。

应用外壳单独负责 Token 生命周期、连接与退出、认证失效后的统一清理、服务重启最终状态确认，以及各 Feature 的初始化和定向刷新；这些职责不下沉到 `api-client`，也不归属任一业务 Feature。

共享层不得包含 Codex、自动化、日志或资料的专用状态判断。缓存键、数据结构、有效期和清理策略仍由对应 Feature 或 Component 管理，不建立全局状态仓库。

### 4.2 按功能拆分 Feature

首页主要能力分别形成 Feature 模块：

- 节点状态；
- Codex 会话；
- OpenClaw Gateway；
- 自动化任务；
- 项目资料；
- 日志。

每个 Feature 文件集中承载：

- 调用对应 API；
- 保存本功能最近一次成功内容；
- 处理加载、成功、失败和轮询状态；
- 渲染本功能 DOM；
- 对外暴露初始化、刷新和必要的生命周期方法。

本轮保持现有显式函数调用和加载顺序，不为了形式统一新增生命周期框架。后续确实出现多页面组合或复杂跨 Feature 协调时，再从真实调用中提取 `init`、`refresh`、`suspend`、`reset` 和 `dispose` 等最小接口，不引入全局事件总线。

Feature 文件仍通过现有全局函数和共享 `elements` 工作，并不是可独立加载的模块。一个 Feature 请求失败时不得清空、阻塞或闪烁刷新其他 Feature；跨功能共享资源操作继续由应用外壳显式协调。

### 4.3 提取通用 DOM 组件

首轮只提取已经稳定且能够保持行为不变的交互组件：

- 可折叠卡片；
- 状态 badge；
- 通用消息和错误提示。

组件只管理通用 DOM 行为和无障碍状态，不负责请求业务数据，也不根据中文提示推断业务状态。现有 dialog 的确认内容、关闭条件和后续操作差异明显，继续由所属 Feature 或应用外壳管理，不为了形式统一抽取空泛封装。

### 4.4 拆分 CSS 层次

将单一 CSS 文件逐步整理为：

```text
app/web/static/css/
  tokens.css          # 颜色、字号、间距、圆角、阴影、动画时长
  base.css            # reset、排版、原生控件和全局交互规则
  components.css      # card、button、badge、dialog、message
  responsive.css      # 现有手机端与桌面端媒体查询
```

首轮按原文件连续区间拆分，加载顺序固定为 Token、Base、Component、Responsive，以保证规则顺序和选择器优先级不变。页面模板直接按该顺序引用四个文件，避免 `@import` 加载瀑布；旧的 `app.css` 不再保留。本次不修改 Token 数值、不新增主题，也不为了分类移动可能改变层叠结果的规则。只有后续修改某个真实页面时，才在视觉对照通过的前提下继续细分页面样式。

### 4.5 整理模板职责

Jinja2 继续负责页面骨架和服务端初始信息。存在稳定复用价值时，可以使用 partial 或 macro 整理卡片标题、dialog 外壳等静态结构。

模板不承载动态业务状态，JavaScript 不通过字符串拼接生成不受控 HTML；动态外部内容继续使用 DOM API 和 `textContent`。

## 5. 目标目录结构

首轮采用同源外部脚本和固定 `defer` 顺序完成物理拆分，不改变原有全局调用语义，也不增加 Node.js、打包器或构建产物。只有后续出现需要独立复用和测试的稳定接口时，才逐步迁移为浏览器原生 ES Modules：

```text
app/web/
  templates/
    index.html
    partials/
      app_styles.html         # 统一分层样式及固定加载顺序
  static/
    js/
      core/
        dashboard-core.js
      components/
        collapsible-card.js
        ui.js
      features/
        node-status.js
        codex-sessions.js
        openclaw.js
        automations.js
        project-documents.js
        logs.js
      app.js                    # 首页应用外壳与组合入口
    css/
      tokens.css
      base.css
      components.css
      responsive.css
```

次级页面已有的独立脚本可以继续保留。只有共享边界明确时才迁移公共能力，避免为了目录整齐一次性改写所有页面。

## 6. 模块边界

首轮实际依赖方向为：

```text
固定 defer 顺序
  -> Core 与共享 elements
  -> Shared DOM components
  -> Feature 文件
  -> app.js 应用外壳与启动
```

当前需要遵守：

- 模板中的脚本顺序属于受测试保护的兼容契约，不能随意调整；
- `app.js` 只负责组合、跨功能协调和初始化，不复制 Feature 的状态判断；
- Feature 可以使用 Core 与 Component，Feature 之间不直接读取内部状态；
- Component 不调用业务 API；
- Core 当前仍保存共享 DOM 引用并承担认证失效后的跨功能清理；只有出现真实复用需求时才继续解耦；
- UI 只通过现有 HTTP API 获取动态业务数据；
- 不在前端引入任意 API、文件路径或系统命令拼接能力。

## 7. 实施顺序

采用小步迁移，每一步保持页面可运行、可测试、可回退定位：

1. 保存桌面端、手机端关键页面和交互基线。
2. 按项目资料、日志、节点状态、自动化和 Codex 拆出 Feature 文件，保持函数内容与调用顺序。
3. 抽出通用 UI 与可折叠卡片逻辑，将 `app.js` 收敛为首页应用外壳。
4. JavaScript 稳定后，按原顺序拆分 Token、Base、Component 和 Responsive CSS。
5. 运行全量测试，并在临时服务上完成桌面端和手机端真实浏览器回归。
6. 后续只有在真实功能改动需要时，再继续提取 API Client、生命周期接口或模板 partial。

迁移期间不同时修改产品交互或视觉设计。发现现有缺陷时单独记录，避免结构调整与行为修复混在同一批改动。

## 8. 验证与验收

### 8.1 自动化验证

- 运行完整 pytest；
- 保持现有 API 和 Web 页面测试通过；
- 为模块加载、关键 DOM 结构和静态资源引用补充必要测试；
- 运行 `git diff --check`；
- 确认没有遗留失效的静态资源路径。

### 8.2 浏览器验收

桌面端与手机端至少检查：

- 首页首次加载及各卡片独立刷新；
- 刷新失败时保留最近一次成功内容；
- 页面隐藏、恢复和浏览器返回后的缓存与定向刷新；
- 卡片折叠持久化、动画、键盘操作和减少动态效果；
- 所有 dialog、原生选择器和危险操作确认；
- Codex 状态、入口切换、轮询及快速交互；
- 自动化运行状态和项目资料、日志入口；
- 页面布局、间距、颜色、字体和响应式效果与调整前一致。

验收以实际页面行为和视觉对照为准，不能只以脚本成功加载或测试通过判断完成。

## 9. 完成标准

满足以下条件即可认为本轮调整完成：

- `app.js` 不再承载各功能的完整请求、状态和渲染实现；
- 首页主要功能均已拆入对应 Feature 文件，且保持原有卡片自治行为；
- 公共 API 请求、消息、badge 和折叠行为只有一份实现；业务 dialog 继续由所属 Feature 或应用外壳管理；
- CSS 已按 Token、基础、组件和响应式职责分层，并保持原层叠顺序；
- 页面效果、交互行为、路由和 API 契约没有变化；
- 全量测试和桌面端、手机端浏览器验收通过；
- 没有引入构建链、前端框架或额外部署步骤。

## 10. 非当前范围

本轮明确不做：

- 第二个 AI Provider 接入或 `app/ai/` 通用化；
- OpenClaw 集成；
- 新 UI 主题、第二套布局或页面重新设计；
- API 版本化或现有 `/api/codex/*` 路径迁移；
- React、Vue、Node 构建链或独立前端工程；
- 后端目录重构、数据库、任务队列或微服务拆分。

这些方向只有出现明确、已排期的真实需求后再单独设计，不作为本次前端整理的隐含目标。
