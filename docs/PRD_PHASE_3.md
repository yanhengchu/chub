# Chub 第三阶段产品目标

> 状态：第三阶段首版已闭环并进入持续维护。OpenClaw、微信 ClawBot、只读 Chub 状态 Tool 和飞书单向通知已完成 MacBook、Ubuntu 核心链路验收；BRClient 关停后，Chub 基础 LLM 已移除。新增低风险状态变更能力由后续真实需求驱动，不作为首版闭环条件。

## 1. 阶段定位

第三阶段在第二阶段已闭环的单节点能力之上，探索 Chub 与外部 Agent、消息入口和模型服务的连接方式。

Chub 继续负责可信设备能力、安全校验和最终状态确认；OpenClaw 作为上层 Agent 与编排入口。微信设备能力调用固定为“微信 ClawBot → OpenClaw → Chub → OpenClaw → 微信 ClawBot”。微信 Chub 入站任务绑定本次消息的账号与发送者，并只通过该路由调用 `openclaw message send` 回送；Chub 页面发起的快速交互使用全局固定接收人，账号默认选择唯一健康 ClawBot，也允许兼容性配置明确覆盖。两者都不调用 Agent 或触发新的设备能力，且不可互相兜底。飞书群机器人 Webhook 用于向群聊单向推送通知和结果，微信 ClawBot 作为双向通道接收指令并返回状态和结果。OpenClaw Gateway 首轮可部署在 MacBook 或 Ubuntu，按实施时的在线条件选择，不将操作系统作为方案阻塞项。

## 2. 核心方向

### 2.1 OpenClaw 接入

- 明确 OpenClaw 与 Chub 的职责边界和调用方式。
- 优先复用 Chub 已验收的状态查询、Codex、自动化和日志能力。
- 从只读场景开始验证，再根据实际价值评估低风险操作。
- 保持 Chub 对输入校验、权限、安全边界和最终状态的控制。

### 2.2 消息通道接入

- 接入飞书群机器人 Webhook 单向通道，用于向群聊推送状态、通知和最终结果，不承担指令接收或交互控制。
- 普通微信群没有纳入本阶段的 Webhook 方案；微信消息入口仅使用 ClawBot。
- 接入微信 ClawBot 双向通道，用于接收用户指令并持续返回执行状态和结果。
- 首期聚焦通过受限 Tool 完成状态检查和结果返回，不开放任意远程操作；白名单状态变更能力按真实需求另行设计。
- 明确微信用户、群聊、ClawBot 会话、OpenClaw 会话、目标设备与实际操作之间的映射。
- 分别设计两种通道的鉴权、重复消息、超时、失败反馈和人工确认流程。
- 双向通道不默认等同于无限权限；高风险指令必须在执行前获得明确确认。

## 3. 阶段目标

- 完成 OpenClaw、飞书单向通知、微信 ClawBot 双向交互与 Chub 的整体边界设计。
- 分别打通飞书群机器人 Webhook 单向通知链路和 ClawBot 双向交互链路。
- 验证 ClawBot 通过受限 Tool 完成 Chub 状态检查和结果返回，并明确身份、会话、权限、超时与错误语义。
- 在明确安全边界后逐步开放实际操作，不把通道连通直接视为设备控制能力验收通过。
- 保持第二阶段已经验收的 macOS、Ubuntu、手机端和 Standard UI 行为稳定。

## 4. 当前范围

包含：

- OpenClaw 与 Chub 的集成方案和最小验证。
- 飞书群机器人 Webhook 单向通知通道。
- 微信 ClawBot 双向指令与交互通道。
- 请求来源识别、认证、授权、操作确认和审计。
- 超时、重试、重复消息、失败回复和最终状态确认。
- macOS、Ubuntu 及手机/微信入口的真实链路验收。

暂不包含：

- Chub 直接暴露到公网。
- 任意 Shell、任意文件路径或通用远程执行入口。
- 未经确认的高风险状态变更。
- 复杂多用户权限平台和开放式插件市场。
- 在需求未明确前重构第二阶段已稳定的核心能力。

## 5. 工作原则

- 先明确边界，再选择协议和实现。
- 先只读、后低风险操作，高风险能力单独评估。
- 外部入口只表达意图，具体操作仍由 Chub 固定映射和校验。
- 微信入口的 Chub 能力只经 OpenClaw Tool 进入；Chub 返回结构化最终状态给 OpenClaw，再由 OpenClaw 回复微信，不增加 Chub 反向驱动 OpenClaw 的链路。快速交互完成通知仅发送该任务的结果摘要，不复用此通道下发设备指令。
- Tailscale 身份可以作为可信 Tailnet 内的可选认证来源，但认证不等于授权，不能绕过能力白名单和高风险确认。
- “请求已接收”“Agent 已调用”和“操作最终成功”必须保持不同语义。
- 凭证、用户消息和模型上下文按最小必要原则处理，不进入不必要的日志或响应。
- 每一步保持可独立关闭和回退，不影响现有 Chub 节点使用。

## 6. 实施时确定的配置

- 首批 Chub 状态项、任务白名单及风险等级随具体功能落地确定。
- 维护者提供飞书群机器人 Webhook 地址；目标群由地址固定，只发送明确配置的状态、任务最终结果和异常消息；启用签名校验时一并提供签名密钥。
- ClawBot 使用已绑定并通过允许列表的微信账号；高风险能力可进一步限制为指定账号，且仍需逐次确认。
- 多节点发现、统一入口或更复杂的主动通知有明确需求后另行设计。

## 7. 高层验收方向

- 飞书群机器人 Webhook 可以稳定接收单向状态通知和最终结果，并且不能反向下发指令。
- 微信 ClawBot 可以通过 OpenClaw 双向收发消息，并通过受限 Tool 完成 Chub 状态检查和结果返回；后续状态变更能力不得绕过白名单，高风险指令必须经过明确确认。
- 请求来源、会话、操作 ID、处理中状态和最终结果可追踪。
- 重复消息、超时、模型失败、通道不可用、OpenClaw 不可用和 Chub 不可达时均有明确反馈。
- 接入不会影响现有 macOS、Ubuntu、手机 Web、Codex 和自动化能力。

## 8. 后续扩展边界

第三阶段首版的通道、只读状态 Tool 和飞书通知能力已经完成闭环。后续如出现真实需求，可选择参数固定、风险可控且失败可恢复的低风险状态变更能力，单独完成身份、会话、操作 ID、目标节点、最终结果和异常路径设计；不以增加 Tool 数量作为阶段延续目标。

飞书指定人员提醒、连续电脑交互、自动事件通知和多节点统一入口同样按实际需求或外部条件扩展，不影响第三阶段首版状态。
