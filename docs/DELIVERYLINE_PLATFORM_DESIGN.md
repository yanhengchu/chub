# Deliveryline 需求交付管理平台设计

> 状态：持续维护
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义 Deliveryline 的产品定位、主体阶段、作为 Chub 业务模块的接入方向，以及与 Chub 的职责边界。
> 本文不负责：阶段内资料结构、页面交互细节、AI Agent 调度协议、测试实现或发布运维流程；这些内容在进入对应阶段后再单独设计。

## AI 可执行契约

1. Deliveryline 是需求交付管理平台，不是 Chub 核心能力、Chub 的别名或 Chub 的替代品；它将作为 Chub 的首个**固定开发业务模块**接入工作台，而不是另建独立控制台。
2. 从需求提出到需求合格，主体阶段名称固定为：`需求提出 → 需求评审 → 方案设计 → 开发实现 → 自动化测试 → 测试验收`。后续不得因执行方式、人员或 Agent 类型重命名这些阶段。
3. `开发实现`是稳定的交付阶段名称；当前可由 AI Agent 执行，但“调用 AI Agent 开发”只是该阶段的执行方式或记录，不是新的主体阶段。
4. 方案经确认后才能进入开发实现；自动化测试通过只构成测试证据，测试验收按验收标准确认真实交付结果后才能标记需求合格。验收未通过时，根据问题性质回到方案设计或开发实现。
5. Deliveryline 负责需求流程、阶段门槛、资料、决策、测试结果和验收结论；它不管理 AI Agent 在开发实现阶段内的具体推理、代码编辑或运行时状态。
6. Chub 仍是个人 AI 工作站，负责工作台壳、可信入口、统一模块生命周期、通知、本机 AI Agent、Runtime、任务与运行环境的执行和最终运行状态。Deliveryline 负责需求流程、交付资料和阶段结论；在维护者明确触发“开发实现”时，只通过 Chub 已定义的受控 Session/任务用例发起执行，并保存关联和最终结果作为交付证据。
7. Deliveryline 的固定开发源码位于 `business-modules/deliveryline/`。设置页在模块已导入时保留插件管理入口；首页只在模块已启用且当前可用时，在 `Workspace` 与 Runtime Sessions 之间显示 `Business → Deliveryline`，折叠侧栏和窄屏图标导航同步提供入口。业务页面与业务 API 使用同一可用性门槛。启用后，页面顶部以“进行中、待我处理、存在风险、已交付”四项跨阶段概览呈现整体交付状态，下方展示需求队列、已归档需求和选中需求的六阶段工作区；当前“需求提出”的首次入口只负责原始需求入库和初始化展示，不创建 Session、任务或后续阶段业务流程。
8. Deliveryline 的正式需求档案是可共享的业务事实，权威根目录固定为 `data/shared/deliveryline/requirements/`；每条需求使用一个独立 JSON 文件。不得复用或编辑 `data/shared/chub/requests.json`，也不得把共享需求档案写入 Chub Session、任务、通知、配置或其他模块的数据文件。
9. 一条需求档案的固定根字段为：`version`、`id`、`title`、`original_request_content`、`background`、`delivery_goal`、`scope`、`out_of_scope`、`constraints`、`acceptance_criteria`、`risks_and_open_items`、`workflow`、`activity`、`created_at` 和 `updated_at`。首次入库只写入 `original_request_content` 与系统字段，创建后不可编辑；`title` 和其他正式需求字段在初始化档案中允许为空，页面使用“未命名需求 + 编号”作为临时展示。历史档案未保留原始内容时固定为 `null`，不得从当前背景反推补写。`workflow` 负责六阶段中的当前阶段、跨阶段交付状态、下一步和最近阶段结论；`activity` 只追加创建、编辑、推进、退回、归档等业务事实。顶部概览和各类工作队列必须从需求档案实时计算，不单独保存统计结果。
10. `id` 使用不可修改的 `DL-日期-短随机码` 格式，不使用跨设备递增序号；页面可按创建时间或更新时间提供阅读排序。除系统字段外，需求可在草稿阶段不完整，但进入需求评审前必须满足该阶段的完整性规则。
11. 本机锁、草稿恢复、缓存、导入状态和未来执行关联缓存只可位于 `data/local/state/deliveryline/` 或 `data/local/runtime/deliveryline/`，不属于业务事实，也不得进入 Git。停用、升级、重新导入或移除 Deliveryline 不得删除共享需求档案；归档仅改变业务状态。删除共享业务数据必须是独立的危险操作，明确说明影响范围并经过维护者确认。
12. Chub 不自动执行 Git 同步。每次保存必须先校验当前文件，再以有界、原子写入替换单条需求文件；读取和写入必须限制文件大小、字段长度、活动记录数量和权限。出现 Git 未合并冲突、格式非法、文件超限或同步状态无法确认时，必须停止该需求写入并保留原文件，不自动覆盖、合并或丢弃活动记录。

## 产品定位

Deliveryline 面向个人 AI 协作场景，作为 Chub 工作台内的独立业务模块，管理一项需求从提出到验收合格的交付闭环。它关注“需求是否已具备进入下一阶段的条件”和“最终是否已验收合格”，而不是取代开发工具或运行环境。

Chub 与 Deliveryline 的关系为：

```text
Chub 工作台
  ├─ Deliveryline 业务模块：需求流程、阶段门槛、资料、测试和验收结论
  └─ Chub 核心 / AI Runtime：受控执行、Session、Worker 和最终运行状态
```

## 主体阶段

| 阶段 | 阶段目标 |
| --- | --- |
| 需求提出 | 形成可讨论的需求目标、场景、范围、约束和验收预期。 |
| 需求评审 | 确认需求值得实施、边界明确，并可进入方案阶段。 |
| 方案设计 | 形成并确认交付方案与验收标准。 |
| 开发实现 | 按已确认方案完成实现，并记录执行结果；可由 AI Agent、人工或混合方式执行。 |
| 自动化测试 | 通过可重复测试验证正常、异常、边界与回归行为，形成测试证据。 |
| 测试验收 | 按验收标准确认真实交付结果，并决定需求合格或退回。 |

“自动化测试通过”不等同于“测试验收合格”：前者说明已获得测试证据，后者才是对交付结果的业务确认。上线、发布、运行观察与归档不属于上述“需求提出到合格”的主体阶段；后续如有需要，作为需求合格后的独立交付运维流程设计。

## 当前范围与接入方向

Deliveryline 已以 Chub 业务插件接入，而非独立控制台。设置页与首页都读取统一生命周期状态，但投影规则不同：导入决定设置页插件管理入口是否显示；首页业务入口、业务页面和业务 API 均要求已启用且当前可用。ZIP 由本机构建流程写入固定制品目录，不经浏览器上传或下载。启用不会创建业务数据、Session 或任务。

当前已实现“需求提出”的首次入口：维护者提交任意非空原始需求内容后，Deliveryline 只建立共享档案并进行初始化展示。输入可以是一句话、链接或混合内容；当前不解析、不分类、不生成正式标题，也不把原始内容复制为背景与问题。本次不新增自动解析或 AI 处理；既有档案维护与需求评审能力保持不变。Chub 仅在维护者显式触发开发实现时创建受控 AI Session/任务，Deliveryline 当前不直接操作 Runtime、Worker 或原生 Session。

当前业务模块宿主提供可信访问、固定 Deliveryline 插件包导入、实现选择、启停/可用状态、首页投影，以及第一阶段共享需求档案的读写 API 和页面交互。通用发现、任意第三方模块、动态页面注入、后续阶段治理、受控 Chub 用例和跨模块流程编排不属于当前阶段；出现第二个真实业务模块后，再依据共同需求定义标准协议。

## 共享档案与本机运行态

Deliveryline 的数据按是否为长期业务事实拆分，当前格式基线如下：

```text
data/shared/deliveryline/
  requirements/
    DL-20260912-A3F7.json
    DL-20260915-C8D2.json

data/local/state/deliveryline/
  # 本机锁、草稿恢复、缓存和模块运行状态
data/local/runtime/deliveryline/
  # 本机临时运行文件和未来受控执行关联缓存
```

每个共享需求文件只拥有一条需求，避免不同需求的独立修改集中到同一个大文件而扩大 Git 冲突范围。需求文件采用当前版本的严格 JSON 模型，不接受未知根字段；正式实现以固定 Pydantic 模型校验字段、枚举、时间和文件上限。共享档案不保存 Token、Cookie、账号、访问票据、本机绝对路径、原生 Session 标识或其他秘密。

| 字段组 | 字段 | 规则 |
| --- | --- | --- |
| 识别与时间 | `version`、`id`、`created_at`、`updated_at` | 系统写入；`id` 永不变更，`version` 只用于当前格式校验。 |
| 原始需求 | `original_request_content` | 首次创建时输入的一句话、链接或混合内容；创建后只读，是首次入库的唯一业务输入。历史档案可为 `null`，不从后续编辑内容反推。 |
| 需求档案 | `title`、`background`、`delivery_goal`、`scope`、`out_of_scope`、`constraints`、`acceptance_criteria`、`risks_and_open_items` | 初始化档案保持为空；既有档案维护可在后续使用时补充，本次不新增自动处理。 |
| 交付工作流 | `workflow.current_stage`、`workflow.delivery_status`、`workflow.next_action`、`workflow.latest_stage_conclusion` | 当前阶段固定为六阶段之一；交付状态固定为“进行中、待我处理、存在风险、已交付、已归档”之一。 |
| 活动事实 | `activity` | 按时间追加创建、编辑、推进、退回、归档等记录；每项记录包含时间、动作和有界摘要，不保存原始敏感内容。 |

`workflow.delivery_status` 是跨阶段视图，不替代 `workflow.current_stage`：前者用于顶部四项概览和工作队列，后者用于单条需求的六阶段推进。阶段推进、退回和归档必须同时更新 `updated_at` 并追加活动记录；统计和列表投影只能由这些权威字段计算。

共享目录以 Git 作为维护者主动使用的同步媒介，而不是在线协作数据库。Chub 不自动 `pull`、`commit` 或 `push`；同一需求在不同设备发生未合并冲突时，维护者先完成 Git 冲突处理，Chub 在文件重新合法且同步状态可确认前保持该需求只读。不同需求文件可独立保存和合并，不需要全局编号计数器。

## 当前需求的分阶段实现目标

本章记录 Deliveryline 当前需求的总体目标和分阶段目标，用于拆分讨论、实现和验收顺序，不是单条需求的业务阶段定义。需求业务阶段仍固定为“需求提出、需求评审、方案设计、开发实现、自动化测试、测试验收”；完成任一实现目标不会自动推进任何需求。

### 总体目标

当前总体目标是建立一个面向个人 AI 协作的轻量需求交付管理能力：维护者能清楚看到每项需求要交付什么、当前处于哪个阶段、进入下一阶段还缺少什么、已有何种证据，以及最终是否经过测试验收合格。Deliveryline 负责这些业务事实、决策和结论；Chub 继续负责 Session、任务和运行终态，后者只能作为交付证据，不能替代业务验收。

### 目标调整规则

本章以 **2026-09-12** 的讨论结论为当前基线。后续可根据实际使用、实现成本或新的交付需求调整总体目标和未完成阶段的阶段目标；调整时必须同步更新本章的总体目标、受影响阶段的目标与完成判定，并重新确认当前阶段是否仍可继续。已完成阶段的实际交付与验收结论保留为事实，不因后续目标调整而改写。涉及六个需求业务阶段、状态所有权、证据语义、Chub 执行关联或用户可见验收结论的调整，仍须重新评审本设计。

### 阶段 1：需求台账与交付档案

**阶段目标**：让维护者能够建立并持续查看一条需求的交付上下文。

**交付内容**：基于“共享档案与本机运行态”定义的需求创建、编辑、归档和列表；标题、背景与问题、交付目标、范围、不做什么、约束、验收标准和风险/待确认事项；工作队列中的编号、标题、当前阶段、跨阶段状态、风险、最近更新和下一步；需求详情入口及基础活动记录。

**完成判定**：已实现。不依赖 Chub Session 或外部文档，也能确认“要交付什么、如何验收、当前处于哪个阶段、下一步是什么”；可从一句需求描述建档，评审前资料缺失时明确阻止推进。

**进入下一阶段前确认**：需求评审的完整性规则，以及详情页和列表页的最小交互。

### 阶段 2：六阶段治理

**阶段目标**：让每条需求按固定业务阶段受控推进或退回。

**交付内容**：六阶段进度和当前阶段工作区；各阶段的进入条件、完成条件、允许操作和可退回阶段；阶段确认、退回原因和状态变更记录。

**完成判定**：需求不能跳过关键确认；任一退回都能看到原因、时间和目标阶段。

**进入下一阶段前确认**：每个阶段必须具备的资料、谁可以确认、哪些情况必须退回，以及未完成状态的恢复方式。

### 阶段 3：证据与验收闭环

**阶段目标**：让交付结论可追溯，不把执行活动误当作验收结论。

**交付内容**：方案、决策、问题、测试结果和验收结论的记录；“开发完成”“自动化测试通过”和“测试验收合格”的区分；需求活动历史和交付证据视图。

**完成判定**：任一标记为合格的需求，都能追溯到方案、测试证据和最终验收确认。

**进入下一阶段前确认**：证据类型、引用与附件的存储边界、修改与删除规则，以及验收结论的不可误判条件。

### 阶段 4：受控接入 Chub 执行能力

**阶段目标**：在不改变 Chub 状态所有权的前提下，为“开发实现”阶段补充执行证据。

**交付内容**：维护者明确触发的 Chub Session 或任务创建入口；Deliveryline 需求与受限 Chub 标识的关联；Chub 最终状态和结果摘要在需求详情中的只读投影。

**完成判定**：任务成功、失败、取消或状态未知时，Deliveryline 都能显示真实结果，且不会自动推进需求阶段。

**进入下一阶段前确认**：可调用的固定 Chub 用例、关联记录保留范围、失败恢复路径和用户可见提示。

### 阶段 5：自动化与运营视图

**阶段目标**：基于已确认的业务记录提升测试反馈与交付管理效率。

**交付内容**：自动化测试结果的受控关联；待处理、阻塞、风险和待验收视图；交付统计、提醒和周期复盘。

**完成判定**：所有统计、提醒和自动化结果均可追溯到已有业务事实，不形成另一套需求状态。

**进入下一阶段前确认**：自动化结果来源、失败重试与人工覆盖边界，以及统计口径和通知范围。

阶段 1 至阶段 3 构成首个可人工运行的 Deliveryline MVP。阶段 4 和阶段 5 在 MVP 的状态、证据和验收边界稳定后再启动。开始任一阶段前，必须复核本设计、[Chub 总体架构设计](CHUB_ARCHITECTURE_DESIGN.md)和当前可用能力；涉及需求状态所有权、六阶段名称、证据语义、Chub 执行关联或用户可见验收结论的变化，必须补充对应设计与回归。

## 验收范围与复检

当前已验证 Deliveryline 的插件生命周期、首页入口，以及阶段 1 的共享需求档案创建、编辑、归档、评审前校验和提交评审。六阶段的后续治理、证据记录、Chub 执行关联、自动化测试结果和运营视图尚未实现，也未进入本轮验收。本轮仅在自动化测试环境验证 Web/API 与文件持久化，未进行 macOS、Ubuntu 或多设备 Git 冲突实机验证。后续改变需求状态所有权、主体阶段、阶段推进条件、证据语义、Chub 关联协议或用户可见的验收结论时，必须重新评审本文并补充对应自动化与产品回归。
