# Deliveryline 需求交付管理平台设计

> 状态：持续维护
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义 Deliveryline 的产品定位、主体阶段、作为 Chub 业务模块的接入方向、AI 协作的跨阶段规范，以及已定义阶段的 AI 协作方案。
> 本文不负责：尚未设计阶段的详细资料结构和阶段专属交互、Chub 通用 AI Runtime 调度协议、测试实现或发布运维流程；这些内容在进入对应阶段后再补充。

## AI 可执行契约

1. Deliveryline 是需求交付管理平台，不是 Chub 核心能力、Chub 的别名或 Chub 的替代品；它将作为 Chub 的首个**固定开发业务模块**接入工作台，而不是另建独立控制台。
2. 从需求提出到需求合格，主体阶段名称固定为：`需求提出 → 需求评审 → 方案设计 → 开发实现 → 自动化测试 → 测试验收`。后续不得因执行方式、人员或 Agent 类型重命名这些阶段。本文已定义第一个主体阶段“需求提出”的两个派生小阶段：`1-1 原始需求入库`与`1-2 需求整理与档案补全`。小阶段只说明该主体阶段内的工作顺序，不是新的工作流状态，也不改变进入需求评审的门槛。

阶段目标和验收标准是 Deliveryline 的核心业务契约，本文是唯一权威来源，不得在页面、接口提示、测试说明或其他资料中维护第二个版本。页面可以展示更短的目标摘要以便扫描，但摘要必须与本文语义一致，不得遗漏会改变阶段结果、推进条件或原始业务事实边界的内容。变更任一阶段或小阶段的目标、验收标准或推进条件时，必须先更新本文，再同步页面展示和相关回归用例。

实现中的 `app/deliveryline/workflow.py` 仅是本文已定义阶段契约的机器可读投影，供页面和 AI 协作提示共同读取，不构成第二个业务来源。修改投影必须与本文同次完成，并由回归用例验证目标摘要、AI 输入和阶段名称一致；协作轮次保存当次目标与验收标准快照，仅用于追溯历史输入，不替代本文后续维护的权威契约。

3. `开发实现`是稳定的交付阶段名称；当前可由 AI Agent 执行，但“调用 AI Agent 开发”只是该阶段的执行方式或记录，不是新的主体阶段。
4. 当前只保留跨阶段的初步方向：方案设计应先于开发实现；自动化测试通过只构成测试证据，测试验收按验收标准确认真实交付结果后才能标记需求合格。各后续阶段的具体进入门槛、验收标准和退回规则，待实际进入该阶段前再制定，不得据此提前实现或自动推进。
5. Deliveryline 负责需求流程、阶段门槛、资料、决策、测试结果、验收结论，以及 AI 协作轮次与需求的业务关联；它不管理 AI Agent 的模型设置、具体推理、代码编辑或运行时状态。
6. Chub 仍是个人 AI 工作站，负责工作台壳、可信入口、统一模块生命周期、通知、本机 AI Agent、Runtime、普通交互 Session、任务与运行环境的执行和最终运行状态。Deliveryline 只能通过已定义的受控用例创建或复用关联 Session，并根据已确认的最终结果更新业务资料；任务已受理、Session 已创建或 AI 已返回内容都不等于业务阶段已完成。
7. Deliveryline 的固定模块包位于 `business-modules/deliveryline/`，当前业务实现由 Chub 宿主提供。设置页在模块已导入时保留插件管理入口；首页只在模块已启用且当前可用时，在 `Workspace` 与 Runtime Sessions 之间显示 `Business → Deliveryline`，折叠侧栏和窄屏图标导航同步提供入口。业务页面与业务 API 使用同一可用性门槛。启用后，页面顶部以“进行中、待我处理、存在风险、已交付”四项跨阶段概览呈现整体交付状态，下方展示需求队列、已归档需求和选中需求的六阶段工作区；当前实现覆盖“需求提出”内的原始需求入库、档案补全、提交需求评审和 `1-2` 的 AI 协作。
8. Deliveryline 的正式需求档案是可共享的业务事实，权威根目录固定为 `data/shared/deliveryline/requirements/`；每条需求使用一个独立 JSON 文件。不得复用或编辑 `data/shared/chub/requests.json`，也不得把共享需求档案写入 Chub Session、任务、通知、配置或其他模块的数据文件。
9. 一条需求档案的固定根字段为：`version`、`id`、`title`、`original_request_content`、`background`、`delivery_goal`、`scope`、`out_of_scope`、`constraints`、`acceptance_criteria`、`risks_and_open_items`、`workflow`、`activity`、`created_at` 和 `updated_at`。首次入库只写入 `original_request_content` 与系统字段，创建后不可编辑；`title` 和其他正式需求字段在初始化档案中允许为空，页面使用“未命名需求 + 编号”作为临时展示。历史档案未保留原始内容时固定为 `null`，不得从当前背景反推补写。`workflow` 负责六阶段中的当前阶段、跨阶段交付状态、下一步和最近阶段结论；当前 `activity` 只追加创建、编辑、提交评审和归档事实，推进、退回等动作在对应阶段治理设计后再定义。顶部概览和各类工作队列必须从需求档案实时计算，不单独保存统计结果。
10. `id` 使用不可修改的 `DL-日期-短随机码` 格式，不使用跨设备递增序号；页面可按创建时间或更新时间提供阅读排序。除系统字段外，需求可在草稿阶段不完整，但进入需求评审前必须满足该阶段的完整性规则。
11. 本机锁、草稿恢复、缓存、导入状态和未来执行关联缓存只可位于 `data/local/state/deliveryline/` 或 `data/local/runtime/deliveryline/`，不属于业务事实，也不得进入 Git。停用、升级、重新导入或移除 Deliveryline 不得删除共享需求档案；归档仅改变业务状态。删除共享业务数据必须是独立的危险操作，明确说明影响范围并经过维护者确认。
12. Chub 不自动执行 Git 同步。每次保存必须先校验当前文件，再以有界、原子写入替换单条需求文件；读取和写入必须限制文件大小、字段长度、活动记录数量和权限。出现 Git 未合并冲突、格式非法、文件超限或同步状态无法确认时，必须停止该需求写入并保留原文件，不自动覆盖、合并或丢弃活动记录。

## 产品定位

Deliveryline 面向个人 AI 协作场景，作为 Chub 工作台内的独立业务模块，管理一项需求从提出到验收合格的交付闭环。它关注“需求是否已具备进入下一阶段的条件”和“最终是否已验收合格”，而不是取代开发工具或运行环境。

Chub 与 Deliveryline 的关系为：

```text
Chub 工作台
  ├─ Deliveryline 业务模块：需求流程、阶段门槛、资料、测试和验收结论
  └─ Chub 核心 / AI Runtime：受控执行、Session、Worker 和最终运行状态
```

## AI 协作规范

AI 协作是完成某个阶段目标的处理方式，不是主体阶段、小阶段、`workflow` 状态或交付结论。本文统一维护跨阶段规则；每个实际采用 AI 协作的阶段，再在其阶段契约下维护专属交互方案。阶段方案只能引用本文定义的 Session、轮次和确认规则，不得复制或改写其他阶段的目标、验收标准和推进条件。

### 跨阶段规则

1. 每条 Deliveryline 需求最多关联一个当前有效的 Chub 普通交互 Session。首次发起 AI 协作时创建；同一需求后续协作复用。该 Session 使用 Chub 通用的模型、推理等级和权限设置，Deliveryline 不创建第二套 Runtime 配置，也不修改用户选择的通用设置。
2. Session 关联的范围是“当前需求”，不是“当前阶段”。每一轮协作必须固定记录所属的阶段和阶段契约快照；进入新阶段后可以继续复用同一 Session 的需求上下文，但不得把旧阶段未确认的建议、评论或任务终态作为新阶段的业务结论。阶段契约发生实质变化或维护者明确要求替换时，必须先通过 Chub 标准删除链路删除该需求已关联的旧 Session；只有原生删除和 Chub 清理均确认完成后，才创建替代 Session。删除失败、结果未知或旧关联暂时不可读取时不得创建新 Session，避免重复关联。
3. Chub 是 Session、任务、模型配置、执行状态、停止和删除的唯一所有者。Deliveryline 仅保存“需求关联哪个 Session”、协作轮次、阶段契约快照、建议和评论，用于恢复页面和发起下一轮协作；它不得复制或自行推断 Session 的运行状态。页面读取 Chub 已确认的终态后展示协作结果，任务创建成功或 HTTP 响应成功都不表示 AI 建议已生成。
4. Session 关联、协作轮次、字段建议、维护者意见和本机展示缓存属于本机运行资料，固定保存于 `data/local/state/deliveryline/` 或 `data/local/runtime/deliveryline/`，不写入共享需求 JSON，也不进入 Git。共享档案只保存维护者已确认的正式需求字段和必要活动事实。采纳单项 AI 建议导致字段变化时，按需求编辑记录活动；不把未采纳建议或维护者意见写入共享活动摘要。字段级协作状态使用当前第 2 版本机格式；发现第 1 版整份建议状态时，丢弃旧轮次和建议，但保留旧关联作为“待替换”对象。下一次协作必须先确认删除该旧 Session，再建立新的字段级协作 Session；删除不能确认时不创建新的关联，避免留下重复 Session。
5. Deliveryline 设置页提供独立的“显示 Deliveryline 协作 Session”开关，默认关闭。关闭时该模块关联的 Session 不在 Runtime Sessions 主列表展示，但协作和既有任务不受影响；开启后可按普通 Session 的既有入口查看和管理。该设置仅参考内部翻译 Session 的“默认隐藏、按模块显式显示”模式，不复用内部翻译的文字、配置或筛选范围。
6. AI 只能依据本轮输入生成候选建议、待确认问题或阶段方案规定的其他候选产出。它不得改写 `original_request_content`、直接写入共享需求档案、自动推进或退回 `workflow`，也不得把自身输出标记为验收通过。维护者确认后产生的业务资料和明确触发的推进操作，才适用对应阶段契约。
7. 归档需求不得发起新的协作轮次；删除需求时清理 Deliveryline 本机关联资料。关联 Session 的停止、删除、执行中处理和最终状态确认仍遵循 Chub 的普通 Session 规则，Deliveryline 不得因清理关联而伪造 Session 已停止或已删除。

### 协作轮次固定格式

每个阶段的 AI 协作方案必须明确以下内容：

| 字段 | 作用 |
| --- | --- |
| 触发条件 | 何时允许对该阶段发起或继续协作。 |
| 本轮输入 | 必须传入的需求事实、阶段契约和维护者补充。 |
| AI 工作目标 | 该阶段希望 AI 协助完成的事情；必须与本阶段目标和验收标准一致。 |
| 建议产出 | AI 返回的候选资料、问题或证据形式。 |
| 页面交互 | 详情页如何展示建议、维护者如何确认、评论或继续处理。 |
| 确认后的业务结果 | 维护者确认会更新哪些正式资料，及是否允许推进。 |
| 不确认或失败处理 | 建议被评论、任务失败、结果未知或资料不足时如何保留和恢复。 |

尚未定义阶段专属 AI 协作方案时，不提供该阶段的 AI 协作入口；不得仅因存在关联 Session 就假定 AI 能处理该阶段。

## 主体阶段

六个主体阶段名称与顺序固定。阶段目标、验收标准、推进条件和业务事实以本文为唯一权威来源；页面只展示等义摘要，不能自行扩展、缩减或另行维护业务规则。每条需求的当前阶段、是否完成或是否存在风险只属于该需求档案的 `workflow` 和活动记录，页面据此投影；本文不声明任何具体需求的阶段状态。

### 阶段契约固定格式

每个主体阶段及其小阶段都必须按以下格式维护：

| 字段 | 作用 |
| --- | --- |
| 生命周期位置 | 说明该阶段在固定流程中的位置及其前后关系，不记录任何具体需求的状态。 |
| 目标 | 说明本阶段要达成的业务结果。 |
| 页面目标摘要 | 面向维护者的一句等义摘要；必须从本阶段“目标”导出，不得独立维护业务含义。 |
| 输入 | 说明开始本阶段时使用的业务事实或前置结论。 |
| 产出 | 说明阶段结束时形成的业务资料或结论。 |
| 验收标准 | 说明如何确认目标已经达成。 |
| 推进与未通过处理 | 说明何时、由谁推进，以及资料不足或验收未通过时的处理。 |
| 需保留的业务事实 | 说明必须写入需求档案、不可仅存在于页面或运行态的事实。 |

尚未定义详细契约的阶段只填写“生命周期位置”和“初步目标”；页面固定展示“详细阶段契约待制定。”，输入、产出、验收标准、推进与未通过处理、需保留的业务事实均标记为“进入该阶段前制定”。不得把初步目标视为已确认的验收规则或据此自动推进。

### 六个主体阶段总览

| 阶段 | 生命周期位置 | 初步目标 |
| --- | --- | --- |
| 需求提出 | 固定流程第 1 阶段。 | 形成可讨论、可提交评审的正式需求档案。 |
| 需求评审 | 固定流程第 2 阶段，位于需求提出之后。 | 确认需求值得实施、边界明确，并可进入方案阶段。 |
| 方案设计 | 固定流程第 3 阶段，位于需求评审之后。 | 形成并确认交付方案与验收标准。 |
| 开发实现 | 固定流程第 4 阶段，位于方案设计之后。 | 按已确认方案完成实现，并记录执行结果；可由 AI Agent、人工或混合方式执行。 |
| 自动化测试 | 固定流程第 5 阶段，位于开发实现之后。 | 通过可重复测试验证正常、异常、边界与回归行为，形成测试证据。 |
| 测试验收 | 固定流程第 6 阶段，位于自动化测试之后。 | 按验收标准确认真实交付结果，并决定需求合格或退回。 |

“自动化测试通过”不等同于“测试验收合格”：前者说明已获得测试证据，后者才是对交付结果的业务确认。上线、发布、运行观察与归档不属于上述“需求提出到合格”的主体阶段；后续如有需要，作为需求合格后的独立交付运维流程设计。

### 需求提出阶段契约

| 字段 | 阶段契约 |
| --- | --- |
| 生命周期位置 | 固定流程第 1 阶段，由 `1-1` 后接 `1-2` 组成。 |
| 目标 | 在保留只读原始需求内容的前提下，形成可讨论、可提交评审的正式需求档案。 |
| 页面目标摘要 | 当前页面展示 `1-2` 的页面目标摘要。 |
| 输入 | 维护者首次提交的任意非空原始需求内容，以及后续补充的需求信息。 |
| 产出 | 原始需求来源记录和补全后的正式需求档案。 |
| 验收标准 | `1-1` 与 `1-2` 均达到各自验收标准，且维护者显式提交需求评审。 |
| 推进与未通过处理 | 仅维护者可提交进入需求评审；资料未补全时停留在 `1-2`，页面指出待补充内容，不自动推进。 |
| 需保留的业务事实 | 原始需求内容、正式需求字段、当前阶段、跨阶段状态、下一步、活动记录和时间。 |

AI 协助和人工处理都是完成上述目标的方式，不构成新的阶段或小阶段。

#### 1-1 原始需求入库

| 字段 | 阶段契约 |
| --- | --- |
| 生命周期位置 | 需求提出的入口小阶段；完成后进入 `1-2`。 |
| 目标 | 保存首次输入的一句话、链接或混合内容，并保留为只读来源记录。 |
| 页面目标摘要 | 保存原始需求并建立需求档案。 |
| 输入 | 维护者提交的任意非空原始需求内容。 |
| 产出 | 具有唯一编号的初始化需求档案。 |
| 验收标准 | 已创建唯一的初始化需求档案和编号；原始内容完整写入 `original_request_content` 且创建后只读；失败时不保留半成品档案或伪造成功结果。 |
| 推进与未通过处理 | 创建成功后自动完成 `1-1` 并转入 `1-2`；创建失败时停留在入库操作，不生成需求档案。 |
| 需保留的业务事实 | `id`、`original_request_content`、创建时间和创建活动记录。 |

#### 1-2 需求整理与档案补全

| 字段 | 阶段契约 |
| --- | --- |
| 生命周期位置 | 位于 `1-1` 之后、需求评审之前。 |
| 目标 | 在不改写只读原始需求内容的前提下，将已入库的原始需求整理为可讨论、可提交评审的正式需求档案；明确标题、背景与问题、交付目标、本次范围、不做什么、约束与依赖、验收标准和风险与待确认事项。 |
| 页面目标摘要 | 保留原始需求，补全为可提交评审的正式档案。 |
| 输入 | `1-1` 留存的原始需求内容，以及维护者、AI 或其他可信资料提供的补充信息。 |
| 产出 | 补全八项正式需求字段、具备提交评审资格的需求档案。 |
| 验收标准 | 标题、背景与问题、交付目标、本次范围、不做什么、约束与依赖、验收标准、风险与待确认事项均已按当前完整性规则补全，获得“可提交评审”资格。 |
| 推进与未通过处理 | 资料未补全时停留在 `1-2` 并显示待补充内容；达标后仍须由维护者显式提交，才进入需求评审，不自动推进。 |
| 需保留的业务事实 | 八项正式需求字段、原始需求内容、可由正式字段计算的准备度、当前阶段、下一步、更新时间和编辑活动记录。 |

##### AI 协作方案

| 字段 | 本阶段方案 |
| --- | --- |
| 触发条件 | 需求已完成 `1-1`、当前仍处于“需求提出”且未归档。详情页底部提供单一“AI 协作”入口；当前轮返回建议后，已采纳字段保持正式档案值，未采纳字段可直接继续协作并由新一轮建议替换。维护者填写的字段意见作为下一轮优先输入，但不要求先为每项未采纳建议填写意见。 |
| 本轮输入 | `1-2` 的目标和验收标准、只读 `original_request_content`、当前八项正式字段、由这些字段计算的待补充项，以及存在时的上一轮字段建议与维护者对字段提出的意见。原始内容中的链接最多识别三项：已登记 Chub 项目资料页按固定文档 ID 读取有界正文；其他公共 HTTP(S) 链接仅对该次协作任务授予既有页面只读能力后读取；本机、内网、带凭据、不合规或读取失败的链接不扩展访问范围，AI 不得臆测正文，应写入待确认问题。资料正文仅作为本轮候选建议输入，不写入共享需求档案。 |
| AI 工作目标 | 在不改写原始需求的前提下，形成一份完整的正式需求档案建议，并明确仍缺少或需要维护者确认的信息，使维护者能够判断该需求如何达到“可提交评审”资格。 |
| 建议产出 | 一份整体生成、字段级确认的 AI 协作建议：八项正式字段各有建议值和独立处理状态，并附带待确认问题。字段值必须是可直接写入档案的正文；标题只返回标题本身，不得包含“AI 建议”“建议”“待确认”“标题”“展示”等展示或状态前缀。标题信息不足时仍生成中性的可用工作标题，所有不确定、待确认或缺失信息只写入 `open_questions`，不得作为标题前缀。出现该类前缀时，整轮建议无效并要求重新协作，不由系统改写后采纳。建议是候选内容，不是阶段结论。 |
| 初始页面展示 | 依次展示标题、待补充内容、原始需求内容和当前正式需求字段；底部展示“AI 协作”。 |
| 返回建议后的页面交互 | AI 建议直接展示在同一“待补充内容”框的对应字段下方。每项待处理建议提供“采纳”和“建议”：采纳后立即移除该项建议并更新正式字段；建议后只展开该字段的意见输入框，不提供单独提交按钮。维护者在再次点击“AI 协作”时，页面一次性提交原始需求、上一轮建议和所有已填写意见。 |
| 确认后的业务结果 | 单项采纳表示维护者确认该字段建议，将该值立即写入正式需求档案并重新计算待补充项；不改写原始需求，不自动推进阶段。字段建议后不写入正式字段，只作为下一轮协作输入。 |
| 再次协作 | 当前轮存在未采纳字段时恢复“继续 AI 协作”；维护者可先采纳任意字段，也可直接继续。下一轮复用该需求关联 Session，只为未采纳字段生成新建议，并同时输入原始需求、上一轮完整建议和已填写的维护者意见。已采纳字段保留当前正式档案值，不重新生成；全部字段均已采纳时无需再次协作。 |
| 阶段确认与失败处理 | “阶段确认”与“AI 协作”并列展示。仅在八项正式字段满足 `1-2` 完整性规则且不存在未处理字段建议时可用；维护者确认后才进入需求评审。任务失败、任务不存在或提交结果未知时保留当前正式字段和最近可用建议，并显示“AI 协作”作为恢复入口；协作本机状态不可读取时，不重置或猜测关联，停止新的协作写入并保留状态文件供恢复。 |

提交需求评审是 `1-2` 的出口动作，不表示需求评审阶段治理已经实现。进入需求评审后，页面只显示“详细阶段契约待制定。”；当后续开始设计任一尚未定义详细契约的主体阶段时，必须先按本节固定格式补全其完整契约，再开始对应的页面、接口或执行能力设计。

## 当前范围与接入方向

Deliveryline 已以 Chub 业务插件接入，而非独立控制台。设置页与首页都读取统一生命周期状态，但投影规则不同：导入决定设置页插件管理入口是否显示；首页业务入口、业务页面和业务 API 均要求已启用且当前可用。ZIP 由本机构建流程写入固定制品目录，不经浏览器上传或下载。启用不会创建业务数据、Session 或任务。

当前页面展示六个主体阶段、需求提出的两个小阶段，以及从本节“页面目标摘要”派生的当前工作目标。`1-1` 和 `1-2` 的完整业务契约以“主体阶段”一节为准；页面不另行维护目标或验收规则。当前实现支持任意非空原始内容入库、初始化展示和档案字段补全，并在 `1-2` 通过受控普通交互 Session 发起、恢复和确认 AI 协作建议。其他尚未定义阶段不创建或复用 Deliveryline 协作 Session。

当前业务模块宿主提供可信访问、固定 Deliveryline 插件包导入、实现选择、启停/可用状态、首页投影，以及需求提出阶段共享需求档案的读写 API 和页面交互。通用发现、任意第三方模块、动态页面注入、后续阶段治理、受控 Chub 用例和跨模块流程编排不属于当前阶段；出现第二个真实业务模块后，再依据共同需求定义标准协议。

## 共享档案与本机运行态

Deliveryline 的数据按是否为长期业务事实拆分，当前格式基线如下：

```text
data/shared/deliveryline/
  requirements/
    DL-20260912-A3F7.json
    DL-20260915-C8D2.json

data/local/state/deliveryline/
  # 本机锁、草稿恢复、缓存、协作轮次和模块运行状态
data/local/runtime/deliveryline/
  # 本机临时运行文件和 Session/任务关联缓存
```

每个共享需求文件只拥有一条需求，避免不同需求的独立修改集中到同一个大文件而扩大 Git 冲突范围。需求文件采用当前版本的严格 JSON 模型，不接受未知根字段；正式实现以固定 Pydantic 模型校验字段、枚举、时间和文件上限。共享档案不保存 Token、Cookie、账号、访问票据、本机绝对路径、原生 Session 标识或其他秘密。

| 字段组 | 字段 | 规则 |
| --- | --- | --- |
| 识别与时间 | `version`、`id`、`created_at`、`updated_at` | 系统写入；`id` 永不变更，`version` 只用于当前格式校验。 |
| 原始需求 | `original_request_content` | 首次创建时输入的一句话、链接或混合内容；创建后只读，是首次入库的唯一业务输入。历史档案可为 `null`，不从后续编辑内容反推。 |
| 需求档案 | `title`、`background`、`delivery_goal`、`scope`、`out_of_scope`、`constraints`、`acceptance_criteria`、`risks_and_open_items` | 初始化档案保持为空；维护者可以手动补充，或在对应阶段逐项采纳 AI 协作建议后写入。 |
| 交付工作流 | `workflow.current_stage`、`workflow.delivery_status`、`workflow.next_action`、`workflow.latest_stage_conclusion` | 当前阶段固定为六阶段之一；交付状态固定为“进行中、待我处理、存在风险、已交付、已归档”之一。 |
| 活动事实 | `activity` | 当前按时间追加创建、编辑、提交评审和归档记录；每项记录包含时间、动作和有界摘要，不保存原始敏感内容。推进、退回等记录在对应阶段治理设计后再定义。 |

`workflow.delivery_status` 是跨阶段视图，不替代 `workflow.current_stage`：前者用于顶部四项概览和工作队列，后者用于单条需求的六阶段推进。阶段推进、退回和归档必须同时更新 `updated_at` 并追加活动记录；统计和列表投影只能由这些权威字段计算。

共享目录以 Git 作为维护者主动使用的同步媒介，而不是在线协作数据库。Chub 不自动 `pull`、`commit` 或 `push`；同一需求在不同设备发生未合并冲突时，维护者先完成 Git 冲突处理，Chub 在文件重新合法且同步状态可确认前保持该需求只读。不同需求文件可独立保存和合并，不需要全局编号计数器。

## Deliveryline 建设里程碑

本章记录 Deliveryline 的建设目标和建设里程碑，用于拆分讨论、实现和验收顺序，不是单条需求的业务阶段定义。需求业务阶段仍固定为“需求提出、需求评审、方案设计、开发实现、自动化测试、测试验收”；完成任一建设里程碑不会自动推进任何需求。

### 总体目标

当前总体目标是建立一个面向个人 AI 协作的轻量需求交付管理能力：维护者能清楚看到每项需求要交付什么、当前处于哪个阶段、进入下一阶段还缺少什么、已有何种证据，以及最终是否经过测试验收合格。Deliveryline 负责这些业务事实、决策和结论；Chub 继续负责 Session、任务和运行终态，后者只能作为交付证据，不能替代业务验收。

### 目标调整规则

本章以 **2026-09-12** 的讨论结论为当前基线。后续可根据实际使用、实现成本或新的交付需求调整总体目标和建设里程碑的初步目标；详细范围、验收标准和完成判定，必须在开始对应建设工作时制定，不提前视为既定契约。已经验证的实现范围保留为事实，不因后续目标调整而改写。涉及六个需求业务阶段、状态所有权、证据语义、Chub 执行关联或用户可见验收结论的调整，仍须重新评审本设计。

### 建设里程碑 1：需求台账与交付档案

**阶段目标**：让维护者能够建立并持续查看一条需求的交付上下文。

**交付内容**：基于“共享档案与本机运行态”定义的需求创建、编辑、归档和列表；标题、背景与问题、交付目标、范围、不做什么、约束、验收标准和风险/待确认事项；工作队列中的编号、标题、当前阶段、跨阶段状态、风险、最近更新和下一步；需求详情入口及基础活动记录；以及仅限已定义阶段的 AI 协作入口、关联与维护者确认流程。

**已验证基线**：基础能力不依赖 Chub Session 或外部文档，也能确认“要交付什么、如何验收、当前处于哪个阶段、下一步是什么”；可从一句需求描述建档，评审前资料缺失时明确阻止推进。需求提出阶段的 `1-2` 适用本文当前规则。

**后续调整**：随着 `1-2` 的实际推进，按主体阶段规则补充或收敛其资料要求与验收标准，并按“AI 协作规范”和 `1-2` 的阶段方案接入协作能力；不把基础能力已验证理解为任一具体需求已经完成需求提出阶段。

### 建设里程碑 2：六阶段治理

**初步目标**：让每条需求按固定业务阶段受控推进或退回。

**验收标准与细项**：开始对应建设工作时再制定各阶段的资料要求、进入与完成条件、允许操作、退回规则、恢复方式和状态记录。

### 建设里程碑 3：证据与验收闭环

**初步目标**：让交付结论可追溯，不把执行活动误当作验收结论。

**验收标准与细项**：开始对应建设工作时再制定证据类型、存储边界、修改与删除规则、验收结论的确认方式和追溯要求。

### 建设里程碑 4：受控接入 Chub 开发执行能力

**初步目标**：在不改变 Chub 状态所有权的前提下，为“开发实现”阶段补充执行证据；它不替代前述已定义阶段的资料整理型 AI 协作。

**验收标准与细项**：开始对应建设工作时再制定可调用的固定 Chub 用例、关联记录范围、最终状态投影、失败恢复和不自动推进的边界。

### 建设里程碑 5：自动化与运营视图

**初步目标**：基于已确认的业务记录提升测试反馈与交付管理效率。

**验收标准与细项**：开始对应建设工作时再制定自动化结果来源、统计口径、通知范围、失败重试、人工覆盖和不形成第二套需求状态的约束。

建设里程碑 1 至建设里程碑 3 是首个可人工运行 MVP 的初步建设顺序，不构成后续里程碑的验收承诺。建设里程碑 4 和建设里程碑 5 在 MVP 的状态、证据和验收边界稳定后再评估是否开始。开始任一建设里程碑前，必须复核本设计、[Chub 总体架构设计](CHUB_ARCHITECTURE_DESIGN.md)和当前可用能力；涉及需求状态所有权、六阶段名称、证据语义、Chub 执行关联或用户可见验收结论的变化，必须补充对应设计与回归。

## 验收范围与复检

当前已验证 Deliveryline 的插件生命周期、首页入口，以及建设里程碑 1 的共享需求档案创建、编辑、归档、评审前校验和提交评审。`1-2` 的 AI 协作已完成本机状态、建议确认与页面/API 自动化测试，但尚未在真实 AI Runtime 完成从任务提交到建议返回的端到端实机验收；六阶段的后续治理、证据记录、Chub 开发执行关联、自动化测试结果和运营视图同样尚未实现。本轮未进行 macOS、Ubuntu 或多设备 Git 冲突实机验证。后续改变需求状态所有权、主体阶段、阶段推进条件、证据语义、Chub 关联协议或用户可见的验收结论时，必须重新评审本文并补充对应自动化与产品回归。
