# Deliveryline 需求交付管理平台设计

> 状态：调研中
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义 Deliveryline 的产品定位、主体阶段、作为 Chub 业务模块的接入方向，以及与 Chub 的职责边界。
> 本文不负责：业务模块宿主协议、阶段内资料结构、页面交互、数据模型、AI Agent 调度协议、测试实现或发布运维流程；这些内容在进入对应阶段后再单独设计。

## AI 可执行契约

1. Deliveryline 是需求交付管理平台，不是 Chub 核心能力、Chub 的别名或 Chub 的替代品；它将作为 Chub 的首个**固定开发业务模块**接入工作台，而不是另建独立控制台。
2. 从需求提出到需求合格，主体阶段名称固定为：`需求提出 → 需求评审 → 方案设计 → 开发实现 → 自动化测试 → 测试验收`。后续不得因执行方式、人员或 Agent 类型重命名这些阶段。
3. `开发实现`是稳定的交付阶段名称；当前可由 AI Agent 执行，但“调用 AI Agent 开发”只是该阶段的执行方式或记录，不是新的主体阶段。
4. 方案经确认后才能进入开发实现；测试验收通过才可标记需求合格。验收未通过时，根据问题性质回到方案设计或开发实现。
5. Deliveryline 负责需求流程、阶段门槛、资料、决策、测试结果和验收结论；它不管理 AI Agent 在开发实现阶段内的具体推理、代码编辑或运行时状态。
6. Chub 仍是个人 AI 工作站，负责工作台壳、可信入口、模块生命周期、通知、本机 AI Agent、Runtime、任务与运行环境的执行和最终运行状态。Deliveryline 负责需求流程、交付资料和阶段结论；在维护者明确触发“开发实现”时，只通过 Chub 已定义的受控 Session/任务用例发起执行，并保存关联和最终结果作为交付证据。
7. Deliveryline 的固定开发源码将在实现开始时放入 `business-modules/deliveryline/`。当前只确认该目录与模块方向，尚未创建业务模块宿主、源码目录、页面入口、数据模型或 ZIP 安装协议；不得将其写成当前可安装能力。

## 产品定位

Deliveryline 面向个人 AI 协作场景，作为 Chub 工作台内的独立业务模块，管理一项需求从提出到验收合格的交付闭环。它关注“需求是否已具备进入下一阶段的条件”和“最终是否已验收合格”，而不是取代开发工具或运行环境。

Chub 与 Deliveryline 的关系为：

```text
Chub 工作台
  ├─ Deliveryline 业务模块：需求流程、阶段门槛、资料、测试和验收结论
  └─ Chub 核心 / AI Runtime：受控执行、Session、Worker 和最终运行状态
```

## 主体阶段

| 阶段 | 阶段目标 |
| --- | --- |
| 需求提出 | 明确需求目标、场景、范围、约束和验收预期。 |
| 需求评审 | 确认需求清晰、合理且具备实施价值，明确边界与风险。 |
| 方案设计 | 形成可确认的交付方案与验收标准。 |
| 开发实现 | 按已确认方案完成实现；可由 AI Agent、人工或混合方式执行。 |
| 自动化测试 | 通过可重复测试验证正常、异常、边界与回归行为。 |
| 测试验收 | 按验收标准确认真实结果；通过后需求合格。 |

上线、发布、运行观察与归档不属于上述“需求提出到合格”的主体阶段；后续如有需要，作为需求合格后的独立交付运维流程设计。

## 当前范围与接入方向

当前已确认 Deliveryline 以 Chub 固定开发业务模块接入，而非独立控制台；尚未开始 Deliveryline 或业务模块宿主的产品实现。

第一阶段先实现固定的 Deliveryline 业务闭环：需求记录、阶段资料与确认规则、状态流转、自动化测试结果和验收记录。Chub 仅在维护者显式触发开发实现时创建受控 AI Session/任务，Deliveryline 不直接操作 Runtime、Worker 或原生 Session。

业务模块宿主在开始实现时只提供 Deliveryline 所需的最小能力：固定工作台分区、可信访问、模块专属数据边界、启停/可用状态和受控 Chub 用例。ZIP 导入、通用发现、任意第三方模块、动态页面注入和跨模块流程编排不属于第一阶段；出现第二个真实业务模块后，再依据两者共同需求定义标准协议。
