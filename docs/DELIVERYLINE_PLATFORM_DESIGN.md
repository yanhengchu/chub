# Deliveryline 需求交付管理平台设计

> 状态：持续维护
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义 Deliveryline 的产品定位、整体交付线与交付项的两层流程、作为 Chub 业务模块的接入方向、AI 协作的跨阶段规范，以及已定义阶段的 AI 协作方案。
> 本文不负责：整体交付线的持久化格式、版本/影响分析页面、尚未设计交付项阶段的详细资料结构和交互、Chub 通用 AI Runtime 调度协议、测试实现或发布运维流程；这些内容在进入对应建设工作后再补充。

## AI 可执行契约

1. Deliveryline 是需求交付管理平台，不是 Chub 核心能力、Chub 的别名或 Chub 的替代品；它将作为 Chub 的首个**固定开发业务模块**接入工作台，而不是另建独立控制台。
2. Deliveryline 区分**整体交付线**与**交付项**。整体交付线承载大设计资料、总体目标、路线图、目标版本和影响分析；交付项是当前可独立评审、实施和验收的具体切片。需求澄清、正式成档、评审、方案设计、开发实现、测试与验收是交付项可选用且可反复进入的工作检查点，不构成每项必须线性走完的固定生命周期；仅在适用时才成为该交付项的推进条件。后续不得因执行方式、人员或 Agent 类型改变这些检查点的业务含义。

阶段目标和验收标准是 Deliveryline 的核心业务契约，本文是唯一权威来源，不得在页面、接口提示、测试说明或其他资料中维护第二个版本。页面可以展示更短的目标摘要以便扫描，但摘要必须与本文语义一致，不得遗漏会改变阶段结果、推进条件或原始业务事实边界的内容。变更任一阶段或小阶段的目标、验收标准或推进条件时，必须先更新本文，再同步页面展示和相关回归用例。

交付线状态由共享交付线档案自身的 `status` 字段唯一记录；不再使用或映射旧单交付项 `workflow`。AI 整体澄清轮次只保存于本机运行态，用于追溯候选输入和恢复，不替代维护者确认后的目标版本。

3. `开发实现`是稳定的交付阶段名称；当前可由 AI Agent 执行，但“调用 AI Agent 开发”只是该阶段的执行方式或记录，不是新的交付项阶段。
4. 当前只保留跨检查点的初步方向：需要方案的交付项应在开发实现前完成方案确认；自动化测试通过只构成测试证据，测试验收按验收标准确认真实交付结果后才能标记交付项合格。检查点可因资料补充、评审结论、实施发现或整体目标变更回到需求澄清或方案设计；各检查点的具体进入门槛、验收标准和回退规则，待实际进入对应建设工作前再制定，不得据此提前实现或自动推进。
5. Deliveryline 负责需求流程、阶段门槛、资料、决策、测试结果、验收结论，以及 AI 协作轮次与需求的业务关联；它不管理 AI Agent 的模型设置、具体推理、代码编辑或运行时状态。
6. Chub 仍是个人 AI 工作站，负责工作台壳、可信入口、统一模块生命周期、通知、本机 AI Agent、Runtime、普通交互 Session、任务与运行环境的执行和最终运行状态。Deliveryline 只能通过已定义的受控用例创建或复用关联 Session，并根据已确认的最终结果更新业务资料；任务已受理、Session 已创建或 AI 已返回内容都不等于业务阶段已完成。
7. Deliveryline 的固定模块包位于 `business-modules/deliveryline/`，当前业务实现由 Chub 宿主提供。设置页在模块已导入时保留插件管理入口；首页只在模块已启用且当前可用时，在 `Workspace` 与 Runtime Sessions 之间显示 `Business → Deliveryline`。当前已实现原始资料入库、交付线详情中的 AI 整体澄清、维护者确认整体目标版本，以及结束和删除交付线；尚未实现路线图、交付项拆分、影响分析和交付项工作循环。
8. Deliveryline 的交付线档案是可共享的业务事实，权威根目录固定为 `data/shared/deliveryline/requirements/`；每条交付线使用一个独立 JSON 文件。不得复用或编辑 `data/shared/chub/requests.json`，也不得把共享档案写入 Chub Session、任务、通知、配置或其他模块的数据文件。
9. 当前交付线根字段为：`version`、`id`、`original_request_content`、`status`、`title`、`source_role`、`overall_goal`、`confirmed_facts`、`scope_boundary`、`open_questions`、`goal_versions`、`activity`、`created_at` 和 `updated_at`。首次入库只写原始资料与系统字段，状态为`待澄清`；AI 候选不写入共享档案。只有维护者显式确认后，当前目标字段和一个不可变目标版本写入档案，状态进入`规划中`。当前不保存路线图或交付项。
10. `id` 使用不可修改的 `DL-日期-短随机码` 格式，不使用跨设备递增序号；页面可按创建时间或更新时间提供阅读排序。
11. 本机锁、草稿恢复、缓存、导入状态和未来执行关联缓存只可位于 `data/local/state/deliveryline/` 或 `data/local/runtime/deliveryline/`，不属于业务事实，也不得进入 Git。停用、升级、重新导入或移除 Deliveryline 不得删除共享需求档案；归档仅改变业务状态。删除共享业务数据必须是独立的危险操作，明确说明影响范围并经过维护者确认。
12. Chub 不自动执行 Git 同步。每次保存必须先校验当前文件，再以有界、原子写入替换单条需求文件；读取和写入必须限制文件大小、字段长度、活动记录数量和权限。出现 Git 未合并冲突、格式非法、文件超限或同步状态无法确认时，必须停止该需求写入并保留原文件，不自动覆盖、合并或丢弃活动记录。

## 产品定位

Deliveryline 面向个人 AI 协作场景，作为 Chub 工作台内的独立业务模块，管理整体交付意图及其下可独立验收的交付项。AI 是资料分析、澄清、方案整理、执行建议和证据归集的主要工作主体；维护者负责确认或修正 AI 候选结论，决定范围、优先级和是否推进。它先帮助维护者从资料中确认“这次要改变什么”，再管理交付项是否具备进入下一阶段的条件和最终是否验收合格；它不把任意设计文档、链接或背景资料自动等同为一条可实施需求，也不取代开发工具或运行环境。

Chub 与 Deliveryline 的关系为：

```text
Chub 工作台
  ├─ Deliveryline 业务模块：需求流程、阶段门槛、资料、测试和验收结论
  └─ Chub 核心 / AI Runtime：受控执行、Session、Worker 和最终运行状态
```

## 交付线与交付项

### 名称与列表层级

页面与接口使用以下固定名称，不用“需求列表”“待整理记录”或“原型记录”混合指代不同层级：

| 名称 | 对象与页面位置 | 规则 |
| --- | --- | --- |
| 交付线列表 | Deliveryline 首页的主列表。 | 每次导入原始资料先形成一条整体交付线，初始状态为`待澄清`。列表持续显示该交付线，不因确认整体目标或拆分交付项而改名。 |
| 交付线详情 | 选中交付线后的主详情。 | 未确认整体目标时，只展示原始资料、整体澄清、当前目标版本和待确认事项；确认后再展示路线图、影响分析与交付项列表。 |
| 交付项列表 | 已确认交付线详情内的下级列表。 | 仅展示该交付线已经创建的具体交付项；整体目标未确认时不展示也不允许创建。 |
| 交付项详情 | 选中交付项后的下级详情。 | 展示正式档案、适用检查点、运行状态、待处理事项、证据和活动事实。 |

交付线状态固定使用`待澄清`、`规划中`、`推进中`、`变更评估中`和`已结束`。其中状态表达整体治理进展，不替代交付项的运行状态或检查点结论。现有单交付项原型的`workflow`状态不映射为上述状态；新模型实施时必须由交付线自身的权威字段记录。

### 整体交付线

整体交付线用于管理一份大设计资料或持续演进的总体目标。它的工作流是：`资料入库 → 整体需求澄清 → 路线图规划 → 交付项拆分与排序 → 持续影响分析 → 已结束`。这是管理视图，不是严格串行的全局门禁：路线图可以调整，影响分析可以在任意时点重新发生，只有被判断为直接冲突的交付项才暂停或回退。

整体需求澄清的产出是资料角色、已知事实、整体目标候选和最少待确认问题。它不直接产出一套八字段正式档案，不把设计资料中的已实现基线或长期路线图写成本次实施范围，也不在整体目标确认前产出路线图、当前优先项或交付项拆分结论。

### AI 整体澄清

交付线处于`待澄清`时，详情标题与说明右侧的主操作固定为 **AI 整体澄清**。同一操作区仅保留危险次级操作 **删除**，不在详情正文重复展示；无选中交付线、AI 正在处理或交付线已结束时删除不可用。维护者不需要先手工填写完整表单，AI 先根据原始资料完成理解和候选整理，维护者再确认或修正。

| 字段 | 本阶段契约 |
| --- | --- |
| 触发条件 | 交付线已入库、尚未确认整体目标且未结束；由维护者主动发起。维护者可携带补充说明或对上一轮候选的修正意见再次发起。 |
| 本轮输入 | 只读原始资料、已允许读取的链接正文、上一轮未确认候选、已确认事实（如有）和维护者意见。链接读取继续遵循受控范围，不访问本机、内网、带凭据或其他未授权资源。 |
| AI 工作目标 | 判断资料是相对完整的需求、需要持续演进的需求、设计提案、现状说明还是混合资料；提炼可追溯的事实，并给出可由维护者确认的整体目标候选。 |
| 候选输出 | 资料角色、已知事实、整体目标候选、目标适用范围、未解决问题与必要假设。每项标记为“资料事实”“AI 推断”或“待确认”。不输出正式交付项档案、路线图、交付项列表、优先级或实现方案。 |
| 页面交互 | 候选结果显示在原始资料之后；维护者可确认、直接编辑，或填写修正意见后再次协作。处理中主按钮显示处理中；存在未确认候选时显示“继续 AI 整体澄清”。 |
| 确认后的业务结果 | 只有维护者显式确认的整体目标、事实与边界写入交付线共享业务档案，并形成第一个整体目标版本；AI 返回、Session 创建或任务成功均不产生该结果。 |
| 未通过与失败处理 | 资料不足时保持`待澄清`并只展示待确认问题；任务失败、结果未知或解析失败时保留原始资料和最近可用候选，可再次协作；不得自动创建交付项或推进到路线图规划。 |

整体目标只有在维护者显式确认后才成为交付线的当前目标版本；确认前，交付线详情不得展示“当前交付项”，不得创建交付项，也不得把 AI 候选、Session 创建或任务成功视为整体目标已确认。确认后，交付线才进入路线图规划；AI 可提出交付项拆分与排序建议，但仍由维护者确认后才创建具体交付项。

整体目标变更必须形成新的版本，并记录变更内容、原因、影响范围和分析结论。每个交付项在创建或进入评审时保存其依据的整体目标版本快照。影响分析只能得出以下有限结论：`无影响`、`需局部调整`、`需停止或替换`、`仅影响后续计划`。整体变更默认不自动改写、取消或重放任何交付项。

### 交付项

交付项是从整体交付线选出的当前可独立评审、实施和验收的切片。它以“当前要达成的结果”和“还需要哪些检查点”为中心推进，而不是进入一条固定六阶段状态机。通常先完成需求准备与正式成档；随后是否需要评审、方案设计、开发实现、自动化测试和测试验收，取决于该交付项的类型、风险和已确认的验收方式。已澄清或已落地的交付项是否随整体目标变化而调整，必须按其影响分析结论判断：无影响则继续；未完成且直接受影响时回到自身澄清或方案设计；已验收结果需要改变时创建新的修正、替换或下线交付项，不能回写历史结论。

当前版本已实现整体交付线的基础数据、详情页和目标版本确认。大设计文档可作为一条交付线的原始资料，但系统不会自动拆分路线图或创建交付项；这些仍需在后续规划阶段单独确认。

## AI 协作规范

AI 协作是完成某个阶段目标的处理方式，不是交付项阶段、小阶段、`workflow` 状态或交付结论。本文统一维护跨阶段规则；每个实际采用 AI 协作的阶段，再在其阶段契约下维护专属交互方案。阶段方案只能引用本文定义的 Session、轮次和确认规则，不得复制或改写其他阶段的目标、验收标准和推进条件。

### AI 与维护者职责

1. AI 默认承担资料阅读、事实提炼、候选结论生成、待确认问题归纳、方案草拟、实现建议、测试建议与证据整理等可执行工作；后续工作不应要求维护者先手工填写 AI 本可从资料和已确认结论中完成的内容。每轮 AI 的工作目标必须收敛到当前检查点，不能借“协作”提前输出后续检查点的正式结论。
2. 维护者默认承担确认、修正、补充缺失事实、选择优先级、决定范围、授权推进和业务验收；维护者的编辑或意见是下一轮 AI 协作的高优先级输入。
3. AI 的任何输出均为候选，不得自动确认整体目标、写入共享业务事实、创建或停止交付项、改变交付线/交付项状态，或替代维护者的验收结论。
4. 每个检查点的页面优先呈现“AI 已完成什么、仍需维护者确认什么、可如何修正或再次协作”，而非以空表单要求维护者承担主体整理工作。

### 跨阶段规则

1. 每条交付线最多关联一个当前有效的 Chub 普通交互 Session。首次整体澄清时创建；同一条待澄清交付线的再次澄清复用。该 Session 使用 Chub 通用的模型、推理等级和权限设置，Deliveryline 不创建第二套 Runtime 配置，也不修改用户选择的通用设置。
2. 当前关联仅用于整体澄清。整体目标确认后，不得继续使用该入口修改目标；目标变更必须在后续“变更评估中”流程中定义原因、影响范围、分析结论和新版本，再提供对应协作入口。
3. Chub 是 Session、任务、模型配置、执行状态、停止和删除的唯一所有者。Deliveryline 只保存交付线与 Session 的关联、澄清轮次、候选和维护者意见，用于恢复页面和再次澄清；它不得自行推断任务状态。任务提交发生异常时必须按操作 ID 对账，任务创建成功或 HTTP 响应成功都不表示 AI 候选已生成。
4. Session 关联、整体澄清轮次、未确认候选、维护者意见和本机展示缓存属于本机运行资料，固定保存于 `data/local/state/deliveryline/` 或 `data/local/runtime/deliveryline/`，不写入共享交付线 JSON，也不进入 Git。共享档案只保存维护者确认的目标版本、当前目标和必要活动事实。旧字段级协作状态不兼容当前模型，不读取也不迁移；下一次整体澄清创建或复用当前交付线的关联 Session。
5. 会话设置页的“内部会话显示”分组提供独立的“显示 Deliveryline 协作 Session”开关，默认关闭。关闭时该模块关联的 Session 不在 Runtime Sessions 主列表展示，但协作和既有任务不受影响；开启后可按普通 Session 的既有入口查看和管理。该设置仍由 Deliveryline 独立保存，仅与内部翻译 Session 共享展示入口，不复用其文字、配置或筛选范围。
6. AI 只能依据本轮输入生成候选建议、待确认问题或阶段方案规定的其他候选产出。它不得改写 `original_request_content`、直接写入共享交付线档案、自动推进或改变交付线状态，也不得把自身输出标记为验收通过。维护者确认后产生的业务资料和明确触发的推进操作，才适用对应阶段契约。
7. 已结束交付线不得发起新的协作轮次，但仍允许删除；删除交付线时，先按 Chub 通用 Session 删除流程取消关联任务、确认关联原生 Session 已删除并清理 Chub Session/任务记录，再删除共享交付线档案与 Deliveryline 本机关联资料。关联 Session 无法安全删除或最终状态无法确认时，交付线必须保留并报告失败，供维护者处理后重试；Deliveryline 不得因清理关联而伪造 Session 已停止或已删除。

### 协作轮次固定格式

每个阶段的 AI 协作方案必须明确以下内容：

| 字段 | 作用 |
| --- | --- |
| 触发条件 | 何时由维护者主动发起或继续协作。 |
| 本轮输入 | 必须传入的需求事实、阶段契约和维护者补充。 |
| AI 工作目标 | 该阶段希望 AI 协助完成的事情；必须与本阶段目标和验收标准一致。 |
| 建议产出 | AI 返回的候选资料、问题或证据形式。 |
| 页面交互 | 详情页如何展示建议、维护者如何确认、评论或继续处理。 |
| 确认后的业务结果 | 维护者确认会更新哪些正式资料，及是否允许推进；AI 本身不得产生该结果。 |
| 不确认或失败处理 | 建议被评论、任务失败、结果未知或资料不足时如何保留和恢复。 |

尚未定义阶段专属 AI 协作方案时，不提供该阶段的 AI 协作入口；不得仅因存在关联 Session 就假定 AI 能处理该阶段。

## 交付项工作循环与检查点

交付项不使用固定顺序的“当前阶段”作为唯一状态。它以当前交付目标、整体目标版本快照、影响分析和待完成检查点推进；同一检查点可以反复进入，未适用的检查点可明确跳过。页面最终应分别呈现交付项运行状态、待处理检查点、已确认结论和整体目标影响，不能用一个线性 `workflow.current_stage` 混合表达。

### 检查点规则固定格式

每个交付项检查点及其子步骤都必须按以下格式维护：

| 字段 | 作用 |
| --- | --- |
| 适用条件与关系 | 说明何时需要该检查点、依赖哪些已确认事实、可回到哪些前序检查点；不记录任何具体交付项的状态。 |
| 目标 | 说明本阶段要达成的业务结果。 |
| 页面目标摘要 | 面向维护者的一句等义摘要；必须从本阶段“目标”导出，不得独立维护业务含义。 |
| 输入 | 说明开始本阶段时使用的业务事实或前置结论。 |
| 产出 | 说明阶段结束时形成的业务资料或结论。 |
| 验收标准 | 说明如何确认目标已经达成。 |
| 推进与未通过处理 | 说明何时、由谁推进，以及资料不足或验收未通过时的处理。 |
| 需保留的业务事实 | 说明必须写入需求档案、不可仅存在于页面或运行态的事实。 |

尚未定义详细契约的检查点只填写“适用条件与关系”和“初步目标”；页面固定展示“详细检查点规则待制定。”，输入、产出、验收标准、推进与未通过处理、需保留的业务事实均标记为“进入该检查点前制定”。不得把初步目标视为已确认的验收规则或据此自动推进。

### 常用工作检查点

| 检查点 | 适用条件与关系 | 初步目标 |
| --- | --- | --- |
| 需求准备与正式成档 | 每个新交付项必须先完成；由 `1-1`、`1-2` 和 `1-3` 组成，后续发现目标不清时可重新进入。 | 保留原始资料、确认当前交付意图，并形成可讨论、可提交评审的正式档案。 |
| 需求评审 | 交付项需要评审决策时使用；以正式档案为输入，可要求回到澄清或成档。 | 确认是否值得实施、边界是否明确，以及后续需要哪些检查点。 |
| 方案设计 | 实现方式、交互、数据或验收方式需要设计结论时使用；可由评审或实施发现触发。 | 形成并确认适用于该交付项的方案与验收方式。 |
| 开发实现 | 交付项包含变更实现时使用；通常以已确认方案为输入，也可因实施发现回到澄清或设计。 | 按已确认范围完成实现，并记录执行结果；可由 AI Agent、人工或混合方式执行。 |
| 自动化测试 | 交付项需要可重复的技术验证时使用；测试不足或失败可回到设计或实现。 | 形成正常、异常、边界与回归行为的测试证据。 |
| 测试验收 | 交付项需要业务验收结论时使用；以适用的验收标准和证据为输入，可退回任一相关检查点。 | 确认真实交付结果，并决定交付项合格、继续调整或停止。 |

“自动化测试通过”不等同于“测试验收合格”：前者说明已获得测试证据，后者才是对交付结果的业务确认。上线、发布、运行观察与归档不属于上述检查点；后续如有需要，作为独立交付运维流程设计。

### 需求准备与正式成档

| 字段 | 阶段契约 |
| --- | --- |
| 适用条件与关系 | 每个新交付项的必经准备检查点，由 `1-1`、`1-2` 和 `1-3` 组成；整体目标变更、评审退回或实施发现目标不清时可重新进入 `1-2` 或 `1-3`。 |
| 目标 | 在保留只读原始资料的前提下，先确认当前交付项要改变什么，再形成可讨论、可提交评审的正式需求档案。 |
| 页面目标摘要 | 先澄清本次交付意图，再补全正式档案。 |
| 输入 | 维护者首次提交的任意非空原始资料，以及后续补充的当前交付目标和需求信息。 |
| 产出 | 原始资料来源记录、已确认的当前交付意图和补全后的正式需求档案。 |
| 验收标准 | `1-1`、`1-2` 与 `1-3` 均达到各自验收标准，且维护者显式提交需求评审。 |
| 推进与未通过处理 | 仅维护者可提交进入需求评审；交付意图或资料未澄清时停留在对应小阶段并指出待补充内容，不自动推进。 |
| 需保留的业务事实 | 原始资料、当前交付意图、正式需求字段、检查点结论、待处理事项、整体目标版本快照、活动记录和时间。 |

AI 协助和人工处理都是完成上述目标的方式，不构成新的阶段或小阶段。

#### 1-1 原始需求入库

| 字段 | 阶段契约 |
| --- | --- |
| 适用条件与关系 | 准备检查点的入口子步骤；完成后进入 `1-2`。 |
| 目标 | 保存首次输入的一句话、链接或混合内容，并保留为只读来源记录。 |
| 页面目标摘要 | 保存原始需求并建立需求档案。 |
| 输入 | 维护者提交的任意非空原始需求内容。 |
| 产出 | 具有唯一编号的初始化需求档案。 |
| 验收标准 | 已创建唯一的初始化交付项档案和编号；原始内容完整写入 `original_request_content` 且创建后只读；入库不读取链接、不启动 AI、不创建 Session 或建议；失败时不保留半成品档案或伪造成功结果。 |
| 推进与未通过处理 | 创建成功后自动完成 `1-1` 并转入 `1-2`；创建失败时停留在入库操作，不生成需求档案。 |
| 需保留的业务事实 | `id`、`original_request_content`、创建时间和创建活动记录。 |

#### 1-2 需求澄清

| 字段 | 阶段契约 |
| --- | --- |
| 适用条件与关系 | 位于 `1-1` 与 `1-3` 之间；后续发现当前目标、资料角色或整体目标版本不清时可重新进入。 |
| 目标 | 判断原始资料在当前交付项中的角色，确认“本次要改变什么”的最小交付意图；资料可以说明现状、长期设计、背景或明确需求，但不因存在资料就自动成为本次范围。 |
| 页面目标摘要 | 结合资料确认本次交付意图。 |
| 输入 | `1-1` 留存的原始资料，以及维护者补充的目标、场景或问题。维护者主动发起 AI 澄清时，才允许读取合规链接资料。 |
| 产出 | 资料角色、已知事实、当前交付目标、最少待确认事项；无明确交付目标时，不产出完整正式档案。 |
| 验收标准 | 维护者能够说明本次要改变什么、面向谁或什么场景、触发原因或问题、预期结果，以及资料在本次交付中的作用；仍缺少的事实明确列为待确认。 |
| 推进与未通过处理 | 信息不足时停留在 `1-2`，可继续补充或再次澄清；维护者确认当前交付目标后进入 `1-3`，不自动进入需求评审。 |
| 需保留的业务事实 | 原始资料、维护者确认的当前交付目标和必要澄清结论；AI 的候选总结与问题仍是本机协作资料。 |

##### AI 协作方案

| 字段 | 本阶段方案 |
| --- | --- |
| 触发条件 | 交付项已完成 `1-1`、当前处于准备检查点且未归档。维护者主动发起“AI 澄清”；未确认的候选结论可直接再次澄清，维护者填写的意见优先输入，但不要求逐项填写意见。 |
| 本轮输入 | `1-2` 的目标和验收标准、只读 `original_request_content`、已确认的当前交付目标（如有）、上一轮候选澄清与维护者意见。原始内容中的链接最多识别三项：已登记 Chub 项目资料页按固定文档 ID 读取有界正文；其他公共 HTTP(S) 链接仅对该次协作任务授予既有页面只读能力后读取；本机、内网、带凭据、不合规或读取失败的链接不扩展访问范围，AI 不得臆测正文，应写入待确认问题。资料正文仅作为本轮候选输入，不写入共享档案。 |
| AI 工作目标 | 识别资料是现状、设计提案、历史记录还是明确交付意图；区分已实现基线、长期路线图与当前交付目标，提炼已知事实并提出最少待确认问题。 |
| 建议产出 | 候选资料角色、已知事实、当前交付目标和待确认问题；没有明确交付目标时不得生成八项正式字段、虚构范围或验收标准。AI 输出始终是候选内容，不是阶段结论。 |
| 页面交互 | 页面展示资料来源、候选澄清和待确认问题；维护者确认或编辑当前交付目标后进入 `1-3`。 |
| 确认后的业务结果 | 维护者确认的当前交付目标写入交付项正式资料；原始资料不改写，不自动推进到需求评审。 |
| 再次协作 | 维护者可在补充目标、场景或意见后继续 AI 澄清；新一轮替换未确认候选结论，已确认事实保留。 |
| 阶段确认与失败处理 | 资料不足、任务失败、任务不存在或结果未知时停留在 `1-2`，保留最近可用候选和恢复入口；协作本机状态不可读取时停止新的协作写入并保留状态文件供恢复。 |

#### 1-3 正式需求整理与档案补全

| 字段 | 阶段契约 |
| --- | --- |
| 适用条件与关系 | 位于 `1-2` 与后续评审决策之间；正式档案因整体目标变化、评审或实施发现而失效时可重新进入。 |
| 目标 | 基于已确认的当前交付目标和相关资料，补全可讨论、可提交评审的八项正式需求字段。 |
| 页面目标摘要 | 依据已澄清目标，整理正式需求档案。 |
| 输入 | 原始资料、维护者确认的当前交付目标、`1-2` 的已确认事实，以及必要补充信息。 |
| 产出 | 标题、背景与问题、交付目标、本次范围、不做什么、约束与依赖、验收标准、风险与待确认事项。 |
| 验收标准 | 八项字段均完整、相互一致且只描述当前交付项；已实现基线和整体交付线资料只作为背景或约束，不被写成本次新增范围；维护者显式确认后具备提交评审资格。 |
| 推进与未通过处理 | 资料未补全时停留在 `1-3`；达标后仍须由维护者显式提交，才进入需求评审，不自动推进。 |
| 需保留的业务事实 | 八项正式字段、当前交付目标、可由正式字段计算的准备度、当前阶段、下一步、更新时间和编辑活动记录。 |

提交需求评审是 `1-3` 的出口动作，不表示需求评审阶段治理已经实现。进入需求评审后，页面只显示“详细阶段契约待制定。”；当后续开始设计任一尚未定义详细契约的交付项阶段时，必须先按本节固定格式补全其完整契约，再开始对应的页面、接口或执行能力设计。

## 当前范围与接入方向

Deliveryline 已以 Chub 业务插件接入，而非独立控制台。设置页与首页都读取统一生命周期状态，但投影规则不同：导入决定设置页插件管理入口是否显示；首页业务入口、业务页面和业务 API 均要求已启用且当前可用。ZIP 由本机构建流程写入固定制品目录，不经浏览器上传或下载。启用不会创建业务数据、Session 或任务。

当前页面以交付线为数据来源。详情标题右侧依次提供 **AI 整体澄清**、**结束交付线** 和危险次级操作 **删除**；结束与删除不在详情内容内重复展示。未确认时只展示原始资料、候选、待确认问题和修正入口，确认前不展示或创建交付项。维护者确认候选或修正后的内容，会写入当前目标并形成版本；确认后显示“规划中”，但不会提前生成路线图或交付项。旧六阶段原型不再使用。

当前业务模块宿主提供可信访问、固定 Deliveryline 插件包导入、实现选择、启停/可用状态、首页投影，以及交付线共享档案的读写 API 和页面交互。通用发现、任意第三方模块、动态页面注入、后续交付项治理、受控 Chub 用例和跨模块流程编排不属于当前阶段；出现第二个真实业务模块后，再依据共同需求定义标准协议。

## 共享档案与本机运行态

Deliveryline 的数据按是否为长期业务事实拆分，当前格式基线如下：

```text
data/shared/deliveryline/
  requirements/
    DL-20260912-A3F7.json
    DL-20260915-C8D2.json

data/local/state/deliveryline/
  # 本机锁、草稿恢复、缓存、协作轮次和模块运行状态
data/local/runtime/deliveryline/
  # 本机临时运行文件和 Session/任务关联缓存
```

每个共享需求文件只拥有一条需求，避免不同需求的独立修改集中到同一个大文件而扩大 Git 冲突范围。需求文件采用当前版本的严格 JSON 模型，不接受未知根字段；正式实现以固定 Pydantic 模型校验字段、枚举、时间和文件上限。共享档案不保存 Token、Cookie、账号、访问票据、本机绝对路径、原生 Session 标识或其他秘密。

| 字段组 | 字段 | 规则 |
| --- | --- | --- |
| 识别与时间 | `version`、`id`、`created_at`、`updated_at` | 系统写入；`id` 永不变更，`version` 只用于当前格式校验。 |
| 原始资料 | `original_request_content` | 首次创建时输入的一句话、链接或混合内容；创建后只读，是首次入库的唯一业务输入。 |
| 当前整体目标 | `title`、`source_role`、`overall_goal`、`confirmed_facts`、`scope_boundary`、`open_questions` | 只有维护者确认 AI 候选或其修正后写入；`source_role`不得为“未澄清”。 |
| 目标版本 | `goal_versions` | 每次已定义的目标变更流程确认后追加版本。当前实现只允许在首次整体澄清后形成 V1；目标变更和影响分析尚未实现。 |
| 交付线状态 | `status` | 固定为“待澄清、规划中、推进中、变更评估中、已结束”之一，表达整体治理进展；当前实现负责前两种与结束，不用其表达未来交付项检查点。 |
| 活动事实 | `activity` | 当前按时间追加创建、整体目标确认和结束记录；每项记录包含时间、动作和有界摘要，不保存原始敏感内容。 |

交付项运行状态、检查点记录、待处理事项和目标版本快照尚未实现；进入交付项建设前必须定义其权威字段，不得回用旧 `workflow`。

当前整体交付线已包含稳定标识、只读原始资料、当前目标、目标版本历史、状态和时间。路线图、交付项关联和影响分析记录尚未实现；交付项至少应包含稳定标识、所属交付线、目标版本快照、运行状态、检查点记录、待处理事项、正式档案和活动事实。整体目标版本与未来交付项快照都属于共享业务事实；AI 轮次、未确认建议和本机 Session 关联继续属于本机运行态。

共享目录以 Git 作为维护者主动使用的同步媒介，而不是在线协作数据库。Chub 不自动 `pull`、`commit` 或 `push`；同一需求在不同设备发生未合并冲突时，维护者先完成 Git 冲突处理，Chub 在文件重新合法且同步状态可确认前保持该需求只读。不同需求文件可独立保存和合并，不需要全局编号计数器。

## Deliveryline 建设里程碑

本章记录 Deliveryline 的建设目标和建设里程碑，用于拆分讨论、实现和验收顺序，不是整体交付线或单交付项的业务状态定义。工作检查点不构成固定生命周期；完成任一建设里程碑不会自动推进任何交付项。

### 总体目标

当前总体目标是建立一个面向个人 AI 协作的轻量交付管理能力：维护者能先从大资料确认整体交付目标和当前优先项，再将可独立验收的切片作为交付项推进；能看到每项要交付什么、当前处于哪个阶段、进入下一阶段还缺少什么、已有何种证据，以及最终是否经过测试验收合格。Deliveryline 负责这些业务事实、决策和结论；Chub 继续负责 Session、任务和运行终态，后者只能作为交付证据，不能替代业务验收。

### 目标调整规则

本章以 **2026-09-15** 的讨论结论为当前基线。后续可根据实际使用、实现成本或新的交付需求调整总体目标和建设里程碑的初步目标；详细范围、验收标准和完成判定，必须在开始对应建设工作时制定，不提前视为既定契约。已经验证的实现范围保留为事实，不因后续目标调整而改写。涉及整体交付线/交付项边界、交付项阶段、状态所有权、证据语义、Chub 执行关联或用户可见验收结论的调整，仍须重新评审本设计。

### 建设里程碑 1：单交付项台账与原型档案

**阶段目标**：让维护者能够建立并持续查看一个单交付项的交付上下文。

**交付内容**：基于“共享档案与本机运行态”定义的单交付项创建、编辑、归档和列表；标题、背景与问题、交付目标、范围、不做什么、约束、验收标准和风险/待确认事项；工作队列中的编号、标题、当前阶段、跨阶段状态、风险、最近更新和下一步；详情入口及基础活动记录；以及原型 AI 协作入口、关联与维护者确认流程。

**已验证基线**：单交付项原型可从一句需求描述建档，维护者可编辑字段、归档，并在资料缺失时被阻止提交评审；原型 AI 协作已完成本机状态、字段确认与页面/API 自动化测试。它不等同于新 `1-2` 或 `1-3` 的目标行为。

**后续调整**：该原型不能替代整体交付线与交付项两层模型。后续以新 `1-2/1-3` 契约替换原型资料整理行为；不把基础能力已验证理解为任一具体交付项已经完成需求提出阶段。

### 建设里程碑 2：整体交付线与交付项澄清

**初步目标**：让维护者将大设计资料保留为整体交付线，先澄清总体目标和当前优先项，再创建或选择一个当前交付项进行正式档案整理。

**验收标准与细项**：开始对应建设工作时定义整体交付线格式、目标版本、资料读取、路线图、交付项关联、AI 整体澄清的页面/API/候选结构/确认与修正方式、`1-2/1-3` 的页面/API/AI 协作、现有原型运行态清理和新实例最终状态确认；不得以当前单交付项 JSON 兼容承载新模型。

### 建设里程碑 3：交付项工作循环与检查点治理

**初步目标**：让每个交付项按适用检查点受控推进、回退、跳过或停止，并能清楚呈现当前运行状态与待处理事项。

**验收标准与细项**：开始对应建设工作时再制定检查点适用条件、资料要求、进入与完成条件、允许操作、跳过与回退规则、恢复方式和状态记录；不得重新引入“每条交付项固定六阶段”的状态机。

### 建设里程碑 4：证据与验收闭环

**初步目标**：让交付结论可追溯，不把执行活动误当作验收结论。

**验收标准与细项**：开始对应建设工作时再制定证据类型、存储边界、修改与删除规则、验收结论的确认方式和追溯要求。

### 建设里程碑 5：受控接入 Chub 开发执行能力

**初步目标**：在不改变 Chub 状态所有权的前提下，为“开发实现”阶段补充执行证据；它不替代前述已定义阶段的资料整理型 AI 协作。

**验收标准与细项**：开始对应建设工作时再制定可调用的固定 Chub 用例、关联记录范围、最终状态投影、失败恢复和不自动推进的边界。

### 建设里程碑 6：自动化与运营视图

**初步目标**：基于已确认的业务记录提升测试反馈与交付管理效率。

**验收标准与细项**：开始对应建设工作时再制定自动化结果来源、统计口径、通知范围、失败重试、人工覆盖和不形成第二套需求状态的约束。

建设里程碑 1 至建设里程碑 4 是首个可人工运行 MVP 的初步建设顺序，不构成后续里程碑的验收承诺。建设里程碑 5 和建设里程碑 6 在 MVP 的状态、证据和验收边界稳定后再评估是否开始。开始任一建设里程碑前，必须复核本设计、[Chub 总体架构设计](CHUB_ARCHITECTURE_DESIGN.md)和当前可用能力；涉及整体交付线/交付项状态所有权、交付项阶段名称、证据语义、Chub 执行关联或用户可见验收结论的变化，必须补充对应设计与回归。

## 验收范围与复检

当前已验证 Deliveryline 的插件生命周期、首页入口、交付线原始资料入库、AI 整体澄清候选、显式确认目标版本、结束和删除操作。路线图、交付项拆分、影响分析、交付项工作循环及真实 AI Runtime 端到端验收尚未实现；交付项后续治理、证据记录、Chub 开发执行关联、自动化测试结果和运营视图同样尚未实现。本轮未进行 macOS、Ubuntu 或多设备 Git 冲突实机验证。后续改变整体交付线/交付项状态所有权、检查点适用条件、推进条件、证据语义、Chub 关联协议或用户可见的验收结论时，必须重新评审本文并补充对应自动化与产品回归。
