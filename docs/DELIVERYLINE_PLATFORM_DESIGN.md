# Deliveryline 需求交付管理平台设计

> 状态：调研中
> 主要读者：负责定义需求交付流程的维护人员，以及后续实现 Deliveryline 的 AI Agent。
> 本文负责：定义 Deliveryline 的产品定位、主体阶段和与 Chub 的职责边界。
> 本文不负责：阶段内资料结构、页面交互、数据模型、AI Agent 调度协议、测试实现或发布运维流程；这些内容在进入对应阶段后再单独设计。

## AI 可执行契约

1. Deliveryline 是需求交付管理平台，不是 Chub 的别名或 Chub 的替代品。
2. 从需求提出到需求合格，主体阶段名称固定为：`需求提出 → 需求评审 → 方案设计 → 开发实现 → 自动化测试 → 测试验收`。后续不得因执行方式、人员或 Agent 类型重命名这些阶段。
3. `开发实现`是稳定的交付阶段名称；当前可由 AI Agent 执行，但“调用 AI Agent 开发”只是该阶段的执行方式或记录，不是新的主体阶段。
4. 方案经确认后才能进入开发实现；测试验收通过才可标记需求合格。验收未通过时，根据问题性质回到方案设计或开发实现。
5. Deliveryline 负责需求流程、阶段门槛、资料、决策、测试结果和验收结论；它不管理 AI Agent 在开发实现阶段内的具体推理、代码编辑或运行时状态。
6. Chub 仍是个人 AI 工作站，负责本机 AI Agent、Runtime、任务与运行环境的执行和最终运行状态。Deliveryline 未来可调用 Chub 发起开发任务，但本设计不定义调用接口，也不改变 Chub 当前能力或安全边界。

## 产品定位

Deliveryline 面向个人 AI 协作场景，管理一项需求从提出到验收合格的交付闭环。它关注“需求是否已具备进入下一阶段的条件”和“最终是否已验收合格”，而不是取代开发工具或运行环境。

Chub 与 Deliveryline 的关系为：

```text
Deliveryline：需求流程与交付编排
        ↓
Chub：个人 AI 工作站与本机执行控制
        ↓
AI Agent / Runtime：具体开发与测试执行
```

## 主体阶段

| 阶段 | 阶段目标 |
| --- | --- |
| 需求提出 | 明确需求目标、场景、范围、约束和验收预期。 |
| 需求评审 | 确认需求清晰、合理且具备实施价值，明确边界与风险。 |
| 方案设计 | 形成可确认的交付方案与验收标准。 |
| 开发实现 | 按已确认方案完成实现；可由 AI Agent、人工或混合方式执行。 |
| 自动化测试 | 通过可重复测试验证正常、异常、边界与回归行为。 |
| 测试验收 | 按验收标准确认真实结果；通过后需求合格。 |

上线、发布、运行观察与归档不属于上述“需求提出到合格”的主体阶段；后续如有需要，作为需求合格后的独立交付运维流程设计。
