# Chub 任务编排插件模块架构设计

> 状态：持续维护
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义当前统一任务编排分发架构，以及任务编排插件模块的通用职责、Chub 进程内能力执行面、请求与检查点模型、模块协议、生命周期和平台验收原则。
> 本文不负责：插件宿主的通用发现、生命周期、页面承载、能力调用和状态隔离（见[Chub 总体架构设计](CHUB_ARCHITECTURE_DESIGN.md)）、任何具体入口的认证、指令语法、用户可见交互、固定内部工作流细节或一次性实施步骤；一次性收敛记录见[任务编排收敛实施归档](archive/task-orchestration/CHUB_TASK_ORCHESTRATION_CONVERGENCE_DESIGN.md)。
> 维护说明：本文是 AI Agent 日常理解任务编排的唯一长期架构依据。当前实现以“当前实现”一节为准；能力清单和入口专项设计只补充当前能力、交互与路由，不得另行定义统一分发、状态所有权或恢复规则。

## 当前实现

Chub 当前只启用**空阶段链**，没有启用通用任务编排阶段插件。空阶段链不是绕过编排，而是由统一分发器创建或恢复编排请求后，直接完成一次物理主任务投递。

当前仓库已在 `modules/chub-modules.json` 登记首个开发任务编排模块
`chub-task-prompt-optimizer`。插件管理器按通用索引发现它、预检任务编排 Manifest 和入口，并登记开发实现或符合协议的 ZIP 制品；ZIP 使用通用插件候选目录和安全安装边界，导入会保存不可变的内容摘要引用。开发实现可通过通用生命周期启用或停用；Web 应用装配时只加载已导入、已启用且源码摘要仍匹配的开发实现，并校验入口返回的最小模块描述。插件管理页以“任务编排插件 · 任务提示词优化”显示模块，前者是插件类别，后者取自插件 Manifest；页面分别报告持久化启用状态、当前 Web 实例装载结果和待重载状态，启用状态本身不代表已加载。

通用任务编排插件宿主支持发现、协议预检、开发实现或 ZIP 制品导入、启停、最小入口装配确认和移除。此处描述通用宿主能力，不代表本案例的 ZIP 制品路径已完成独立交付验收；本案例目前验收的是仓库开发模块来源，ZIP 路径仍作为低优先级独立小功能暂缓。启用中的制品可通过通用移除入口直接移除；宿主先持久化停用，再清除开发实现登记或 ZIP 专属安装副本。当前插件没有已注册阶段和任务引用，故已启用或当前 Web 实例仍持有已装配入口本身不阻止移除；实例中旧入口待重载卸载时必须如实显示。移除开发实现不改仓库索引或源码；移除 ZIP 保留候选 ZIP 来源文件。首个插件的开发实现仅从仓库 `modules/chub-modules.json` 索引发现；制品 ZIP 复用通用插件候选目录与导入 API，不读取平级 `chub-local-modules/` 中同 ID 的本机源码。Manifest 预检要求通用协议版本、编排协议版本和能力协议版本均为 `1`，`scope` 为 `ordinary_user_task`，开发 Manifest 的 `chub_version` 为 `dev` 或当前版本，ZIP 必须精确匹配当前版本；`entry` 必须指向包内语法有效且声明了顶层入口符号的 Python 文件，`command_entry` 显式为 `null` 表示本插件不接收固定指令。预检以静态读取完成，不执行插件入口。

本项交付开发实现的启用、停用、移除和宿主装配确认；ZIP 制品的启停与加载、阶段注册与调用、能力投影、实现快照和恢复仍属于后续独立交付项。第一阶段第三个独立交付项已实现插件专属设置页及模式配置：设置入口位于插件管理侧栏的“任务编排插件”分组，模式控件即时保存且无单独保存按钮；默认配置为 `direct`，`auto` 在执行阶段就绪前保持不可选。当前最小入口仍只返回插件描述，不注册或调用阶段，因此 Web/微信普通任务继续使用空阶段链；设置页不展示常驻的阶段链未接入提示；不能把“已加载”或“已配置”视为提示词优化已经可用，当前模式仍未接入任务受理快照或普通任务执行。启停只改变持久化的后续装配目标；当前 Web 实例若仍持有先前装配的描述，会如实报告并标记待重载。加载失败隔离在该插件内，不阻断空阶段链或其他插件。后续开放阶段链前，必须由分发状态权威所有者提供活动请求引用检查；只有确认不存在未终态引用后才可清除对应实现。

### 普通用户任务

Web 快速交互和微信普通正文都由各自入口适配器完成认证、输入限制、入口去重、目标 Session 选择和交付关联保存，然后调用同一个 `TaskOrchestrationDispatcher`：

```text
Web / 微信入口适配器
        -> TaskOrchestrationDispatcher（唯一普通任务 writer）
        -> 空阶段链
        -> Quick Interaction / Quick Worker
        -> 原入口展示或微信回送
```

分发器持久化入口类型、入口幂等键、正文指纹、目标 Session、`operation_id`、物理任务关联和当前终态。它必须先保存入口幂等关联与 `operation_id`，再调用 Quick Interaction 提交 Worker；回执丢失或 Web/Worker 重启后，只能按 `operation_id` 对账，找回则回写原任务，无法确认则记录明确失败，不能创建替代任务。

当前普通任务的分发状态使用 `accepted`、`running`、`completed` 和 `failed`；`waiting_capability`、阶段 cursor 和能力调用记录属于未来启用非空阶段链时的扩展，不是当前空阶段链的运行状态。

### 固定内部工作流

周报、今日关注、部署包说明和 Deliveryline AI 整体澄清等固定内部工作流可以直接调用 Quick Interaction/Quick Worker，不进入普通任务分发器，也不匹配通用阶段插件。它们各自拥有业务状态，必须在物理提交前持久化自己的 `operation_id`，在回执丢失或重启后按该 ID 对账，并收敛到明确终态。固定工作流不能因此成为普通用户任务的旁路入口。

### 状态所有权与退役边界

- 普通任务幂等关联和入口到物理任务的映射由分发器状态负责。
- Chub Quick Interaction 状态负责 Session 任务、Worker 交付和操作上下文；Quick Worker 状态负责物理任务执行与最终终态。
- Web 请求关联和微信通知路由只由各自入口适配器持有，不进入通用分发器或 Worker 任务模型。
- 分发器状态不可读、校验失败或不可写时，只拒绝新的普通任务；不得清空状态，也不得阻断无关能力。
- 终态记录只做轻量留存；受信维护入口只能清理终态，不能影响活跃任务。清理后旧浏览器请求 ID 失效，用户必须明确重新提交。
- 旧微信润色状态、确认队列和专属阶段已退役；`text` / `text-check` 明确拒绝，不降级为普通任务。

## AI 可执行契约

任务编排插件复用[总体架构](CHUB_ARCHITECTURE_DESIGN.md#212-插件宿主通用能力)规定的模块发现、导入、启停、页面承载、公开能力调用、状态隔离和恢复能力。本节只定义任务编排特有的阶段执行面、分发请求、检查点和版本绑定。

1. **统一任务编排分发点**是用户普通任务在提交 Quick Worker 前的唯一正式边界。入口适配先完成自己的认证、幂等、输入限制、固定指令识别和目标选择，再以规范化任务信息调用分发点；分发点创建或恢复编排请求，按创建时快照串行调用零个或多个编排阶段，并且只能由分发点决定下一阶段或最终物理主任务投递。空阶段链就是直接执行，不是绕过这条边界。Chub 继续拥有权限、实际执行、任务终态、通知、日志和插件模块维护。
2. 任务编排插件模块处理的是**已准备执行用户需求的逻辑处理阶段**，而不是入口拦截器。模块不能取得原始入口控制权，也不能解释其他模块或主模块的指令。前缀目录、未导入或重建期间的提示由入口 Chub 适配维护；命中受保留前缀时不得静默回退为普通任务。
3. 模块与 Chub 同机，由宿主按总体架构的模块发现和装配规则加载。任务编排的**进程内能力执行面**不是远程服务或通用 HTTP API；它只能通过宿主授予的公开能力投影工作。
4. 模块只能查询并调用本次编排请求获得授权的能力投影。能力目录和公开用例以[总体架构](CHUB_ARCHITECTURE_DESIGN.md#213-能力目录与公开用例)及[Chub 集成能力清单](CHUB_INTEGRATION_CAPABILITIES.md#11-核心能力)为准；能力 ID 不是模块可直接导入的函数。任务编排模块不得操作 Worker、Runtime、入口路由、文件、网络或系统命令，也不得提供 Runtime、原生 Session、路径、命令、URL、环境变量、收件人或身份材料。
5. 当前空阶段链至少保存编排记录 ID、入口幂等关联、入口种类、规范化正文指纹、固定目标 Session、`operation_id`、物理任务关联和最终状态。启用非空阶段链后，再按受理快照增加当前任务文本、阶段链与 cursor、固定实现引用、授权能力、能力调用记录和检查点。入口幂等关联是重复入口的权威关联；编排记录只能与其一对一绑定，重启对账不能以新请求替代原记录。模块只定义检查点与下一任务文本，不能直接读写 Chub 持久化状态。
6. 能力执行面只返回 `succeeded`、`waiting`、`rejected`、`unavailable` 或 `unknown`。模块只能依据可信成功或对应等待关联的终态推进；不得以 HTTP 成功、进程启动、日志文本或模型正文推断成功。
7. 启用非空阶段插件后，模块在一个事件回合中至多请求一次能力，随后返回检查点、等待声明或下一任务文本。它不能以未受控线程、计时器、连接或内存会话推进流程。阶段完成不等于用户主任务完成：阶段返回下一任务文本后，Chub 分发点才继续后续阶段或最终投递；只有物理主任务终态才决定用户完成通知。当前空阶段链不执行模块回合或能力调用。
8. 分发器必须先持久化入口幂等关联与 `operation_id`，再提交物理任务。持久化请求尚未回写任务 ID 时，重试与重启必须先按 `operation_id` 对账并校验目标与正文指纹；能找回任务则回写关联，确认未接受或无法确认时写入明确失败终态。不得把所有未关联请求笼统报为“状态未知”。
9. 分发状态文件不可读、超限、校验失败或路径不安全时，分发器进入局部不可用并拒绝新的用户普通任务；不得删除、覆盖或初始化为空状态。只有已定义的整体运行态清理流程才能同时清理该状态与关联 Quick Worker 任务。
10. 编排记录最多保留 5,000 条。活跃记录不清理；终态记录仅保留幂等键、指纹、操作 ID、任务关联和终态，不保留原始正文，启动时也会压缩遗留终态正文。达到固定留存上限时拒绝新的普通任务，而不是自动丢弃或静默重放旧请求。维护者可通过受信 `POST /api/maintenance/task-orchestration/compact` 明确清理**终态** tombstone；操作记录 `requested`、`started`、`succeeded` 或 `failed`，绝不影响活跃请求。清理后旧浏览器请求 ID 不再有效，页面必须由维护者重新明确提交以生成新 ID；该维护入口不是工作站重建的替代品。

## 架构范围与非范围

本文定义所有入口共享的分发、阶段、能力和恢复边界；具体能力是否已交付、哪些入口接入、阶段如何匹配，以及插件的用户可见状态，都由能力清单和相应专项/交付设计决定。任何入口未接入本文契约前，不得因模块存在而被隐式视为可编排。

编排 ZIP 的 `implementation_ref` 是“插件标识 + 版本 + 内容摘要”的不可变产物引用；它在请求创建时固定。它不是 Runtime 的 `implementation_id` 槽位，不能用于选择 Runtime、Session 或 Runner，也不能复用 Runtime 插件的目录、注册表或维护操作。

## 统一任务编排分发点、入口适配与状态

```text
外部通道入口适配                                  Web 入口适配
认证、入口幂等、指令、路由、目标选择              可信浏览器、请求、目标 Session
       |                                                 |
       `------------------ 规范化提交意图 -----------------'
                                   |
                                   v
                         统一任务编排分发点
            创建/恢复请求、匹配阶段、固定快照与推进 cursor
                 ├─ 空阶段链 → 唯一最终主任务投递 → Quick Worker / Runtime
                 └─ 当前阶段（开发实现 / 已激活模块）
                      → 阶段内部按需调用受限能力
                      → 返回下一任务文本、检查点或等待声明
                      → 回到同一分发点，从下一阶段继续
                                   |
                                   v
                      可信主任务终态 → 原入口交互适配
                                   ├─ 通道：保存路由的通知/确认交互
                                   └─ 页面：时间线/模态确认
```

统一任务编排分发点是提交**外部用户主任务**的唯一 writer；它拥有编排请求、阶段链快照、当前位置、能力调用记录、检查点、活动偏好、最终主任务关联和编排最终状态。入口适配只负责把已验证的请求转换为规范化提交意图，至少包含入口种类、入口幂等关联、规范化正文、固定目标 Session 与不透明的原入口交付关联。交付关联只由原入口适配持有和使用：通道可保存受控回送路由，页面可保存可恢复的请求关联；模块和阶段均不可读取、修改或推断它。

阶段匹配是按提交意图的入口种类、任务正文类型和已启用模块范围进行的局部决策，不是全局门禁。没有匹配或已启用阶段时，分发点创建空阶段链并直接投递；某一模块未导入、停用或故障不得阻止不匹配的入口或独立能力。只有请求已快照选中某个阶段后，该阶段不可用、结果未知或失败才使该请求失败关闭，不能跳过阶段、执行原文或改投其他实现。

Worker 不加载或重新解释任务编排插件；它只执行分发点在没有后续阶段时提交的受控物理主任务。内部阶段子任务必须标记为内部任务，不能再次进入分发点形成递归；固定自动化、周报和维护任务也不因本文自动纳入该边界。插件在 Chub 控制面收到调用或可信能力完成事件后进入下一回合。

确认、取消、结果展示和外部回送属于入口交互适配，不属于模块协议。未来阶段专项若定义确认操作，只能恢复已经持久化的编排请求并交回分发点；它不能创建替代请求或绕过阶段。通道入口可以使用固定指令、专项定义的确认交互和保存的回送路由；页面入口可以使用时间线、预览和模态确认，但它们必须共享同一请求快照、阶段推进、最终主任务唯一投递和恢复规则。当前空阶段链不创建确认队列。

入口中的可信语音只在通道层用于确认来源并取得干净转写；进入 Chub 后，转写与文字都作为同一类规范化任务正文。携带任务正文的固定指令可先由 Chub 完成固定目标选择，再将正文和该目标的受限授权上下文交给编排；没有任务正文的固定指令不创建编排请求。续提、确认、取消等操作只恢复或推进已有请求的检查点，不创建新的编排请求。

启用非空阶段链时，编排逻辑状态可使用 `accepted`、`running`、`waiting_capability`、`resuming`、`completed`、`discarded` 或 `failed`；当前空阶段链只使用 `accepted`、`running`、`completed` 和 `failed`。`completed` 只表示最终物理主任务已经确认完成，不能用于表示逻辑阶段完成。Worker 任务状态、Session 生命周期、Native 映射和通知终态继续分别以其专项设计为准。重复入口消息只读取首次请求的当前决定或终态，不重新创建副作用。

重启后，Chub 先对账已提交能力的真实结果：可确认则按原检查点和原模块产物恢复；未完成则继续等待；结果未知且继续会重复副作用时明确失败。不得切换到当前活动模块、内置流程、另一 Runtime 或另一 Session 来“恢复”已受理请求。

### 统一分发点的最小恢复契约

分发点接收用户需求时保存阶段链快照和 `cursor`；每次阶段完成或可信子任务终态到达时，先持久化该阶段结果及下一 cursor，再安排下一次分发。重复回调只能读取已经持久化的阶段结果，不能再次推进 cursor 或重新投递子任务。空阶段链和 cursor 已越过链尾时，分发点才可创建一次最终物理主任务；该任务的终态再收敛整个编排请求。阶段可使用受限能力完成内部工作，但其子任务终态不得被误作最终主任务终态或用户完成通知。

## 插件包协议与生命周期

任务编排插件使用总体架构规定的统一模块生命周期；它不取消已受理请求，也不清除已导入实现或所选版本。任务编排专属规则是：插件关闭时，匹配范围内的新请求使用空阶段链直接提交；入口不得读取插件专属设置、创建阶段续提或因该设置读取失败拒绝直接路径。阶段模式、匹配条件和用户可见交互由相应专项设计定义。任一入口接入相同分发点时，必须明确其匹配范围、默认空链策略和用户可见交互，不能因为模块已启用就隐式改变新入口任务。

已导入模块在停用后仍保留其已登记指令的最小“排空”能力：只读队列、确认、取消或推进已受理请求可以继续路由，不能变更后续任务配置或新建编排请求。模块实现、阶段链和受理时快照是存量任务的权威依据；停用、替换或当前活动版本变化不得改写它们。只有没有非终态引用后才允许移除相应产物。

正式或已导入的任务编排插件包复用总体架构的插件包安全、安装隔离和宿主生命周期规则。其包根目录有唯一的 `chub-capability-orchestration.json`，且 `module_type` 固定为 `capability-orchestration`。`scope` 是阶段匹配的稳定受控标识，不是入口 UI 或通知协议。新的 scope 必须先完成对应入口到统一分发点的接入、宿主协议支持、请求恢复规则和专项验收，不能仅靠新增清单字符串宣称可用。需要接收入口指令的模块还必须在清单声明固定 `command_entry`；该入口只返回受限命令描述或“不匹配”，不能取得原始路由、执行或持久化能力。页面阶段不得借用通道 `command_entry` 作为交互接口。模块返回值仍由 Chub 限制在该模块预先登记的指令组，不能映射为核心维护、模型或 Session 指令。任务编排插件使用独立的实现引用、阶段注册和恢复记录，不能复用 Runtime 插件的实现槽位或注册表。

具体编排任务可使用 Chub 固定加载的**开发实现**。它在活动偏好中以 `development_ref` 表示，只从仓库内的固定开发目录加载，不接受页面、外部通道、插件或配置传入的代码路径。开发实现与已导入 ZIP 并列为受控实现类型，且直接加载其 ZIP 打包的同一仓库源码目录；它不提供任意插件发现或安装。插件管理页保留固定开发实现和已导入 ZIP 的状态，并统一决定是否启用；导入 ZIP 不会自动启用，任务设置选择版本时只在已启用范围内切换，不删除源码或改写已受理请求的阶段链。已导入但停用或不可用的实现仍保留在插件管理列表与工作台状态中；设置侧边栏和任务设置只展示当前可选实现。设置页仅以能力名称展示实现：开发实现为“`<能力名称> · 开发实现`”，ZIP 为“`<能力名称> · 正式版 v<版本号>`”；`development_ref` 与 `implementation_ref` 保持内部绑定，不得显示、接受或由名称反推。

每次加载开发实现都计算源码摘要，并将“开发实现名 + 源码摘要”保存到已受理请求的阶段链快照。存在引用该摘要的非终态请求时不得重载其开发目录；Web 重启后发现已保存摘要与当前源码不一致时，相关请求明确失败，不得以新源码继续旧检查点。导入 ZIP 时 Chub 对解压产物计算内容摘要，并保存 `module_id@version+内容摘要` 作为独立、不可变的 `implementation_ref`；每次调用前重新校验安装目录内容摘要，摘要不一致的已受理请求明确失败。

清单至少声明 `protocol_version`、`module_id`、`version`、`scope`、`orchestration_protocol_version`、`capability_protocol_version`、`display_name`、`description`、`chub_version`、`entry` 和 `command_entry`。`command_entry` 仅接收原始 prompt 并返回受限命令描述或“不匹配”；它不能取得路由、执行、持久化或能力调用权限。未知协议、无效入口、超出声明范围、输入/检查点模型不兼容或能力执行面协议不支持时，候选必须保持未激活。

Chub 为每个导入包计算不可变 `implementation_ref`（`module_id@version` 加内容摘要）。活动偏好以 `scope -> 有序阶段引用列表` 保存：空列表表示直接投递。阶段引用是结构化数据，至少包含阶段类别和稳定标识；开发和 ZIP 阶段分别保存其 `development_ref` 或 `implementation_ref`。已受理请求固定其完整阶段链及各阶段摘要。相同版本的新包也是新产物，不能覆盖或删除仍被非终态请求引用的旧产物。阶段链变更、停用或替换只影响后续新请求；已受理请求继续原阶段链，不能自动改投或回退。

`module_id`、`module_type`、活动状态中的 `orchestration_module_ref`、阶段 `kind="module"` 和 `orchestration_modules_dir` 配置键都是已保存请求、插件包或本机配置的兼容字段。它们不代表产品仍使用“外置模块”定位，后续不得仅为文案统一改写；新增产品文案、代码对象和操作记录统一使用“任务编排插件”。

| 阶段引用 | 含义 | 已受理请求绑定 |
| --- | --- | --- |
| `development_ref` | 具体任务的固定开发实现名加源码摘要 | 相同开发实现与摘要；源码变化不得继续旧检查点 |
| `implementation_ref` | 已导入 ZIP 的插件标识、版本和内容摘要 | 相同 ZIP 产物 |

导入、激活、停用、替换、移除和恢复均记录 `requested`、`started`、`succeeded` 或 `failed`。目录写入、入口加载或 HTTP 成功不代表操作成功；必须确认注册表、活动偏好和受影响请求的最终状态。通用宿主移除开发实现只撤销导入登记；移除 ZIP 实现还清理该制品专属安装副本，原始候选 ZIP 保留。“替换”通过导入新不可变产物并切换活动引用完成，不覆盖同版本旧产物；被非终态请求引用时拒绝移除。没有未结束请求时，移除当前活动 ZIP 会清空其活动引用；是否同时关闭某项专项能力由该专项设计定义。插件专属缓存可按固定白名单清理，Chub 通用设置、编排记录、Session、Worker 任务、通知和第三方数据不得清理。

## 通用接入与验收

任务入口分为两类：

- **用户普通任务**：Web 快速交互、微信普通正文及未来同类的人工自由正文入口，必须经过统一分发点，才可能匹配通用阶段插件。
- **固定业务或内部工作流**：周报、今日关注、部署包说明和 Deliveryline AI 整体澄清等受固定业务状态、固定提示词与独立用户终态约束的流程，可以直接使用 Quick Worker，不进入阶段插件。它们必须在物理提交前持久化自己的 `operation_id`，在提交回执丢失或重启后按该 ID 对账，记录明确终态；不能把“进程创建”或“已受理”当完成。若某个工作流将来需要通用阶段，必须以新入口单独接入，不能把既有直接提交流程隐式泛化。

新增具体编排任务或入口接入前，必须先定义其入口上下文、允许能力、模块范围、关闭/开发实现/ZIP 实现的启用分流规则、开发实现名与源码摘要规则、检查点语义、用户可见终态和失败边界。用户普通任务必须通过统一分发点进入 Worker；内部阶段任务必须明确排除，防止递归。具体设计不得扩大为全局任务执行器，也不得把能力执行面暴露为任意 HTTP 调用入口。

除总体架构规定的插件宿主通用验收外，任务编排还必须验证：能力越权与伪造引用被拒绝；重复入口不重复执行；能力结果未知不产生替代副作用；重启、模块回合中断、停用、替换和移除不改写已受理请求。新增入口还必须验证空阶段链仍经分发点只投递一次主任务、入口交互只恢复自身已持久化请求、内部阶段任务不会递归进入分发点，以及一个入口的模块故障不会阻断无关入口。真实外部通道的收发仍由维护者在对应客户端完成验收。
