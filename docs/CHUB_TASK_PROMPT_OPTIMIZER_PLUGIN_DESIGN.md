# Chub 任务提示词优化插件设计

> 状态：持续维护
> 主要读者：AI Agent；维护者通过与 AI Agent 协作，理解并确认本文规则。
> 本文负责：定义一个独立任务编排插件如何接收已受理的普通用户任务，按启用后的运行模式直接返回或优化任务提示词，并把可执行提示词交回统一分发器；同时定义插件请求主项目创建、恢复和提交内部优化任务的边界。
> 本文不负责：入口认证、入口字段规范化、固定指令语法、目标 Session 选择、统一分发器通用协议、Quick Worker 执行和固定内部工作流；这些规则分别以[总体架构](CHUB_ARCHITECTURE_DESIGN.md)、[任务编排插件模块架构设计](CHUB_TASK_ORCHESTRATION_PLUGIN_DESIGN.md)、[Chub 集成能力清单](CHUB_INTEGRATION_CAPABILITIES.md)和对应入口专项设计为准。

本文是一个独立任务编排插件的专项设计。主项目已经负责把 Web 或微信普通任务转换为受控的规范化任务请求；本文只定义插件如何消费该请求、处理任务正文和返回结果，不重复描述前置规范化实现。

## 1. 插件定位

任务提示词优化插件挂载在统一任务编排分发器的阶段链中，功能上承接此前微信任务润色的“改善任务正文、使其更适合 AI 执行”的目标，但实现上是入口无关的通用任务编排插件。插件的启用状态与运行模式是两个不同概念：启用状态决定插件是否进入流程，运行模式决定进入插件后是否执行 AI 优化。

```text
Web / 微信普通任务
  -> 主项目入口校验与规范化
  -> TaskOrchestrationDispatcher
  -> （插件未启用：空阶段链，直接投递）
  -> （插件已启用：任务提示词优化插件）
       ├─ direct：原规范化正文直接返回分发器
       └─ auto：请求主项目创建/恢复普通内部 Session -> 主项目提交优化任务 -> 返回分发器
  -> 唯一物理主任务投递
  -> Quick Worker / Runtime
```

插件不是入口拦截器、不是第二个任务提交器，也不是旧微信润色模块的兼容层。插件不直接接收微信消息，不读取 Web 请求，不维护微信回送路由，不创建确认队列，不直接调用 Worker。

当前插件已进入通用任务编排模块索引并支持宿主协议预检、开发实现导入登记、启停、最小入口装配确认及移除；设置侧栏的“插件管理 → 任务编排插件”分组提供专属设置页，模式控件以模式名和说明分两行展示、变更后立即保存且不设单独保存按钮，默认配置 `direct`，`auto` 在执行阶段就绪前不可选。设置保存在插件专属本机状态中，且可在插件停用时查看和修改。设置页不展示常驻的阶段链未接入提示；当前配置尚未接入任务受理快照，任务阶段也未接入非空阶段链，因此配置不会改变普通任务行为。开发实现移除只撤销宿主登记并保留仓库源码和索引；通用宿主具备 ZIP 处理能力，但本插件的 ZIP 制品路径尚未作为独立交付完成验收；ZIP 实现移除同时清理插件专属安装副本并保留来源 ZIP。插件的发现、启停、实现引用、阶段快照和模块故障隔离遵循[任务编排插件模块架构设计](CHUB_TASK_ORCHESTRATION_PLUGIN_DESIGN.md)；本文不重新定义通用宿主能力。

### 插件状态与运行模式

| 插件状态 | 运行模式 | 是否进入插件 | 插件行为 |
| --- | --- | --- | --- |
| 未启用 | 无 | 否 | 分发器使用空阶段链，直接投递主任务 |
| 已启用 | `direct` | 是 | 不创建内部 Session、不调用 AI，立即返回原规范化正文 |
| 已启用 | `auto` | 是 | 请求主项目为本次请求创建或恢复普通内部 Session，提交一次优化任务并返回结果 |

启用状态和运行模式都在任务受理时固定到阶段链快照；后续停用插件或切换模式只影响新任务。`direct` 是插件内的直接返回模式，不等同于插件未启用，也不绕过统一分发器。

## 2. 任务来源

插件只处理已经通过主项目入口校验并由统一分发器受理的**普通用户任务**：

| 来源 | 是否支持 | 插件看到的内容 |
| --- | --- | --- |
| Web 快速交互 | 支持 | 主项目提供的规范化任务正文、固定目标 Session 和受限任务上下文 |
| 微信普通正文 | 支持 | 主项目提供的干净文字或可信语音转写，以及固定目标 Session 和受限任务上下文 |
| 微信固定指令 | 不直接支持 | 由微信入口先处理，不创建本插件阶段请求 |
| `text` / `text-check` | 不支持 | 旧能力明确拒绝，不进入本插件 |
| 周报、今日关注、部署说明等固定内部工作流 | 默认不支持 | 继续使用各自直接调用 Quick Worker 的业务流程；除非另行完成入口接入设计 |
| 插件或阶段内部任务 | 不支持 | 不得递归进入本插件或统一分发器 |

插件不根据正文自行猜测来源。入口类型、内容类型、目标 Session、请求幂等关联和 `operation_id` 已由主项目确定；插件只能读取本次阶段授权的受限投影。

## 3. 优化目标

插件在 `auto` 模式下的目标是把用户原始任务正文转换为**更明确、更完整、更适合后续 AI 执行的任务提示词**，同时保持原任务意图和执行边界不变。`direct` 模式不改变正文，只验证并返回入口已经规范化的正文。

允许的处理方向包括：

- 补充任务目标、上下文、约束和预期结果的结构化表达。
- 消除明显歧义，整理用户已经表达的要求和验收条件。
- 将口语化、简略或不完整的任务描述转换为清晰的执行说明。
- 保留用户指定的语言、专有名词、路径、标识、代码和明确格式要求。

禁止的处理方向包括：

- 改变用户目标、扩大权限、增加未授权的操作范围或虚构事实。
- 自行选择 Runtime、Session、模型、文件、命令、URL、收件人或外部账号。
- 执行任务、修改文件、调用外部服务或替用户确认高风险动作。
- 把插件结果当作任务完成，或绕过分发器直接提交 Worker。
- 自动恢复旧微信确认队列、旧微信专属设置或旧润色状态。

插件输出的是“下一步要执行的任务提示词”，不是最终业务结果，也不是面向用户的独立回复。

## 4. 插件输入

插件输入由统一分发器根据受理时快照提供。本文只约束插件可消费的字段，不重新定义主项目的入口规范化过程。

| 输入 | 说明 | 插件边界 |
| --- | --- | --- |
| `entry` | `web` 或 `weixin` | 只用于受控匹配和处理策略，不得据此读取入口私有状态 |
| `task_type` | 当前为 `ordinary_user_task` | 不接受插件或用户改写 |
| `content_type` | 普通文字或可信语音转写等受控类型 | 只能使用主项目已经确认的类型 |
| `content` | 已规范化的任务正文 | 只读；不得修改原始受理快照 |
| `session_id` | 固定目标 Session 的受限引用 | 不得重新选择、切换或创建 Session |
| `markers` | 主项目根据可信入口事实提供的受控标记 | 不得伪造入口来源或新增未登记标记 |
| `mode` | `direct` / `auto` | 由插件启用配置在受理时快照；插件不能由正文或模型自行切换 |
| `operation_id` | 当前编排操作的关联 ID | 用于关联阶段记录；不得创建替代主任务 |
| 阶段检查点 | 当前插件阶段的持久化输入和恢复信息 | 只能按插件协议读取和返回 |

插件不得接收或保存微信账号、收件人、Context Token、客户端凭据、任意路径、命令、原始 HTTP 请求或未授权的 Runtime 私有配置。

## 5. 运行模式与提示词输出

### `direct` 模式

插件接收分发器提供的规范化正文后，完成最小输入校验并立即返回原正文：

```text
input.content -> output.optimized_prompt
```

`direct` 模式不创建内部 Session、不调用 AI、不产生插件子任务、不创建确认项。返回结果交回分发器，由分发器继续唯一物理主任务投递。

### `auto` 模式

插件通过 Chub 宿主授予的受控 AI 能力执行提示词优化。插件不得直接调用模型供应商、OpenClaw、`openclaw agent`、Quick Worker 或 Runtime 私有对象。插件只能向主项目公开能力提出创建/恢复内部 Session、提交内部任务和读取任务结果的请求；Session、任务和底层执行均由主项目对应的公开用例负责。宿主能力调用的授权、结果枚举和最终状态以总体架构与任务编排架构为准。

进入 `auto` 模式后，插件请求主项目为当前父编排请求创建或恢复一个标记为 `internal` 的提示词优化 Session。该 Session 不是用户目标 Session，不用于执行最终任务；其是否出现在 Runtime Sessions 主列表中，统一由 Chub 内部 Session 可见性开关控制，类型标记与列表规则以[Chub Session 状态模型设计](AI_SESSION_STATE_DESIGN.md)为准，配套实现完成前本插件能力仍未开放。插件不持有 Session 状态，也不直接调用 Session Manager；主项目负责创建、恢复、关联和最终状态确认。Session 请求必须绑定父 `operation_id` 与阶段调用 ID；重试和重启只能恢复已有 Session/调用，不能重复创建或重复执行。

内部 Session 使用主项目规定的内部默认 Runtime、模型、权限和工作区，插件不能自行选择或覆盖这些配置。主项目在外部任务受理时固定这组内部执行配置；配置之后的修改只影响后续受理任务。内部优化任务使用普通任务提交协议和 `standard` 任务类型，不使用已退役的 `translation` 类型、旧翻译队列或微信通知任务类型。提示词优化用途、父编排请求和阶段调用关系由主项目编排状态记录，不通过新增 Worker 任务类型表达。内部任务不绑定 Web 请求或微信通知路由，结果只返回给插件和分发器，不产生独立用户通知。

主项目必须提供受控的内部任务能力，用于按本次阶段请求创建或恢复普通 Session、提交 `standard` 任务和读取该任务结果。该能力由主项目的公开用例负责状态写入、Worker 协调和最终状态确认；插件只能提交受限参数和读取结果，不能把内部任务伪装成 Web/微信用户任务，也不能直接调用 Session Manager、Quick Worker 或 Runtime。

主项目在提交内部优化任务前，必须以阶段调用 ID 作为内部 Session 创建和任务提交的幂等关联。插件或分发器重启后，先按父 `operation_id` 和阶段调用 ID 查询已有 Session、任务及结果；只有确认尚未创建或提交时才能继续请求，不能用新的 Session 或新的任务替代原请求。

一次 `auto` 阶段回合最多发起一次受控 AI 处理。插件向 AI 能力提供：

- 已规范化的任务正文。
- 本插件固定的处理目标和输出格式约束。
- 本次任务允许使用的非敏感上下文。
- 明确的禁止事项：不得虚构事实、扩大权限或执行任务。

成功时必须返回结构化结果，不能把解释性文字直接当作任务正文：

```text
optimized_prompt       优化后的任务提示词
processing_summary     可选的非敏感处理摘要，仅供阶段记录
checkpoint             可恢复的阶段检查点
```

`optimized_prompt` 只包含下一步要执行的任务正文，必须满足主项目任务正文的长度、非空和结构限制；不得包含“以下是优化结果”等包装文字。`processing_summary` 只能是有长度上限的非敏感内部摘要，不进入用户通知或最终任务正文。分发器收到结果后重新校验，并将其作为下一阶段任务提示词；没有后续阶段时，才由分发器提交唯一物理主任务。

插件不返回 Worker 任务 ID，不返回微信通知路由，不直接发送用户通知，也不宣称主任务成功。

## 6. 状态、幂等与恢复

插件阶段状态归统一分发器所有，至少包括：

| 状态 | 含义 |
| --- | --- |
| `accepted` | 编排请求已受理，尚未开始插件回合 |
| `running` | 插件回合或其受控 AI 能力正在处理；`direct` 模式可快速经过此状态 |
| `waiting_capability` | 已保存等待关联，等待可信能力结果或恢复事件 |
| `resuming` | 已找回阶段检查点，准备继续同一请求 |
| `completed` | 插件阶段已返回合法处理结果；不代表物理主任务完成 |
| `failed` | 插件或恢复无法安全继续，当前请求明确失败 |

插件阶段必须绑定父编排请求、模式快照和不可变实现引用。`direct` 模式的阶段结果是原规范化正文；`auto` 模式的阶段结果还必须绑定内部 Session 和内部任务调用检查点。阶段检查点至少保存父 `operation_id`、阶段调用 ID、模式、实现引用、输入指纹、内部执行配置快照、内部 Session 关联、内部任务关联、阶段状态和最终结果引用。创建或提交内部任务前必须先保存检查点；重复回调只能读取已保存的检查点，不能重复调用 AI 能力；Web 或 Worker 重启后只能恢复原阶段、原模式、原实现和原内部配置，不能切换当前活动实现，也不能重新创建替代任务。

`auto` 模式的检查点还必须保存一个受控子阶段：`session_create_pending`、`session_ready`、`task_submit_pending`、`task_accepted`、`result_pending` 或 `result_ready`。主项目对 Session 创建、任务提交和结果查询分别使用父 `operation_id`、阶段调用 ID 与动作名称组成的幂等关联；每次调用前先写入对应的 pending 子阶段，回执丢失时先按同一关联查询，不得用新 Session 或新任务替代原请求。

恢复规则：

1. AI 调用回执丢失时，按父 `operation_id` 和阶段调用关联对账。
2. 能确认结果且结果校验通过时，回写原阶段检查点并继续分发。
3. 结果未完成时只在固定的阶段对账窗口内等待原关联，不创建第二次调用。
4. 结果未知且继续调用可能产生重复副作用时，阶段明确失败。
5. AI 优化失败、输出为空、输出超限或输出无法校验时，不得回退执行原始正文。

`waiting_capability` 只表示仍在等待原内部任务的可信终态，不表示等待用户确认。等待使用受理时固定的阶段超时或对账窗口；窗口结束仍无法确认时，阶段必须进入 `failed` 并记录脱敏原因，不得无限等待、自动重投或回退执行原文。

`direct` 模式没有 AI 调用和内部 Session；它只需要持久化阶段完成结果，然后回到分发器，不进入等待或确认流程。

插件停用、实现替换、运行模式切换或模块故障只影响尚未受理的新请求；已受理请求继续使用受理时固定的启用状态、运行模式、实现和阶段快照，无法恢复时明确失败。

## 7. 用户可见结果

插件处理过程不是独立的用户任务，不单独产生一条 Web 或微信任务，也不单独发送完成通知。

- 插件成功：用户最终看到的是后续物理主任务的正常执行结果。
- 插件等待：入口根据已有请求状态展示处理中或等待状态，不创建新请求。
- 插件失败：入口展示明确失败原因和原请求终态；用户只能明确重新提交，不能自动回放原请求。
- 微信回送：仍由微信入口保存的原路由负责，插件不能直接发送消息。
- Web 展示：仍由 Web 页面原请求关联负责，插件不能替换浏览器请求 ID。

若未来具体场景需要用户确认处理后的正文，必须新增编排检查点和入口交互设计；确认只能恢复原编排请求，不能恢复旧确认队列，也不能创建第二条物理任务。

## 8. 插件实现与生命周期

插件应作为独立任务编排模块登记，至少定义：

- 稳定 `module_id`、版本和 `scope`。
- 插件协议版本、能力协议版本和 Chub 兼容版本。
- 阶段入口、输入/输出模型和固定处理目标。
- 允许匹配的 `task_type`、`content_type`、入口范围和标记。
- 所需 Chub 能力投影及其失败边界。
- 开发实现或 ZIP 实现的不可变引用和内容摘要。

插件通过 Chub 通用模块机制完成扫描、导入、启用、禁用和加载。导入不自动启用；启用或停用只影响后续受理的新任务，已受理任务继续使用创建时固定的阶段链和模式快照。插件导入后，在插件管理列表中展示通用生命周期操作；设置页通过“设置 → 插件管理”侧栏的“任务编排插件”分组独立进入。专属设置页面只负责维护 `direct` / `auto` 模式等插件配置，不重复提供导入、启用、禁用或移除等生命周期操作。模式选项以名称和说明分两行展示，不以中点连接；控件变更后立即持久化，保存成功后只影响后续受理的任务，不能改写已受理任务；读取或保存失败必须显示真实错误，保存失败恢复此前确认的选项，不展示未确认成功状态。

插件包、开发实现、状态隔离、操作日志、替换和移除规则统一遵循[任务编排插件模块架构设计](CHUB_TASK_ORCHESTRATION_PLUGIN_DESIGN.md)和[总体架构设计](CHUB_ARCHITECTURE_DESIGN.md)的宿主边界。

## 9. 验收标准

首个实现至少验证：

1. Web 和微信普通任务均能从统一分发器进入插件，固定指令和内部工作流不会误匹配。
2. 插件只消费主项目已规范化的任务正文，不读取入口私有路由或敏感凭据。
3. 插件未启用时不进入插件；主任务直接投递。
4. 插件已启用且为 `direct` 时不创建内部 Session、不调用 AI，原正文只返回一次并继续投递一个物理主任务。
5. 插件已启用且为 `auto` 时，插件只请求主项目创建或恢复一个普通内部提示词优化 Session，并以 `standard` 任务类型提交一个内部优化任务；AI 成功后只产生一个优化结果，并由分发器继续提交一个物理主任务。
6. AI 回执丢失、Web/Worker 重启、插件回合中断后，按原 `operation_id`、模式和检查点恢复，不重复创建 Session、调用 AI 或投递任务。
7. AI 结果未知、失败或输出不合法时，任务在固定对账窗口内等待原关联，窗口结束后明确失败，不执行未经处理的原文。
8. 重复 Web 请求或重复微信消息只关联首次编排请求，不创建第二个插件回合或 Worker 任务。
9. 插件停用、运行模式切换、版本替换或实现不可用不会改变已受理任务，也不会阻断不匹配的普通任务和无关 Chub 能力。
10. 受理任务后修改内部 Runtime、模型、权限或工作区默认配置，不改变该任务已保存的内部执行配置。
11. 当前不实现自动优化后的人工确认；插件成功后直接回到分发器。
12. 用户最终收到的是物理主任务终态；插件阶段完成不能提前触发完成通知。
13. 真实微信发送、回送和用户可见结果由维护者在微信客户端完成验收。
14. 插件能通过通用模块机制被发现、导入、启用并加载；导入不自动启用，插件不可用时不影响不匹配的普通任务和无关 Chub 能力。
15. 已导入插件的设置入口出现在“设置 → 插件管理”侧栏的“任务编排插件”分组；插件扫描列表不显示设置按钮，只承担通用生命周期操作。停用插件仍可从侧栏进入设置，移除后侧栏入口消失。
16. 插件专属设置页能读取模式；模式选项名称与说明分两行显示、不用中点连接；模式控件变更后立即保存，不提供单独保存按钮。保存成功后不显示重复的常驻成功提示；保存失败恢复原值并展示错误。模式变更只影响后续受理的新任务。
17. 已受理任务继续使用受理时固定的模式、实现和阶段链，设置变更、停用或替换不能改写这些任务。

## 验收范围与复检

本文定义完整插件运行契约；通用生命周期接入、最小入口装配及独立设置页/模式配置对应第一阶段三个独立交付项，维护者已按案例文档记录验收通过。验收范围限于仓库开发模块路径，不代表本插件 ZIP 制品路径已验收。设置页不显示常驻的阶段链状态提示，但配置仍未进入任务受理快照，非空阶段链和提示词优化执行尚未交付。插件协议、能力执行面、实现引用、阶段状态所有权、入口匹配范围、恢复规则或用户可见终态发生变化时，必须重新完成本设计对应的自动化和真实入口验收。本文不替代主项目已经验收的入口规范化、统一分发器和 Quick Worker 契约。
