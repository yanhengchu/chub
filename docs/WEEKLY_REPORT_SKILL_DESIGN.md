# 工作周报生成技能设计方案

> 状态：评审完成，首版技能已实现。本文定义技能和数据契约，实现位于 `.agents/skills/generate-weekly-report/`。

## 1. 背景

Chub 已通过 `V 国内业务周报` 自动化任务导出主周报及“各端周报”章节中的关联文档。下一步需要基于以下本地原始数据生成本期业务周报：

- 一份上周周报，用于延续事项、历史背景和正式稿结构参考。
- 当前 V 业务所需的五份本周其他端周报，用于提取本周指标、版本、问题、专项和风险。
- 可选的本周周会记录、人工补充和事项负责人最新确认。

`V 国内业务周报/周报工作流.md` 已沉淀完整的周报整理规则。Chub 技能只使用其中与“自动化下载材料的本地汇总”直接相关的规则。

## 2. 目标

在 Chub 项目内提供可复用的 `generate-weekly-report` 技能，实现：

1. 读取自动化任务已经导出的本地 Markdown 原始数据，以及维护者明确提供的补充信息。
2. 校验输入是否齐全、是否存在失败或无法确定的使用范围。
3. 从各份材料中提炼本期重点，先生成供维护者确认的重点清单。
4. 经维护者确认后，生成正式周报和生成核对记录。
5. 保持事实、数据、版本、日期、状态和责任边界可追溯。
6. 不修改原始数据，完成本地 Markdown 和核对记录后结束。

## 3. 首版范围

### 3.1 包含

- 本地 Markdown 文件读取。
- 一份上周周报、当前 V 业务所需的五份本周各端周报，以及可选周会和补充材料的输入约定。
- 按日期或章节限制每份材料的本周使用范围。
- 本期重点提炼和人工确认门禁。
- 正式 Markdown 周报生成。
- 输入、口径、冲突、缺失项和 Review 结果记录。
- 确定性的格式及完整性检查。
- 使用现有周报样本进行回放验证。

### 3.2 不包含

- 打开飞书、识别链接或下载文档。
- 从截图、图片或 Canvas 表格中恢复数据。
- 自动补导失败文件。
- Chub 首页入口、API、调度器或任务状态改造。
- 数据库、任务队列或新的复杂基础设施。

下载仍由现有自动化能力负责；技能只消费已经落盘的数据。后续如需一键执行，应由上层编排顺序调用“下载任务”和“生成技能”，不把两者合并为一个不可拆分流程。

## 4. 设计原则

1. **原始数据只读**：所有生成文件写入独立输出目录。
2. **事实优先**：不能为提高文案完整度猜测缺失结论。
3. **范围受控**：全量历史周报只读取明确指定的本周日期或业务章节。
4. **先确认重点**：未确认重点清单时不生成正式稿。
5. **冲突显式化**：无法按优先级解决的多来源冲突标记为“口径待确认”。
6. **下载与就绪分离**：文件下载成功不等于内容已经完整、复核并可用于正式汇总。
7. **修改全局联动**：维护者修正一个口径后，必须检查摘要、正文、风险和来源中的旧口径残留。
8. **技能保持精简**：流程写入 `SKILL.md`，详细口径按需放入 references，确定性检查放入脚本。
9. **首版人工触发**：先验证生成质量，再考虑接入 Chub 页面或定时任务。

## 5. 总体流程

```text
飞书自动化下载
      ↓
本周原始数据目录
      ↓
输入和范围校验
      ↓
本期工作重点确认清单
      ↓
维护者确认或调整
      ↓
本期业务周报
      ↓
格式校验 + 事实 Review
      ↓
周报生成核对记录
```

本期周报周期固定为周一至周日。每周三开始本期处理窗口，周三至周日处理当周周期；下周一、周二继续处理同一周期，并在下周二固定报送。各端完成时间不一致，因此下载由维护者手动触发。本期只维护唯一的 `inputs/`：主周报、五类本期各端周报和上周参考在同一次暂存下载中完成校验，全部成功后才整体替换输入；任一来源失败即丢弃本次暂存结果并保留上一份完整有效输入。各端来源的统计范围不要求固定为周一至周日：单日、本周周一至周五或从上周延续至本周的范围均可；其单日日期或范围结束日期只要落在本期周一至周日内，即可作为本期输入。输入变化会使既有 Manifest、确认和正式稿失效，必须重新校验后再生成。

流程分为两个阶段：

- **阶段 A：重点确认**。先读取主文档 `V 国内业务周报` 的“重点关注内容”，逐条与各端本期事实交叉核对并标明纳入、合并、降级、排除或待确认；再读取全部有效输入，只做事实提炼、取舍建议和待确认项整理。
- **阶段 B：正式生成**。以确认后的重点清单为主线，回到原始材料核对事实后生成正式周报。

如果输入存在缺失或阻塞，默认停在阶段 A。只有维护者明确同意带缺口继续时，才生成正式稿，并在重点清单和核对记录中说明缺失范围及其影响。

## 6. 输入与输出契约

### 6.1 本地工作目录

```text
data/artifacts/weekly-reports/
└── 2026-07-20至2026-07-26/
    ├── inputs/
    │   ├── <主周报源文档名称>.md
    │   └── linked/
    ├── mapping.json
    ├── manifest.json
    └── output/
        ├── 本期工作重点确认清单-2026-07-20至2026-07-26.md
        ├── weekly-report-confirmation.json
        ├── 本期业务周报-2026-07-20至2026-07-26.md
        └── 周报生成核对记录-2026-07-20至2026-07-26.md
```

目录名称表达角色，不要求来源材料使用固定标题。技能不得只靠诸如“产品周报.md”的自然语言文件名猜测用途，应优先读取 manifest 中的角色和使用范围。

### 6.2 Manifest

当前由技能内的只读适配脚本在自动化下载完成后生成 `manifest.json`：

```json
{
  "version": 1,
  "report_period": {
    "start": "2026-07-20",
    "end": "2026-07-26",
    "timezone": "Asia/Shanghai"
  },
  "documents": [
    {
      "role": "previous-report",
      "path": "previous-weekly-report.md",
      "title": "上周业务周报",
      "source_url": "https://tenant.feishu.cn/wiki/document-id",
      "download_status": "succeeded",
      "content_status": "ready",
      "usage": {
        "mode": "reference-only"
      }
    },
    {
      "role": "product",
      "path": "01-product.md",
      "title": "产品周报",
      "source_url": "https://tenant.feishu.cn/docx/document-id",
      "download_status": "succeeded",
      "content_status": "ready",
      "downloaded_at": "2026-07-24T18:00:00+08:00",
      "run_id": "automation-run-id",
      "sha256": "file-sha256",
      "source_period": {
        "start": "2026-07-17",
        "end": "2026-07-23"
      },
      "usage_period": {
        "start": "2026-07-17",
        "end": "2026-07-23"
      },
      "period_note": "来源按周四截止，与正式周报周期不完全一致",
      "usage": {
        "mode": "heading-range",
        "start_heading": "日期：2026-7-23",
        "end_heading": "日期：2026-7-16"
      }
    }
  ]
}
```

材料角色分为：

- 必需角色：`previous-report` 以及当前周报配置声明的本周业务来源，例如 `product`、`music-product`、`operations`、`client`、`server`。
- 可选角色：`weekly-meeting`、`manual-confirmation`、`supplemental-material`。

五份本期周报是当前 V 业务配置，不应硬编码成技能永久限制。Manifest 或适配配置负责声明本期必需角色；新增、删除或更换来源时不修改技能主流程。

首版支持以下 `usage.mode`：

- `reference-only`：仅作为结构、背景和延续事项参考，不作为本周事实来源。
- `whole-document`：整份文档作为本周输入。
- `heading-range`：从开始标题读取至结束标题之前。

每份材料分别记录：

- `download_status`：自动化是否成功获得并落盘文件。
- `content_status`：文件内容是否允许进入正式汇总。

`content_status` 首版支持：

- `ready`：内容完整，可用于正式汇总。
- `needs-review`：需要人工复核，默认阻塞正式生成。
- `incomplete`：内容缺失或边界不完整，默认阻塞。
- `still-editing`：来源仍在编写，默认阻塞。
- `stale`：不是本周期最新有效结果，默认阻塞。
- `manually-approved`：维护者已明确复核或同意带入。

`download_status: succeeded` 不能替代 `content_status: ready`。若维护者允许带缺口继续，必须将决定及影响写入重点清单和核对记录。

`path` 必须是相对受控 `source_root` 的 Markdown 路径，并解析在该目录内。允许自动化下载目录中的相对子目录，不接受绝对路径、目录穿越或远程 URL 作为本地输入路径。

Manifest 中不保存 Cookie、Token、账号信息或其他浏览器状态。`source_url` 只用于文末来源链接和事实追溯。

`downloaded_at`、`run_id` 和 `sha256` 用于判断数据新鲜度和生成期间的文件变化。适配器必须为每份输入生成 SHA-256，正式生成前再次校验，不使用弱校验替代。

`source_period` 记录来源材料自身统计周期，`usage_period` 记录本次实际采用的范围，`period_note` 说明与正式周报周期的差异。除 `reference-only` 的上周背景材料外，每份本期事实来源必须声明 ISO 格式的 `usage_period`。本期归属以单日日期或范围结束日期为准：结束日必须落在本期周一至周日内，开始日可早于周一。适配器和输入校验同时检查正式周期是否为完整周一至周日、开始日不晚于结束日及结束日归属，避免下载时间或部分内容重叠被误判为本期。生成时：

- 不把来源周期改写成正式周报完整周期。
- 指标正文或表头保留原始统计周期。
- 不直接比较统计窗口不同的数据；确需比较时明确说明周期差异。
- 摘要引用跨周期数据时同样保留口径，不能只在核对记录中说明。

### 6.3 与自动化当前输入的关系

`V 国内业务周报` 自动化先下载到本次暂存目录，只有主文档、五类本期各端周报和上周参考全部通过各自校验后，才整体发布到当前周期工作区的唯一 `inputs/`。尚未更新的来源会保留原输入并呈现等待状态，不作为可供阶段 A 使用的缺口材料。适配器只读已发布目录，生成的 Manifest 将 `source_root` 约束在同一工作区内；不会修改输入文件。每次进入阶段 A 前重新生成并校验 Manifest，避免使用已被来源更新替代的确认结果。

适配规则必须显式配置“哪一份是上周参考、哪些是本周必需和可选事实来源”。不能仅按关联文件顺序永久绑定业务角色，因为线上链接顺序可能变化。

周会记录和补充材料如果由现有主文档中的特定章节提供，适配器应通过明确的 `heading-range` 建立独立材料条目；不能依赖固定章节编号猜测周会位置。

人工确认可以来自当前对话，但必须同时持久化到重点清单和 `output/weekly-report-confirmation.json`。确认 JSON 还必须保存输出目录相对的重点清单路径和其 SHA-256。正式稿校验检查确认状态、Manifest fingerprint、重点清单哈希及配置要求的清单章节，任一项变化都会阻止生成完成。

### 6.4 章节边界匹配

飞书导出的 Markdown 标题可能包含强调标记、转义符、额外空格和不同日期格式。`heading-range` 匹配前应进行受控标准化：

- 去除 Markdown 标题符号和强调标记。
- 还原标题中的常见 Markdown 转义字符。
- 合并多余空格，但不改写普通正文。
- 将可识别日期解析后再比较，兼容 `2026-7-23`、`2026.7.23` 等常见形式。
- 开始或结束边界不存在、不唯一或顺序错误时停止，不自行选择。
- 支持显式的 `to-end-of-document`，用于读取开始标题至文件末尾。

Manifest 应保存原始标题、标准化后的匹配值和边界判断依据，方便核对。标准化只用于定位范围，不修改原始文件。

## 7. 技能结构

建议新增：

```text
.agents/skills/generate-weekly-report/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── manifest-contract.md
│   ├── report-structure.md
│   ├── review-rules.md
│   └── v-report-profile.md
└── scripts/
    ├── adapt_downloads.py
    └── validate_weekly_report.py
```

### 7.1 `SKILL.md`

只保留执行所需的核心流程：

- 读取 manifest 并校验输入。
- 按 usage 范围读取材料。
- 生成重点清单并等待确认。
- 根据确认结果生成正式稿。
- 执行校验和事实 Review。
- 生成核对记录。

### 7.2 `references/report-structure.md`

维护 OKR 化正式稿的默认结构和摘要要求：

1. 业务关键指标。
2. 产品体验提升。
3. 产品营收提升。
4. 项目质量提升。
5. AI 工程化推进。
6. 其他重点工作。
7. 需关注与决策事项。
8. 各端周报。

这是默认结构而非固定模板。技能应按本周实际内容合并、增加或省略空章节，不能依赖历史周报固定编号。

“各端周报”是正式稿必需章节。业务摘要默认不生成；仅在维护者明确要求时保留，且必须是 4—6 条管理结论、不得复述 OKR 正文。其他章节按本周实际内容生成；风险为空时统一省略风险章节，不为了满足模板虚构“无风险”结论。通用校验不会无条件要求所有默认章节；需要稳定模板的业务线应在 mapping 的 `report_validation` 中声明必需章节、段内标签和重点清单章节。当前 V 模板应要求业务关键指标、四项 OKR、各端周报，所有 OKR 的“目标：”及前三项指标型 OKR 的“当前进展：”。

每项 OKR 的标题与原文内容直接放在对应正文标题下，原文内容使用“目标：”标签，不设置会重复原文的 OKR 总览章节。指标型 OKR 在目标后增加“当前进展：”：使用最新可比周期并保留周期；缺少实际达成数据时明确说明缺口，不将活动、版本或局部指标写成目标达成。正文再使用“关键进展”“持续跟进与风险”“质量与合规”“待决策”等标签展开事实。

正式稿不放置输入资料清单、编制说明、内部缺失说明或重复的各端周报链接；顶部直接进入业务关键指标或第一项 OKR 正文。明确不属于 OKR 的专项使用“其他重点工作”，跨目标风险、资源协调和管理选择使用“需关注与决策事项”，两者均不得重复正文细节。

### 7.3 `references/review-rules.md`

维护 V 周报工作流中适合复用的事实规则：

- 信息优先级：维护者或负责人最新确认 > 本周明确会议结论 > 本周各端周报 > 上周周报。
- 上周事项必须被标记为继续、更新、关闭或不纳入。
- 根因、初步判断、验证动作和后续计划分开表达。
- “可能修复”不能写成“将修复”，“待排查”不能写成确定结论。
- 简要会议记录必须结合上下文理解，编号项可能是后续任务，不一定是问题原因。
- 已上线使用完成时态，计划上线使用计划时态。
- 相对日期尽量换算为具体日期。
- 百分比和百分点分开计算。
- 全文统一标题层级、术语、单位和时态。
- 多来源状态无法统一时保留双方口径并标记待确认。
- 图片中无法读取或未经复核的数据不作为确定事实。
- 版本号、人名、金额、日期、广告位名称和专业字段必须按原文核对并能回溯到来源。
- 不因追求精简而丢失必要背景、当前结论或下一步。
- 风险章节只保留需要提醒、协调或决策的事项，不重复展开正文。

### 7.4 `references/v-report-profile.md`

维护 V 业务特有的来源提取清单，不把业务分类写死在通用技能主流程中：

- 产品商业化：指标变化、会员、广告、推荐、版本规划和待决策事项。
- 产品/OS：重要事项、OS 版本、横向需求和运营事项。
- 运营：用户运营、内容运营、付费运营和曲库运营。
- 客户端：只读取“五、VIVO国内”章节，提取版本计划、横向问题、核心业务及技术指标和风险；不读取公共事项和其他客户端业务组。
- 服务端：只读取“一、南京服务端 @薛峰”章节，提取版本迭代、曲库与图谱、商业化、推荐、活动、线上问题和稳定性治理；不读取其他服务端业务组。
- 周会：新增问题、明确结论、验证动作和后续任务。

重点确认和完整性 Review 都应逐项检查该清单。业务来源或分类变化时更新此 profile，不修改通用生成流程。

### 7.5 `scripts/validate_weekly_report.py`

脚本只做确定性校验，不判断业务重要性。建议检查：

- Manifest 格式、完整周一至周日周期、来源范围结束日归属、角色和路径安全。
- 配置声明的必需角色是否存在、非空、下载成功且内容状态允许汇总。
- 每份 `heading-range` 的开始和结束边界是否唯一且顺序正确。
- 文件 SHA-256 是否与重点确认时一致。
- 正式稿是否包含各端周报；业务摘要仅在存在时检查其格式；按 mapping 的 `report_validation` 检查业务线声明的章节和段内必备标签。
- 确认 JSON 是否以安全相对路径和 SHA-256 绑定重点清单，清单是否保留当前 Manifest 指纹及声明的确认章节。
- Markdown 表格每行列数是否一致。
- 文末是否保留来源链接，正文顶部是否重复出现链接清单。
- 是否残留“待核对”“口径待确认”等未处理标记。
- 是否引用明显超出使用范围的历史日期标题。
- 技能自行生成的金额、环比和百分点计算方向是否与原始数字一致；产品报告已发布的指标变化保持原口径，只在核对记录中注明疑似差异。
- 跨周期指标是否保留来源统计周期。

脚本校验失败时不得把周报标记为完成。对于维护者明确允许保留的待确认项，通过显式参数或核对记录白名单处理，不能静默忽略。

## 8. 阶段 A：重点确认

技能逐份读取有效范围后生成重点确认清单，至少包含：

1. 主文档声明的每项 OKR：原始标题和目标文案必须保留，每个本期重点事项按主归属放入对应 OKR，并标注已处理、持续跟进、持续推进、评审中、待决策或资料已输出等状态。
2. `其他重点工作`：仅放置已确认重要、但不属于任何 OKR 的专项。
3. 建议合并或弱化的事项，以及建议不纳入的历史内容、其他业务线内容和重复事项。
4. 多来源冲突和缺失信息。
5. 需要维护者确认的问题。
6. 建议的正式稿叙事结构。
7. `重点关注内容对照`：记录主文档每项优先信号的最终去向。
8. 按来源统计的重点覆盖情况。

每条重点只做轻量提炼，保留关键数据、版本号、日期、状态和责任边界，不提前写成完整汇报文案。

重点清单必须由维护者明确确认或调整。确认可以在对话中完成，但结果必须持久化到重点清单的“维护者确认结果”部分，至少记录：

- 确认时间。
- 同意纳入、弱化或排除的事项。
- 待确认问题的最终口径。
- 是否允许带缺口继续及批准范围。
- 确认时对应的原始文件 SHA-256 和 Manifest fingerprint。

没有持久化确认结果时不得进入正式生成。`manually-approved` 只对记录的文件、范围和问题生效，不能理解为整份材料的所有内容均已复核。

重点确认后、正式生成前必须再次检查原始文件 SHA-256 和 Manifest fingerprint。如果文件或使用范围发生变化，应使旧确认失效并重新生成重点清单，不能将旧确认结果套用到更新后的材料。

## 9. 阶段 B：正式生成

正式生成以确认后的重点清单为主线，并再次回到原始材料核对事实：

1. 从上周周报识别需要延续、更新或关闭的事项。
2. 从五份本期周报提取指标、版本、需求、问题、专项和风险。
3. 合并重复事项，保留关键数字、日期、版本和状态差异。
4. 同一事项优先按“现状或数据、当前结论、验证动作、下一步”组织。
5. 默认不生成业务摘要，直接进入业务关键指标或第一项 OKR 正文；仅在维护者明确需要管理结论总览时生成 4—6 条不重复正文的结论。
6. 每项 OKR 保留原始标题和目标文案，并以“目标：”“当前进展：”“关键进展”“持续跟进与风险”“质量与合规”或“待决策”等层级组织；“当前进展”只使用目标口径的可比数据，缺失时明确说明。
7. 未归属 OKR 的专项使用“其他重点工作”；跨目标风险、资源协调和管理选择使用“需关注与决策事项”，不重复正文细节。
8. 各端来源链接统一放在文末，不在顶部重复。
9. 将输入口径、未采用内容和生成限制写入核对记录；只有影响业务判断的缺口才进入正式稿。
10. 对关键指标表优先保持来源字段、行列、行顺序、空单元格、负责人、状态、备注、统计周期、单位和数据；单元格内换行使用 `<br>` 保留，不因展示宽度转置、拆分、删列、缩写或自行补内容。
11. 对所有来源执行完整性、准确性和文案三类 Review，通过后才能标记生成完成。
12. 单独检查所有待协调和待决策事项是否已纳入正文、风险章节或明确不纳入。

技能不得修改自动化下载源文件或下载任务状态；本地 Markdown 和核对记录生成完成后流程结束。

### 9.1 三类 Review

1. **完整性 Review**：逐份检查来源中的重点事项是否已纳入、合并、明确不纳入或标记待确认；上周延续事项必须有继续、更新、关闭或不纳入的结论。
2. **准确性 Review**：检查数字、日期、版本、人名、链接、状态、责任边界和事实层级；产品报告发布口径按原文保留，技能自行生成的金额、环比和百分点执行算术及方向校验。
3. **文案 Review**：检查标题层级、术语、单位、时态、重复和表达清晰度，避免过度压缩导致背景、结论或下一步缺失。

核对记录应生成来源覆盖表：

```text
| 来源 | 使用范围 | 重点数量 | 已纳入 | 已合并 | 不纳入 | 待确认 |
```

### 9.2 维护者 Review 的全局联动

维护者提出每一条修正后，都必须：

1. 提取受影响的版本号、需求名、指标、金额、日期、风险项和关键词。
2. 修改对应内容后全文搜索正式稿。
3. 检查业务摘要（如存在）、各项 OKR、其他重点工作、需关注与决策事项和文末来源是否仍有旧口径。
4. 需求在版本之间移动时，同时检查移出和移入版本。
5. 数字或金额变化时检查比较方向和相关计算。
6. 事项重要性变化时检查是否应进入、移出或调整业务摘要（如存在）。
7. 事项移动章节后检查原章节是否仍有重复。
8. 将最终修正点和残留检查结果写入核对记录。

每轮 Review 后都执行一次残留检查，不能只在最后一轮处理。

## 10. 核对记录

每次生成应输出核对记录，至少包含：

- 实际使用的文件、角色、日期或章节范围。
- 未使用的历史章节和其他业务线范围。
- 输入失败、缺失和人工放行项。
- 本周采用的关键口径。
- 多来源冲突及最终处理。
- 未引用的图片数据。
- 校验脚本结果。
- 维护者 Review 后的关键修正。
- 全文残留检查及算术方向校验结果。
- 按来源统计的重点覆盖表。
- 是否仍有待处理事项。
- 本周新发现的可复用问题。

核对记录用于追溯生成过程，不放入正式周报顶部。

## 11. 异常处理

| 场景 | 默认处理 |
|---|---|
| Manifest 缺失或格式错误 | 停止并报告，不猜测全部文件角色 |
| 任一必需来源下载失败 | 停在重点确认前，列出缺失材料 |
| 使用范围标题不存在或不唯一 | 停止对应材料读取，要求确认边界 |
| 文件包含历史全量 | 只读取 manifest 指定范围 |
| 图片数据不可读 | 不作为确定事实，记录限制 |
| 多来源状态冲突 | 按信息优先级处理；仍无法判断则待确认 |
| 上周事项在本周无更新 | 不沿用为本周事实，标记待确认或不纳入 |
| 重点确认后原始文件变化 | 旧确认失效，重新生成重点清单 |
| 维护者要求带缺口继续 | 在重点清单和核对记录中写明影响后继续 |
| 正式稿校验失败 | 保留草稿但不标记完成 |

## 12. 安全与隐私

- 设计文档和技能不得包含真实 Token、Cookie、账号或终端票据。
- 输入路径必须限制在明确的周报数据根目录下。
- 自动化原始数据可能包含内部业务信息，不通过公开 API 暴露全文。
- 日志只记录受控任务 ID、文件角色、相对路径、状态和错误摘要，不记录文档全文。

## 13. 验证方案

### 13.1 回放验证

使用已有 `2026-07-13至2026-07-17` 六份原始材料回放：

1. 构造 manifest 并标明五份本周来源的日期或章节范围。
2. 生成本期重点确认清单。
3. 使用历史确认结果生成正式稿。
4. 与现有正式周报比较章节覆盖、关键数字、版本状态、风险和来源链接。
5. 差异不要求逐字一致，但不得出现事实错误、范围外历史内容或重点遗漏。

### 13.2 边界验证

- 缺少一份本期周报。
- 文件为空或非 UTF-8。
- 日期标题缺失、重复或顺序错误。
- 周报包含多周历史内容。
- 客户端或服务端文件包含多个业务组。
- 图片存在但正文没有可验证数据。
- 两份来源对同一版本给出不同状态。
- Markdown 表格列数不一致。
- 下载成功但内容状态为 `needs-review` 或 `still-editing`。
- 重点确认后原始文件哈希或重点清单哈希发生变化。
- 来源结束日落在本期外、周期不是完整周一至周日、缺少 `usage_period`。
- V 模板缺少必需 OKR、目标或当前进展标签。
- 维护者修正版本归属、金额或风险章节后仍有旧口径残留。

### 13.3 基础验证

- 运行技能目录校验。
- 运行校验脚本单元测试和一次真实样本测试。
- 运行 `git diff --check`。
- 验证新增设计文档能被 Chub 设计文档列表读取。

## 14. 实施与维护状态

1. `generate-weekly-report` 技能、只读适配器、输入校验、确认门禁和正式稿校验均已实现。
2. 自动化下载按固定报送周期维护同周期唯一输入集；汇总保持人工触发和确认门禁，不接入定时生成或自动串联。
3. 后续每周在核对记录中复盘可复用问题；只有来源结构、业务范围或稳定口径变化时才更新技能规则。

## 15. 评审结论

1. 周报周期固定为周一至周日，并在每周三切换；周三至次周二的所有下载和汇总保持同一周期。
2. 周报专属自动化在 `data/artifacts/weekly-reports/<周期>/inputs/` 保存一次完整校验后发布的输入集，Manifest 与 `output/` 位于同一周期工作区。
3. 当前五份本期周报的必需角色由 Manifest 显式声明，并允许每周增加可选材料。
4. 采用“两阶段生成”：先确认重点清单，再生成正式稿。
5. 正式稿只生成本地 Markdown，核对记录完成后流程结束。
